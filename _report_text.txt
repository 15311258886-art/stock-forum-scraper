二、问题清单（按严重程度）
P0
自测脚本 selftest.py 必失败，无法作为回归基线
位置：selftest.py / scraper/parsers/taoguba.py
必现
TRADES_FOUND: 1（期望 2）… price=None qty=None
assert t1.quantity == 1000 and t1.price == 12.30 → AssertionError（第 40 行）
根因：解析器
_extract_trades()
第 228-229 行构造交易时写死
"price": None, "quantity": None
（设计上不抽取量价），而 selftest.py 仍断言能抽出价格 12.30、数量 1000、两条交易——测试用例没有跟随解析器实现更新。
影响
：自测长期处于红态，改解析器无任何保护。
P0
实盘交易成交价 / 数量全库为空
位置：taoguba.py 交易构造 → trades 表 → 前端明细弹层
全量 268/268
trades 表：268 行中 price NULL=268、quantity NULL=268、buy_price NULL=268
界面「实盘交易 · 明细」：成交价列、数量列全部显示 "—"
根因同上：淘股吧解析器只识别"动作 + 股票"，不抽取"买入 X 1000股，价格 12.30"中的量价；其他站点（东财/新浪/雪球）同样未抽。
影响
：交易明细缺最核心的价量信息，只能看到方向与标的，无法做盈亏/仓位复盘。
P1
单实例互斥失效：1 个 server + 2 个 desktop_app 进程并存
位置：viewer/desktop_app.py _acquire_single_instance()
本次实测环境
进程列表（13:07-13:08 启动）：
33384 python server.py
10152 python desktop_app.py（13:08:12）
40068 python desktop_app.py（13:08:14）
当日 desktop 日志出现 5 次 "scheduler started"，多进程向同一日志文件交错写入
desktop_app 用
CreateMutexW + GetLastError()==183
判断是否已有实例，但 ctypes 调用未使用
use_last_error=True
，Windows 上 LastError 检查不可靠；两个桌面窗口都认为自己拿到了互斥体。
影响
：可能双调度器重复抓取、前端请求随机命中不同后端、meta/日志状态互相覆盖（是"刷新状态已超时"等异常显示的可疑上游原因之一）。
P1
顶栏"刷新状态：已超时"与实际调度状态不一致
位置：server.py api_refresh_status / 前端顶栏
复现
refresh_status.__all__.last_ok_at = 13:15:13，但各来源（东财/新浪/淘股吧）last_ok_at 已更新到 13:48:54-55；scheduler_state.run_count 138→141 持续增长；界面顶栏却显示"已超时（36 分钟前）"
根因：
last_ok_at
（来源键
__all__
）只在整轮抓取全部成功时更新（任一来源失败即记 error 且不动 last_ok_at），而调度每轮抓取结果未回写该记录。
影响
：用户看到"已超时"误以为数据抓取停了，实际调度一直在跑。
P2
watchdesk 后台任务"假活"：声称运行但 4 天未扫描
位置：watchdesk 状态机 / meta.watchdesk_state
meta.watchdesk_state = {"running": true, "started_at": "2026-10-01 21:41:18", "last_scan_at": "2026-10-01 21:26:17"}
状态标记为运行中，但最近一次扫描停在 10-01（4 天前）。线程可能已死但状态无心跳、无超时自愈。
影响
：用户以为盯盘台在跑，实际数据不再更新。
P2
配置缺失导致两项功能未启用（日志大量 WARNING）
位置：config/sites.yaml → viewer/ingest.py
日志高频出现：
WARNING 未配置 player_page_tpl，跳过持仓采集
WARNING 未配置 players 目标页，跳过选手筛选
影响
：①"持仓记录"271 条依赖选手持仓采集，但该采集从未配置启用（只有行为反推的持仓）；②选手池筛选主要靠行为反推，榜单来源缺失。功能存在但实际处于"半启用"状态，且界面上无任何提示。
P2
雪球代理 127.0.0.1:53269 不可达，降级告警刷屏
位置：scraper/browser_fetch.py
13:10:33 – 13:13:24 约 20 条：
WARNING 雪球代理不可达 127.0.0.1:53269，降级为直连（浏览器不走代理）
配置文件里写了雪球代理端口，但对应代理进程没起，每次抓取都探测失败并降级。
影响
：日志噪音大，掩盖真实错误；直连雪球可能影响稳定性（当前 13:13:25 雪球抓取成功）。
P2
东财 push2 接口不可达（外部依赖风险，软件已有降级）
位置：quote / moneyflow / board_flow 外部源
非代码缺陷
/api/quote → 腾讯行情兜底（东财 push2 不可用）
/api/moneyflow_rank → {"ok": false, "reason": "东财 push2 接口不可达…"}
/api/moneyflow_board → 失败，提示迁移到板块资金流标签页
前端资金流向页展示完整失败原因 + 负缓存倒计时 + "强制重试"按钮（容错设计良好）
影响
：主力净流入榜当前无数据；板块资金流已自动切换新浪源正常展示。属于外部源被限流/屏蔽，建议监控。
P2
"入手概率"新板块首次进入为空态，需手动触发全市场归档
位置：/api/rate/timeline（2026-10-05 新增）
首次请求：{"ok": true, "has_snap": false, "reason": "还没有任何归档（先跑一次「全市场…"}}
实测：首次访问后约 10 分钟内 rate_snap 自动写入 1000+ 行（snap_date=2026-10-05）
功能采用"惰性归档"：首次进入才触发全市场扫描。前端未给出"正在生成（约 1 分钟）"的明确进度态，用户第一眼看到的是空面板，易误判为坏了。
P2
每日预测数据停在 09-30，页面无过期提示
位置：prediction / 每日预测页签
/api/prediction/today → run_date "2026-09-30"（国庆假期前），今日 10-05 页面仍正常渲染该期预测，无"数据截至 09-30"角标
国庆休市期间无新预测可以理解，但页面应明确标注数据日期与"节假日不生成"状态，避免用户拿 5 天前的推荐当新鲜结论。
P3
大接口 payload：K 线 870KB、人物榜 909KB
位置：/api/kline /api/persons
/api/kline?symbol=600519 → 870,009 字节（6015 根日 K）
/api/persons → 909,017 字节（2131 人全量）
首屏/弹层一次性拉全量，弱网或大列表下体验差；K 线全历史对 90% 场景多余。
P3
慢接口：screener_decline 7.1 秒、auction 0.9 秒
位置：/api/screener_decline /api/auction
/api/screener_decline?days=20&limit=5 → 7137ms（全市场 441 只扫描）
/api/auction → 935ms（5533 只聚合）
前者无缓存，每次请求重扫全市场；后者在可接受边缘。
P3
工程目录卫生：备份与中间产物堆积
位置：项目根目录 / viewer/
根目录：约 40 个 *.bak-* 备份、约 120 张测试截图/JSON 中间文件；
viewer/：app.db（58MB）+ 5 份 db 备份、app_isobf/app_isovd 等隔离测试库残留（-shm/-wal 文件 10+）
static/：app.js（698KB）+ 10 个 .bak 版本
备份机制本身是好事（auto_update 自动留档），但长期不归档会让目录越来越难检索，也存在误用旧备份恢复的风险。
P3
server.log 无日期、多进程混写；board_flow 日期口径待确认
位置：viewer/server.log / board_flow_dates
viewer/server.log 无时间戳字段、无编码声明，日志被多次启动的 server 段连续追加；
/api/board_flow_dates 最新交易日 2026-09-30，而 /api/screener 的 trade_date 为 2026-10-02，两个"最近交易日"口径不一致（可能因行情时间戳来源不同）
日志无时间戳导致多实例并发时无法回溯归因；日期口径不一致会让用户在国庆后首日看到"最新数据"分歧。
三、优化建议（按软件现状，可直接落地）
1. 修单实例互斥，从"锁"升级为"端口持有者检测"
落点：viewer/desktop_app.py
CreateMutexW 改用
ctypes.WinDLL("kernel32", use_last_error=True)
+
ctypes.get_last_error()
判断 183；同时保留端口探测，并在
/api/version
返回服务进程 pid，前端启动时若发现已有实例，用
webview
最小化窗口提示或直接复用已有窗口，而不是再开一个。
2. 补齐交易量价链路（价值最高的优化）
落点：scraper/parsers/taoguba.py + 回填脚本 + 前端
① 在
_extract_trades()
的
add()
里增加量价抽取：在动作词邻域 60 字内匹配
(\d+(?:\.\d+)?)\s*(?:股|手|万)
与
价格?[:：]?\s*\d+\.\d+
，命中即回填 price/quantity；② 写一个一次性回填脚本，用 raw_text 字段对历史 268 条重抽一遍（数据已在库里，纯本地 SQL 遍历）；③ 前端把空价量从"—"改为"帖中未披露"，避免误导。此改动同时可让 selftest 断言恢复成立。
3. 刷新状态与调度状态统一口径
落点：server.py api_refresh_status / 前端 renderRefreshBar()
调度每轮抓取完成后同样调用
record_refresh("__all__", …)
（按"至少一个来源成功"记 ok 而非"全部成功"），或前端改以"最近来源成功时间"展示；顶栏超时阈值按调度间隔（300s）而非固定 600s 计算，消除"已超时"误报。
4. 配置项补齐 + 界面显性化"未启用"状态
落点：config/sites.yaml + viewer/ingest.py + 前端
在 sites.yaml 中补
player_page_tpl
与
players
目标页的模板注释和示例（淘股吧可用 /talk/talkSeq 列表页）；在"持仓记录/选手池"面板角标显示"该源未配置，仅行为反推"，让功能半启用状态可见、可引导补齐。
5. 雪球代理不可达自动停用 + 告警降噪
落点：scraper/browser_fetch.py
代理连续 2 次探测失败后自动置为"停用"并写入内存状态，之后每轮只输出 1 条合并告警，改为 10 分钟一次的指数退避重试，直到用户配置里显式改回；避免每轮 5-6 条刷屏淹没真实错误。
6. 后台任务心跳与自愈
落点：watchdesk 状态机 / meta.watchdesk_state
每次扫描完成更新时间戳；调度器每轮检查 watchdesk，若 last_scan_at 距今超过 30 分钟则标记 running=false 并自动重启扫描线程；前端状态牌同步显示"已停止（xx 未扫描）"。
7. 前端空态与过期引导
落点：/api/rate/timeline、每日预测页
入手概率：has_snap=false 时前端展示"正在生成全市场归档（约 1 分钟），可稍后刷新"并自动轮询 3 次；每日预测：run_date 早于最近交易日时在标题加"数据截至 09-30"角标；两个接口都已在 reason 字段给了文案，前端只需把 reason 渲染出来。
8. 大接口分页 / 降采样 / 缓存
落点：/api/kline /api/persons /api/screener_decline
kline 增加
limit
/
step
参数（默认最近 250 根，前端"全量"再拉全）；persons 支持
limit/offset
分页（当前 909KB 一次返回）；screener_decline 对结果按 trade_date 做 1 小时内存缓存。改动都在 server.py 的 api_ 函数内，不涉及数据层。
9. 工程卫生：一次归档 + 自测修复
落点：根目录 / tests/
把约 40 个 *.bak-* 与 120 张中间截图/JSON 移入
backups/archive-20261005/
（只移不删，保留可回滚）；删除隔离测试库残留（app_isobf 等 -shm/-wal，确认无进程占用后）；修复 selftest.py 断言（对齐解析器现状，量价字段按"可空"断言，同时为建议 2 的量价解析写新用例），并把 selftest.py 纳入每次改解析器的必跑清单。
10. 日志治理：统一格式与轮转
落点：viewer/server.py 日志初始化
server 的日志 handler 与 desktop_app 保持一致（UTF-8 + 时间戳 + RotatingFileHandler 5MB×5），并写入同一
viewer/logs/server-YYYYMMDD.log
；这样多实例并发时至少能按时间线合并排查。
