# UI 端到端门禁（tests/e2e/）

单一入口：`tests/e2e/run.cjs`。取代已废弃的 `tests/ui_full_regression.js`。

```
node tests/e2e/run.cjs              # 全量：53 tab × 3 视口 + 单位 + 自选增删 + 6 种空/错态 + 抽屉四入口 + 长文本（上限 6 分钟）
node tests/e2e/run.cjs --quick      # 快速门禁：3 个 tab + 单位 + 健康 + 长文本 + 三视口溢出（实测 ~19s）
node tests/e2e/run.cjs --json       # 机读：stdout 只有一个 JSON 对象
node tests/e2e/run.cjs --no-write   # 只读环境：跳过自选增删
node tests/e2e/run.cjs --port 8765  # 指定端口（默认 8765）
```

**退出码：`0` 全过 / `1` 有用例失败 / `2` 环境不可用（连不上服务、浏览器起不来、或中途掉线导致有用例没跑成）。**
"环境坏了"和"产品坏了"必须分得开 —— 混在一起的后果是红了没人看。

三处刻意把"环境"从"产品"里摘出来的设计：

1. **服务和浏览器都起不来 → EXIT=2**，并且不写 `EXIT=1`（不是产品缺陷，不该触发修 bug 的流程）。
2. **服务在跑的过程中被重启**（别人重启 viewer）→ 报告里 `env.restarted_mid_run` 记录
   `pid 前→后`，并把「接口无失败」从 fail 降级为 warn，摘要里明写
   *"期间的接口连接失败属重启窗口，请复跑定性"*。实测踩过：跑第 3 分钟时 pid 5852 → 17064，
   151 条 `ERR_CONNECTION_REFUSED`、viewport 阶段从 120s 涨到 163s —— 不区分就会被记成"接口全挂"。
3. **两个时间闸**：`deadline`（1.0× 预算）只用于"如实报告是否达标"；
   `hardDeadline`（1.5× 预算）才真正中止后续阶段。否则会出现"预算到点直接 break，
   剩下两个视口一个都没测"，把"被预算掐断"报成产品缺陷。
   服务刚重启（`started_at` 距今 < 3 分钟，缓存全冷）时超预算只记 warn 并注明冷启动。

报告落在 `tests/e2e/_report.json`（已 gitignore），含每条断言的 `why`、分阶段耗时、
接口失败明细、`needs_testid` / `blocked` / `not_covered` 清单。

### 摘要算术必须自洽（加不起来 = 不可信）

摘要打印成一句可以手算核对的等式：

```
断言 111：通过 107 · 失败 0 · 告警 4   （107+0+4=111 ✓）
      告警分层：断言级 3 · 阶段级 1（阶段级=环境/预算状态：服务与磁盘代码一致）
```

三个桶是**互斥且穷尽**的：

| 桶 | 判据 |
|---|---|
| 通过 | `ok === true`（不论 level —— 它真的过了） |
| 失败 | `ok === false && level === "fail"`（计入退出码） |
| 告警 | `ok === false && level === "warn"`（不计入退出码） |
| （其它） | `ok === false && level` 是别的 —— 不该出现，出现就是代码写错了 |

之前这里有过一个**真实的算术 bug**：`passed` 用 `r.ok` 过滤、`warned` 用 `r.level === "warn"` 过滤，
两条口径不是一个划分，于是"通过了但被标成 warn"的记录会**同时进两个桶**，出现过 `105 + 6 > 109`。
加不起来的摘要比红一条更坏：它让人没法核对，而这个仓库最贵的教训就是"数字看起来都对"。

现在**先自检再打印**：`通过 + 失败 + 告警 (+ 其它) === 总数` 不成立时，
会额外记一条 `FAIL [harness] 摘要算术自洽`，退出码 1，并把口径异常的条目打进明细。
告警再分两层（断言级 / 阶段级），两层都在分母里，所以加起来始终等于总数。

## 一、为什么是「动态枚举」而不是写死 tab 列表

旧版 `tests/ui_full_regression.js` 把 10 个 tab 名和 `.tab[data-tab="..."]` 写死。
导航改版后（`viewer/static/app.js` 的 `paintSubnav`）DOM 变成两级：

```
#sidenav .nav-item[data-cat]          一级分类
#subnav  .sub-tab[data-tab]           当前分类下的子板块（只渲染当前分类）
#p-<tab>                              每个 tab 的面板容器（懒创建）
```

于是 `page.click('.tab[data-tab="summary"]')` 直接抛 `No node found for selector`，
**一份回归在第一个 tab 就死掉，一条断言都没跑到** —— 这就是测评里"自动化测试与真实 UI 已漂移"。

新版做法：

1. 读 `#sidenav .nav-item[data-cat]` 得到分类全集（本次实测 7 个）；
2. 逐个点开分类（`ensureCat`），等二级导航稳定后读 `#subnav .sub-tab[data-tab]`；
3. 把 `{cat, tab, label, href}` 摊平成一张表（本次实测 **53 个 tab**，旧文档写的 43 个已过时）；
4. 遍历这张表逐个点。

**代码里不出现任何具体 tab 名。** 连 `--quick` 的"3 个 tab"也是取枚举顺序的前 3 个
（第一个恰好是「今日决策」，所以"含 today"这条自然满足，而不用在代码里写 `"today"`）。

多写一句为什么必须是动态的：2026-11-01 凌晨这门禁写就的同时，另一位同事正在重排导航
（`overview/money/info/opinion/watch/research/learn` → `today/mine/market/stock/strategy/system`）。
同一份门禁代码，半小时内先后跑出 **43 / 53 / 58** 三种 tab 数，而这三个数字**含义完全不同**，
不能互相替代，也不能只报一个：

| 数字 | 含义 | 什么时候出现 |
|---|---|---|
| **43** | **导航重排进行中的中间态** —— 一级分类已经换成新名字，但部分分类的子板块还没迁完 | 重排那半小时里，且只在"页面已被新 JS 渲染、数据侧还没跟上"时 |
| **58** | **含重复的原始条数** —— 横条里 5 个子板块被渲染了两遍（`paintSubnav` 的缺陷，见第七节） | app.js sha1 = `a19ca3f6` / `06feaf78` 这两版 |
| **53** | **去重后的真实入口数** —— 也是"用户真正能点到几个"的口径 | app.js 修掉重复渲染之后（sha1 `6ca3120c`） |

写死名单的测试在这半小时里会连续红三次（且每次都指向不同的"错"），而动态枚举只是如实地把变化报出来。
报告里因此额外记录 `app.js / app.css / index.html` 的 `sha1 + size + mtime`
（`env.app_js`），用于把"结果"和"当时那一版前端代码"绑在一起；没有这个，
两次跑出不同结论时没人能证明是文件变了而不是测试不稳。

### 三个必须知道的坑（都踩过了，别重犯）

- **子板块只在"它所属分类"被选中时存在于 DOM 里。** 遍历到第 20 个 tab 时，二级导航还停在
  上一个分类，直接按 `data-tab` 查元素会得到"元素不存在"。所以每次点击前要先 `ensureCat(cat)`。
  第一版门禁就是因为这个把 3 个 tab 全判失败。
- **等就绪不能只看数量。** 切分类的瞬间列表还是上一个分类的（数量看着稳定），
  必须同时校验"首个 tab 的 `href` 已属于目标分类"**并且**"没有在飞的 `/api/` 请求"才算稳定。
  少这一条会出现"同一份代码一次枚举到 53 个 tab、另一次只有 43 个"（差的是异步到达的动态轨道），
  于是"43/43 全绿"和"53/53 全绿"是两个含义完全不同的绿灯。门禁自带
  `[nav] 导航枚举可复现` 断言专门抓这件事。
- **横条里有「折叠区」，默认收起。** 2026-11-01 起 `#subnav` 把一部分子板块收进
  `<details class="sub-fold"><summary>研究工具（N）</summary>`。收起时里面的
  `<a data-tab>` **仍在 DOM 里**（所以枚举得到、`textContent` 读得到标签），但**不可见也不可点**：
  真实鼠标点击会落到横条或下方面板上，表现为"点了没反应、hash 不变"。
  实测 53 个 tab 里有 **33 个在折叠区**，不展开就跑会得到 `20/53 通过` 的假红。
  处理方式（不写死 class）：每次点击前找 `#subnav details:not([open])`，
  优先真实点击它的 `<summary>`，点不到才退回改 `open` 属性。
  注意横条每次重绘都会重建 `<details>`，所以**展开必须在每次点击之前做**，不能只在切分类时做一次。
  顺带一个教训：`<details>` 未展开时子项的 `innerText` 是空字符串，
  读标签必须用 `textContent`，否则报告里全是 `[today/executability] ——`（标签为空，查不动）。

## 二、每个 tab 检查什么（四件事 + 两项软指标）

| # | 断言 | 判据 | 为什么 |
|---|---|---|---|
| ① | 深链接可用 | `location.hash === "#<cat>/<tab>"` | hash 是分享/回退/自动化的唯一入口，坏了等于不能深链 |
| ② | 无 JS 异常 | 点击窗口内无新增 `pageerror` / `console.error` | JS 崩了通常紧接着整块面板不工作 |
| ③ | 无接口失败 | `/api/` 前缀的 4xx/5xx 增量 = 0（`304` 不计） | 接口烂了用户看到的就是空面板 |
| ④ | 无脏字符 | `document.body.innerText` 里无 `undefined` / `NaN` / `Invalid Date` / `[object Object]`（`null` 见下） | 把内部值直接糊到用户脸上是最典型的前端事故 |

脏字符的两个防假阳性处理：

- 扫描前剔除 `pre / code / script / style / textarea` 的文本 —— 代码示例里出现 `null` 是合法的；
- 用**词边界**正则（`\bundefined\b`），不会把 `nullable` / `nulls` 这类合法英文单词误判。

`null` 单列 **warn** 而不是 fail：中文 UI 理论上不该出现独立 `null`，但它偶尔来自
合法示例载荷；把它当硬失败会让门禁常红，常红的门禁等于没有门禁。出现时会连同上下文一起打印。

软指标（记录但不红）：

- **面板是否有内容**：`#p-<tab>` 的文本长度。空的可能是"当天确实没数据"，直接判 fail 会假红；
  报告里 `nav.empty_panels` 会列出来供人判断。
  **测的时候必须 iframe 感知**：`#p-fundmasters` 整块是一个 `<iframe src="/static/fund_masters/index.html">`，
  而 `innerText` / `textContent` **不跨子文档**，父页面里它永远是 0 字
  （实测：父文档 0 字 / 子文档 127 字 / `index.json` 138KB 在盘）。早期口径只读父文档，
  于是这个面板被稳定误报成"空面板"——**那不是产品坏了，是我的尺子量错了地方**。
  现在的口径写在 `panelTextInPage()`：**三个口径全空才算空面板** —
  ① 父文档 `innerText`；② 有 `data-panel-frame` 时读 `iframe.contentDocument.body.innerText`；
  ③ 就绪标记 `data-ready` + iframe 的 `data-loaded`。
  任一非空就不算空（只看 ③ 会漏掉"文本有内容但没打标记"的真正常面板；只看 ①② 会漏掉 iframe）。
  三个口径的实测值会写进 `report.nav.tabs[].result`（`panel_own_len / panel_sub_len / panel_ready / panel_frame_loaded`），
  空面板还会在 `nav.empty_detail` 里留一份，方便复核"到底哪一档为空"。
  这条不写死 fundmasters —— 任何面板套 iframe 都走同一条路。
- **点击是否被遮挡**：点击前做 `elementFromPoint` 命中测试。被盖住时真实鼠标点不到，
  但 `element.click()` 仍可能"成功"——不单独暴露就会变成"断言莫名失败"。

## 三、必测清单与判据

### 1) 启动 / 健康
- `GET /api/version` 的 `build_id` 存在且长度 ≥ 6；
- `GET /api/health` 的 `leases.items` 是**数组**（断言结构而不是文案：结构变了「系统健康」页会静默空白）。

### 2) 个股详情 + K 线 + 单位一致性（P0-1 端到端守门）

事故原型：同一只 600519，抽屉「行情区」写 `5.99 万手`（对），「K 线区」写 `599.27 万手`（错 100 倍）。

断法：

1. 走**真实用户路径**打开抽屉：`Ctrl+K` → 输入 `600519` → `Enter`（命令面板，`#cmdInput`）；
   命令面板不可用时才兜底 `window.openStock()`，并在 `needs_testid` 里记一笔（不静默降级）。
2. 分别在 `#stkQuote`（行情区）与 `#klineSnap`（K 线区）里找汉字「成交量」那一格，读文本。
3. 断言三者：
   - 两处**单位标注必须不同**（一个「手」一个「股」）；
   - `手 × 100` 与 `股` 的相对误差 **< 1%**；
   - 任一处显示 `—（单位未标注）` 或读不到 → **FAIL**（600519 日线一定有量）。

不写死数值：换数据源/换日期数值就变，写死等于埋一颗定时红。

### 3) 自选增删（可回收的临时数据）

- 先读 `/api/watch_list`，从候选表里挑一个**池中没有**的标的；
- 动态发现「关注池」面板：哪个 tab 的面板里有 `#wtAdd` 就是它（不写死 tab 名）；
- 点 `#wtAdd` → 填 `#wtF-symbol` → 点 `#wtF-save`；
- 断言行出现（**给到 45s**，见下）→ 从行上取 `data-wt-del` 的 id → 真实点击 → 接受 `confirm` → 断言行消失；
- `finally` 里兜底清理 + 再查一次 `/api/watch_list` 复核确实不在池中（自证清理干净）。

三个踩过的坑，都会让"清理"变成假的：

1. **写接口要 Cookie，而 Cookie 只在发 HTML 页面时给。** `server.py` 第 13047 行起，只要设了
   `VIEWER_API_TOKEN`（本机由 `config/viewer_token.txt` 提供），所有非 GET 请求必须带
   `local_token` Cookie，否则 401 `token required`；而这个 Cookie 是**发页面**时
   （第 13178 行）下发的，JSON 接口不下发。
   早期版本直接裸 POST 清理 → 401 → "清理"静默失败，**真的把 `000001` 留在了用户的池子里**
   （已手工删掉并复核 34 条 / 无残留）。
   现在 `httpJson` 在第一次写请求前先 `GET /` 接住 Cookie，并逐条检查删除响应、最后用接口复核。
2. **"行没出现"和"列表刷得慢"是两件事。** `loadWatch()` 会重拉 `/api/watch_list`
   （带行情 + 策略命中，池子 30+ 条时很慢），18s 不够、45s 够。
   所以超时后先查接口：接口也没有 = 写入链路断了；接口有但 DOM 没有 = 刷新太慢。
   两种原因分开写进明细，下一个人不用重跑一遍才知道该找谁修。
3. **上游没出现行时，删除环节不能"就跳过"。** 跳过会让"删除链路已断"显示成绿色。
   这里照样记一条 fail，明细写清"上游：加入后 45s 内列表没出现该行，UI 删除链路无法验证（兜底用接口清理）"。

`--no-write` 跳过；**`--quick` 也跳过**（写链路要等页面拉行情，塞进 quick 会把 19s 拖成 50s+）。
`quick` 输出里会明确写 `[watch] 跳过（quick）`，**不要**把"quick 绿了"理解成写链路没问题。

### 4) 全量导航无 404/5xx
遍历全部 tab，汇总 `/api/` 前缀的 4xx/5xx。过滤两类噪音：

- `304`（走缓存，不是失败）；
- `net::ERR_ABORTED`（前端切 tab 会主动 abort 上一只票的请求，属正常设计）。

### 5) 空态 / 错误态（6 种载荷变体）
`page.setRequestInterception` 在**独立测试页**里构造，不动服务端也不污染主页面。
为什么必须做：本仓库反复踩的坑就是"接口超时/返回空/返回 500 时前端是不是白板"——
数据正常到达的路径永远测不出这个问题。

| 变体 | 构造 | 必须出现错误/重试文案 |
|---|---|---|
| 500 + JSON `{error}` | `respond(500, application/json)` | ✅ |
| 500 + HTML 错误页 | `respond(500, text/html)` | ✅ |
| 网络层失败（等价超时/断网） | `req.abort("timedout")` | ✅ |
| 200 + `{}`（字段全缺） | `respond(200, "{}")` | ⬜ |
| 200 + `[]`（类型不符） | `respond(200, "[]")` | ⬜ |
| 200 + `null` | `respond(200, "null")` | ⬜ |

每条断言五件事：正文非白屏（字数 > 0）、**抽查前 3 个 tab 的面板都不是空 div**、
出现中文人话（`暂无|无数据|失败|错误|重试|加载…`）、无脏字符、无 `pageerror`。

> 为什么后三种不要求"错误文案"：实测前端对"字段缺失"的设计是**降级显示**
> （`部分数据加载失败：【汇总接口】响应中缺少 counts 字段，计数已降级为空`），
> 硬要求错误条会误伤一个合理实现。

> 也**不**断言"面板里必须换成错误文案"：实测 500 时的设计是「底部错误条 + 面板保持加载中并自动重试」
> （`服务端 500，3 秒后自动重试（第 1/3 次）`），那是合理 UX。

### 6) 三档视口 1024 / 1440 / 1920
- **无横向溢出**：`document.documentElement.scrollWidth <= innerWidth + 1`（逐 tab 测）；
- **可点元素不被裁**：面板内 `button / a[href] / input / select` 的 `getBoundingClientRect`
  不得整体落在视口外；在可横向滚动容器（`overflow-x: auto|scroll`）里的不算；
- **顶栏按钮 `elementFromPoint` 可命中**：按钮清单**动态枚举**（`#btnDemo` 这类按钮带 `hidden`，
  写死 id 就会假红），逐个用 `elementFromPoint(中心点)` 验证命中的是它自己或其后代。

效率取舍：不是"每个视口把 53 个 tab 点一遍"（3×53 ≈ 130s），而是「每个 tab 点一次、就地切三档量三次」——
覆盖面完全一样，切换次数从 159 降到 53（实测 70s）。

**这个阶段一条都不许"静默消失"**：跑完若 `report.viewports` 为空，会补一条
`FAIL 三档视口检查已执行`。上一轮就是因为常量 `VPS` 被编辑挤到使用点之后（`ReferenceError`），
整个视口阶段连带 9 条断言凭空消失，而摘要里只多了一条 runner 失败。

### 7) 详情抽屉的四条关闭入口
打开走真实路径：动态找含 `#wtAdd` 的面板 → 点它的 tab 成 active → 点行（`[data-wt-open]`）。
然后**每条入口都"重新打开 → 关闭 → 断言已关"**：

| 入口 | 定位 | 谁在用 |
|---|---|---|
| ✕ 关闭按钮 | `#btnClose` | 鼠标党最短路径 |
| 底部按钮 | `#btnClose2` | 长内容滚到末尾时的顺手出口 |
| `Esc` | `keydown` | 纯键盘用户唯一入口 |
| 点面板外 | document `pointerdown`（app.js ~7533 行） | 习惯点空白处的人 |

第四条有防假绿处理：点击前先算抽屉矩形，确认落点 `x/y` 在矩形外、且
`elementFromPoint` 命中的不是 `#drawer` 内的元素，否则这一条会变成"其实点在抽屉上"。

**"再点同一行"不是关闭入口**：实测 net 效果是**保持打开并重新载入**
（`pointerdown` 先关、随后的 `click` 又让行的 `onclick` 重新打开）。
所以这里断言的是"仍然开着且标题有内容"——把它当关闭入口写会得到一条永远红的假断言。
顺带守一下抽屉正文（`#drawerBody`）无 `undefined/NaN/Invalid Date`：抽屉是最容易把裸字段糊上去的地方。

### 8) 长文本压力（超长中文 / 超长无空格 ASCII）
注入到**当前面板里文本最长的前 5 个叶子元素**（也就是长文本真实落点），而不是随便挑几个 div ——
否则测的是装饰元素，等于没测。注入前存 `textContent`，测完立刻还原（并断言"还原后页宽回到视口内"，
否则会污染后续的视口阶段）。

两档严重度不同：

| 档 | 内容 | 判据 | 现在的结果 |
|---|---|---|---|
| 超长中文 | 38 字 × 5 段（可换行的真实输入：帖子标题、公司全称、备注） | 硬失败 | 3/3 tab **通过**（`scrollWidth` 不变） |
| 超长无空格 ASCII | `"A" × 300`（极限输入：长 URL 粘进备注） | warn | 3/3 tab **都溢出**（1440 → 2381~3892px） |

ASCII 那档记 warn 而不是硬失败，理由写在这里免得下一个人以为是漏了：
它**是真问题**（这些文本节点没有 `word-break`），但属"全站 CSS 补齐"的活、范围远大于本门禁；
把它设成硬失败会让门禁常红，而常红的门禁等于没有门禁。要升级为硬失败，改一个词即可
（`warn(...)` → `rec(..., "fail")`）。

### 9) 深链接冷启动（"点出来的绿" ≠ "直接打开就绿"）

这是本轮补的第二条，也是**点击型回归的先天盲区**。

2026-11-01 实测到一个真 bug：`app.js` 的启动段原来在**本文件被解析时**就执行，
而 `douyin_corpus.js / funnel.js / industry_leaders.js / bottleneck.js / screener_extra.js`
都排在 `app.js` **之后**。于是首屏直接落在依赖这些脚本的面板上时，`window.DOUYIN` 还是 `undefined`，
`if (tab === "dy_reso" && window.DOUYIN)` 这类守卫**静默跳过**，面板永远停在「正在加载数据…」；
点别的 tab 再点回来就正常（那时脚本都到了）。
**上面的导航遍历全部是"点"，天然绕过它** —— 而分享链接、刷新、收藏夹全是冷启动路径。

做法：

- 取样 = 枚举结果的**第一个 / 中间 / 最后一个**（不写死 tab 名，也不挑"看起来容易坏"的）；
- 每个样本 `goto(PAGE_URL + "#cat/tab")`，轮询等就绪（`data-ready` / 有内容 / 20s 上限）；
- 三条判据：① 面板有内容（iframe 感知）；② **不仍停在「正在加载数据」** ——
  "有字"但只有一句加载占位等于没渲；③ 冷启动期间无 `pageerror`。

> 为什么用位置取样而不是"挑几个可疑的"：写死"可疑名单"等于只守这一次的 bug；
> 按位置取样能在**任何** tab 上发现同一类时序问题，且和 tab 改名解耦。

### 10) 环境中途坏掉：记"未执行"，不记"通过"

跑全量时真遇到过服务被同事重启。如果恰好发生在开新页面那一刻，浏览器拿到的是**错误页**
（`ERR_CONNECTION_REFUSED`），此时"面板有没有内容 / 有没有错误文案"的断言全都不成立。

处理方式（这也是退出码 2 的一个新来源）：

- 开跑前先 `GET /api/version` 探活；不通 → 该例登记 `env_skip`，**不记 PASS**；
- 文档层 goto 失败（`ERR_CONNECTION_REFUSED / EMPTY_RESPONSE / RESET / CLOSED`）→ 同上；
- 摘要里单列 `[env] 中途不可用 N 处（未执行，不是通过也不是产品缺陷）`；
- **全跑完若有 `env_skip` 且无真实失败 → 退出码 2，而不是 0**。
  不给自己发"全过"的假证书，也不把环境问题写成产品缺陷。

## 四、`stale_build` —— 为什么"没重启"不能被误判成"改坏了"

服务跑的是启动那一刻的代码快照。`/api/version` 的 `build_id` 是**进程启动时的代码指纹**，
而磁盘指纹随时会变。本门禁在 Node 里按 `viewer/build_id.py::of_disk` 的算法**重算一遍磁盘指纹**
（对 `KEY_FILES` 逐文件算内容 sha1，拼成 `rel|size|sha1;` 再取 sha1 前 12 位，与 Python 逐字节同值），然后：

> 2026-11-01 改口径：原来是 `(mtime, size)`。两个方向都出过事 —— **mtime 只到秒**，同一秒内把一处
> 改成**等长**字符串（sed / 批量替换）指纹一点不变，于是"跑着旧代码"被判定成"代码没换"（漏报，
> 致命）；反过来 `touch` 一下内容没变指纹就变，白喊人重启（误报，会让人习惯性忽略这个告警）。
> 现在只认内容：改一个字节就变，没改就不变。

- 不一致 → `env.stale_build = true`，`[health]` 记一条 **warn**（不红），并在报告与摘要里同时打印
  服务 `build_id` 与磁盘 `build_id`；
- 此时若「单位一致性」FAIL，报告里会追加一句：*这条很可能是「没重启」而不是「改坏了」*。

门禁**不会**自己重启服务（多人共用 8765），也不会为了让测试变绿去改断言。

### 首次访问的 `#firstRunMask`（一个容易把门禁带偏的东西）

所以门禁在 `goto` 之后先做一件事：真实点击 `#frDone` 关掉引导，并单独断言"它确实被点掉了
且挡板不再拦截"。这不是 bug（本来就该由用户点掉），但门禁不知道这件事就会把"点不动"误报成产品缺陷。

## 七、本轮实测发现的真实缺陷（不是测试问题）

### 缺陷 1：二级横条里 5 个子板块被渲染两遍 —— **已修复（app.js sha1 `6ca3120c` 起）**

现象（`node tests/e2e/run.cjs` 的 `tab 标识不重复` 断言）：


DOM 结构（当时实测）：两份都在「研究工具（N）」折叠区里，一份是
`<a class="sub-tab sub-child">`（挂在 main 的 `sub-cluster` 里），另一份是
`<a class="sub-tab">`（挂在 `sub-fold-body` 里）。

根因在 `viewer/static/app.js` 的 `paintSubnav → renderList()`：

- `if (i.child && !inFold) continue;`（约 14127 行）只在**平铺区**跳过子项；
- 折叠区里，lookahead 循环（约 14131–14138 行）已经把 lead 后面同 `mg` 的子项渲染进
  `sub-cluster`；
- 外层循环随后又遍历到同一个子项，因为 `inFold` 为真而没有 `continue`，
  落到 `else` 分支（约 14141 行）**再渲染一次**。

修法（前端已采用）：内层循环把已渲染的子项记进集合，外层据此 `continue`
（`emitted` 集合）。

**复跑验证**：`重复 0 个 / 原始 53 个`，并且 `[nav] 53/53 可打开`、
`原始数` 从 58 回落到 53 —— 三个数字的口径见第一节的表格。
这条断言**保留**，因为它守的是"同一横条里不能有两个一模一样的入口"，
不是为了记录某一次的具体缺陷。

### 观察 2：`strategy/dy_reso` 把字面量 `null` 渲染给用户 —— **已修复**

```
[warn] [strategy/dy_reso] 出现独立 null 文本 —— … 合成-/null 豆包16·共振博主0·信号0 …
```

根因：后端 `card.get(code, ("-", None))` 用 `"-"` 当哨兵 + 前端 `String(x.card_score)` 直接拼，
拼出 `合成-/null`。现在前端三态：`合成层未覆盖`（该票不在卡池）/ `合成A/—`（卡在、档位没算出来）/ `—`。
实测 40 行 **0 个 null**，1 行「合成层未覆盖」。顺带去掉了「共振博主0」——
该维度 2026-10-30 下线后后端不再回吐 `overlap_n`，渲染成 0 是把"没有这个维度"伪装成"0 个博主"。

> 这类**假零**值得单独记一笔：它不是显示瑕疵，而是"数据没有了"和"结果就是 0"被混成同一个字。
> 门禁这边对应的是脏字符断言（`undefined/NaN/null`），但它抓不到"0 是假的"——
> 所以只能靠人看一眼语义。以后若再出现类似字段下线，建议同时删掉渲染，而不是让它显示 0。

### 观察 3：`strategy/fundmasters` 面板"为空" —— **不是缺陷，是我的度量口径无效**

`innerText` / `textContent` 不跨子文档，而这一屏整块是 `<iframe src="/static/fund_masters/index.html">`，
所以父文档里永远是 0 字。实测：父文档 0 字 / 子文档 127 字 / `index.json` 138KB 在盘上。
现在两边都补上了：前端给 iframe 挂 `data-panel-frame` + `data-loaded`（并加了"真失败就画显性空态，
不留白板"的兜底），门禁侧改成 iframe 感知的 `panelTextInPage()`，`nav.empty_panels` 实测为 **`[]`**。
详见第二节"面板是否有内容"那条。

> 这条的教训比结论重要：**软指标错了会稳定地骗人**。
> 它不红、不进退出码，但会让人拿着一个假信号去"修"一个不存在的问题。

### 观察 4：服务跑的是旧代码快照（stale_build）

写门禁期间 `/api/version` 的 `build_id` 与磁盘指纹长期不一致（`d2728a1c88e8` vs `d4cde…/0a2ef…/80bf2…`）。
静态资源（`app.js`/`app.css`/`index.html`）是**每次请求现读磁盘**的，
所以浏览器拿到的是新前端、后端却是旧逻辑 —— 这类"半个新版"最容易出诡异问题。
门禁把两个版本号都打出来，但不重启服务（多人共用）。**改完后端 Python 一定要重启再复跑。**
后来服务被同事重启、`build_id` 与磁盘一致之后，同一套断言依旧全过（`stale_build=false`），
说明这段差异不在两版代码之间。
