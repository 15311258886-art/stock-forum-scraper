# 前向记账（决策台 / 判据的可验证账本）

> 建立日期：2026-11-05 ｜ 维护：`tools/forward_snapshot.py` / `tools/forward_score.py` /
> `tools/forward_scorecard.py`（口径统一在 `tools/forward_lib.py`）

## 1. 为什么要有这套东西

决策台（`pillar_item`）与三条已采纳判据都是**快照型判断**：读的是当天的舆情、资金流、
当天形态。它们**不能用历史数据重建** —— 上游任何一处变了，历史就重建不出来。
所以验证它们只有一条路：**前向记账**。今天把「它说了什么」原样写下来，到期用真实
收盘价回看。

这和「历史回测」不是一件事，两者的关系是：

| | 历史回测 | 前向记账（本套） |
|---|---|---|
| 适用 | 判据能从原始数据重算（K 线类） | 判据依赖当日快照（舆情/资金流/形态） |
| 结论何时有 | 立刻 | **滞后 = 持有期**（T+1 次日就有，T+120 要半年） |
| 能被事后改口径污染吗 | 能（改判据就重算，历史跟着变） | **不能**（写下去的就是当时的判断） |

## 2. 三个脚本各做什么

```
每交易日 15:35 ─►  forward_snapshot.py   把当天所有可验证判断写进 forward_book
                          │
                          ▼
              次日收盘后 ─►  forward_score.py      回填进场价（次日收盘），按 6 档持有期打分
                          │
                          ▼
                          forward_scorecard.py  汇总成计分卡（按 来源 × 持有期）
```

`forward_lib.py` 只放**口径**（表结构、交易日历、涨停门槛、K 线读取、等权基准），
不放业务判断 —— 三个脚本共用一份，避免「两套口径慢慢漂」。

### 2.1 `forward_snapshot.py` —— 记账

- 决策台：读 `viewer/app.db` 的 `pillar_item`，`src` 记成 `pillar:<主线>`。
  真实字段是 `run_date`（`YYYY-MM-DD` **文本**）/ `pillar` / `symbol` / `name` /
  `rank` / `score` / `reason` / `detail_json` —— 不是 `date` / `code`，读的时候别猜。
- 三条已采纳判据的当日触发名单，`src` 直接用 `tools/cond_engine.py::TOOLS` 的键：

  | src | 判据 | 角色 |
  |---|---|---|
  | `oss_near_high` | 距 250 日最高收盘 ≥ -25% | 选股 |
  | `oss_reversal20` | 20 日累计跌幅 ≥ 20% | 选股 |
  | `pb_vol_price_diverge` | 创 20 日新高且量比 < 0.8 | **排除** |

  判据函数**一行没改**，直接调 `cond_engine.TOOLS[key]["fn"](X)`；
  指标全部来自 `viewer/indicators.compute_indicators`。本套代码里没有任何一条
  技术指标公式 —— 这是硬约束（改了公式，账本就和回测对不上了）。

  扫描池子：`snap_date` 当天有 bar、是真 A 股（与 `viewer/quant.py::_is_ashare` 同口径，
  剔 ETF/可转债/B 股）、且 ≥ 60 根历史。**注意**：`cond_engine` 的池子是「kline 里
  全部代码」（含 ETF），所以那边的条数天生比这里多，这是有意的差异，不是 bug。

  > **口径位置澄清**：这三条判据**不全在 `viewer/playbook.py` 里**。
  > `oss_near_high`（距 250 日高 25% 内）和 `oss_reversal20`（20 日跌幅 20%）是
  > `tools/cond_engine.py` 里的 `_t_near_high / _t_reversal`（卡片与参数在
  > `viewer/toolbox.py`、来源登记在 `viewer/oss_mine.py`）；
  > 只有 `pb_vol_price_diverge` 在 `viewer/playbook.py`。
  > `cond_engine` 启动时会把 `playbook.as_tools()` 并进 `TOOLS`，所以三条都在
  > 同一个字典里，本脚本按这个字典取值 —— 不需要知道它们各自住在哪个文件。

- 安全退出（退出码 0）：当日无 K 线（周末/节假日/未更新）→ 打印原因退出；
  当日 K 线覆盖率 < 90% → 打印原因退出（避免记下半张盘），确要记加 `--force`。

### 2.2 `forward_score.py` —— 回填 + 打分

- **回填**：`entry_px IS NULL AND skip_reason IS NULL` 的记录，找到 `snap_date` 的
  **下一个交易日**，写 `entry_date / entry_px`。两种买不进如实记：
  - 次日收盘涨停 → `skip_reason='limit_up'`（不参与打分）
  - 次日没有 bar（停牌/退市）→ `skip_reason='no_bar'`（不参与打分）
- **打分**：每条已进场记录 × 6 档持有期，写 `forward_result`；未到期也写一行
  `matured=0`（`exit_*` 留 NULL，**不拿最后一天的价格冒充到期**）。
- 幂等：`INSERT OR REPLACE`，主键 `(book_id, hold)`，重复跑行数不变。

### 2.3 `forward_scorecard.py` —— 计分卡

按 `(src, hold)` 给：样本数、到期数、胜率、平均超额、超额中位数、t 值。
同时打印到屏幕、写 `docs/前向记账计分卡.md`（每次覆盖）。

**到期样本 < 20 的格子一律打印「样本不足，不作结论」，胜率/超额/t 全部留空。**
10 个样本里对 7 个就会显示「胜率 70%」，那和抛硬币没区别，宁可不说。

t 值用**非重叠抽样**：先按日把同一天的票压成一条，再按持有期 H 把交易日历切成
长度 H 的桶、每桶只留一条。直接用所有行算 t 会把样本量虚报好几倍（`cond_engine`
里已经踩过这个坑）。

## 3. 口径（固定，改之前先想清楚为什么要改）

| 项 | 口径 | 落点 |
|---|---|---|
| 持有期 | 1 / 3 / 5 / 20 / 60 / 120 个交易日 | `forward_lib.HOLDS` |
| 进场 | 信号日**次日收盘** | `forward_score.backfill` |
| 成本 | 双边合计 **0.25%**，从收益里扣 | `forward_lib.COST_PCT` |
| 收益 | 进场日收盘 → 到期日收盘 | `kline` 表（**已后复权**）|
| 到期日 | 该票**自己**第 H 根 bar（停牌不算到期） | `_code_bars_from_entry` |
| 基准 | 同区间全市场等权收益 | `viewer/logs/ew_index.json` |
| 准 | 前向超额 = 个股收益 − 等权收益 − 成本 > 0 记胜 | `forward_result.excess_pct` |
| 涨停门槛 | 300/301/688/689 → 19.8%；4/8 开头或 920 → 29.8%；其余 9.8%；判定 `ret1 ≥ 阈值 − 0.2` | `forward_lib.limit_thr / is_limit_up` |

`ew_index.json` 只到上一个交易日是常态（`tools/cond_box_market_base.py` 手动跑才更新）。
`forward_score.py` 会用**完全相同**的公式（每只票取自己上一根 bar 算日收益、再取均值、
逐日累乘）把缺的日期补上并原子落盘，保证账本和回测卡片用的是同一条基准线。

## 4. 表结构

两张表都建在 `viewer/app.db`（脚本内 `CREATE TABLE IF NOT EXISTS`，幂等）。

```sql
CREATE TABLE forward_book (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  snap_date   INTEGER NOT NULL,        -- 信号日 YYYYMMDD
  src         TEXT    NOT NULL,        -- pillar:<主线> / 判据键
  code        TEXT    NOT NULL,        -- 6 位代码
  name        TEXT,
  entry_date  INTEGER,                 -- 进场日（信号日次日）
  entry_px    REAL,                    -- 进场价（进场日收盘）
  skip_reason TEXT,                    -- limit_up | no_bar
  signal_json TEXT,                    -- 当天"它说了什么"的原始快照
  created_at  TEXT
);
CREATE UNIQUE INDEX ux_forward_book ON forward_book(snap_date, src, code);

CREATE TABLE forward_result (
  book_id    INTEGER NOT NULL,
  hold       INTEGER NOT NULL,
  exit_date  INTEGER,
  exit_px    REAL,
  ret_pct    REAL,                     -- 个股收益（已扣成本），百分点
  bench_pct  REAL,                     -- 同期全市场等权，百分点
  excess_pct REAL,                     -- ret_pct − bench_pct
  matured    INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (book_id, hold)
);
```

## 5. 接入日更

**结论：没接进服务端调度，用 `run_forward_daily.bat` + Windows 任务计划程序。**

原因是服务端调度在 `viewer/server.py`（`_daily_job` + 14000 行的任务表）里，
接进去要同时改 `server.py` 与 `tools/sched_job.py` 两个正在被别人改的文件；
三个脚本本身幂等、零依赖、无共享状态，用任务计划程序拉起来完全等价。
（要求是「能接就接，结构复杂就退一步」，这里是后一种。）

### 加任务计划程序

1. 打开「任务计划程序」→「创建任务」
2. 常规：勾「不管用户是否登录都要运行」，勾「使用最高权限运行」
3. 触发器：**建两个**，都指向同一个 bat

   | 时间 | 作用 |
   |---|---|
   | 每交易日 **15:35** | 记当天三条判据（此时 K 线增量已补完） |
   | 每交易日 **16:45** | 补记决策台（决策台常 16:02 后才落库，有时更晚） |

4. 操作：启动程序 `F:\AI Agent部署知识库\2026-09-22-11-49-42\stock-forum-scraper\run_forward_daily.bat`
   起始位置填项目根目录
5. 条件：取消「只在计算机使用交流电源时才启动」等节能限制

脚本按 `(snap_date, src, code)` 幂等，一天跑两次只会把「已存在」的条数打出来，
不会产生重复行。日志追加到 `viewer/logs/forward_daily.log`。

> `run_forward_daily.bat` **只写 ASCII**。cmd.exe 用系统 ANSI 代码页（中文 Windows 是 cp936）
> 解析 .bat，UTF-8 的中文注释会变成乱码、甚至把行拆断（第一版就是这么坏的：
> 乱码把引号吃掉，后续命令全部「不是内部或外部命令」）。中文说明一律放本文件。

## 6. 已知坑（都是实测撞出来的，不是假设）

1. **决策台不是收盘即出票。** `pillar_run.created_at` 实测是 16:02 / 18:36 / **次日 00:13**。
   只在 15:35 记一次会永远漏掉当天决策台记录，而 `pillar_item` 只写当天、漏了补不回来。
   → 所以 `forward_snapshot.py` 对决策台默认**回看 3 个交易日**（`--pillar-lookback`），
   账本按各自的 `snap_date` 落，进场价仍算「该日次日」，口径不变。**这是原设计没考虑到的一点。**
2. **15:30 之后的 K 线库常常打不开。** `kline_daily` 日更在写的时候，`kline_daily.db`
   的 `-shm/-wal` 被独占，任何打开方式（plain / `mode=ro`）都报
   `unable to open database file`，只有 `immutable=1` 能读 —— 但它忽略 WAL，读到的是昨天的数据。
   **拿旧数据冒充今天比打不开更坏**，所以 `forward_lib.connect_kline` 只重试（6 次 × 5 秒），
   不降级到 immutable；重试仍失败就打印原因、退出码 0。
   同理，`forward_snapshot.py` 有**覆盖率闸门**：当日有 bar 的票数 < 上一交易日的 90% 就不记账。
3. **`viewer/app.db` 会被服务端长时间占用。** 第一次记账撞到 `database is locked`
   （`indicators_daily` 一轮实测几十分钟）。→ `connect_app(timeout=180)` +
   写账重试（4 次 × 20 秒，失败 rollback 重来）。真被占着就下次再跑，不写半截。
4. **别用 `io.TextIOWrapper(sys.stdout.buffer)` 包 stdout。** 解释器退出时会先关 wrapper、
   再关 buffer，之后任何 `print` 都报 `I/O operation on closed file`（本项目 `cond_engine`
   等老脚本用的正是这个写法）。本套统一用 `sys.stdout.reconfigure(...)`。
5. **已有同名近似脚本**：`tools/pillar_forward_score.py`（181 行，未被 git 跟踪）做的事是
   「把已有 `pillar_item` 历史一次性打 T+1/T+2/T+3/T+5 的分」，口径是**进场=出票日收盘**
   （偏乐观）。本套是**进场=次日收盘**、6 档持有期、逐日入账。两者不冲突但会混淆 ——
   建议把老脚本定位成「历史快照分析」，别再当成验证结论。
6. **`run_forward_daily.bat` 必须 ASCII + CRLF**（见第 5 节引用块）。

## 7. 怎么读结论（重要）

- **只看「到期数 ≥ 20」的行**，其余行留在表里是为了看进度，不是看结论。
- `角色=排除` 的判据（`pb_vol_price_diverge`）**超额为负才对** —— 它是「别买」的判据。
- 别把六个持有期加起来看：同一批票在 1/3/5/20/60/120 上是六条互相重叠的序列。
- **头一个月不要下任何结论。** T+20 要 20 个交易日、T+120 要半年才到期。
