# 股票覆盖度排查报告（2026-10-30）

> 起因：进哥多次反馈「我一共有 5000 多只票，你老从几百只里反复选」。这次做了完整漏斗排查，
> 结论是——**这个问题一直没修好，而且不止一处**。本报告记录每一层的实际数字、根因与修复。

## 一、结论先行

| # | 位置 | 修前 | 修后 | 性质 |
|---|---|---|---|---|
| 1 | 预测候选池（`strategy_sim.universe`） | **594 只**（历史 13 天恒为 157） | **1974~2235 只** | 真 bug，且 `POOL_LIMIT` 从 160 调到 2000 完全没生效 |
| 2 | 低波池（`selection.POOL_MAX`） | 300 只（实际符合 609 只） | **609 只**（不截断） | 真 bug，砍掉了 51%，且丢的全是 C 级 |
| 3 | 基本面（`fundamentals`） | **1123 只**（20%） | **5055 只**（99%） | 数据缺口，可补齐 |
| 4 | 股东数据（`stock_holder_num`） | **568 只**（10%） | 每轮 +800 只推进中 | 同类 bug：采集入口依赖已清空的 `positions` |
| 5 | 低位突破池（`screener_lowbox`） | 硬编码 80 只 | 可配置（默认仍 80，披露实际只数） | 设计约束，非 bug |

一句话：**「漏股」不是筛选条件太严，而是几处兜底逻辑依赖了已经清空的表（`positions`），
导致池子在第一步就被锁死，后面的 `LIMIT` 调多大都没用。**

## 二、根因：`universe()` 的兜底顺序写反了

`strategy_sim.universe()` 原逻辑：

```
① 读 stock_liquidity 表（近 60 日成交额）      ← 这张表本机从未建过，必然抛异常
② except 吞掉异常 → 走「positions ∪ lhb_stocks」 ← positions 已清空(0 行)，只剩龙虎榜 703 只
③ 如果 codes 非空 → 只做 codes -= excluded（剔 ST）
④ 从来不会走到「干净宇宙全量」这条分支
```

关键点在第 ③ 步：`if not codes:` 才回退全宇宙，而 `codes` 因为 703 只龙虎榜票**永远非空**，
于是全宇宙分支成了死代码。加上最后又 `sorted(codes)[:limit]` 做了一次按代码字典序截断，
流动性排序也一并丢了。

**铁证**（`prediction_run.pool_n`）：

```
2026-10-23 ~ 10-09  157 只（13 天，恰好是旧 POOL_LIMIT=160 减掉几只 ST）
2026-10-26          658 只
2026-10-27          687 只
2026-10-28          734 只
2026-10-29          594 → 修复后 1974 只
```

594~734 的波动来自「龙虎榜每天新增几只」，与流动性、与全市场毫无关系。这也解释了
为什么 2026-10-26 把 `POOL_LIMIT` 从 160 提到 2000 之后，池子只是从 157 变成 594~734
而不是 2000——**limit 永远没被触发过**。

## 三、修复

### 3.1 `strategy_sim.universe()` 重写（范围最大的改动）

新的来源优先级，前一级失败才降级，**每次降级都打日志，绝不静默**：

```
① stock_liquidity 表（若存在）
② 本地日线全库 data/kline_daily.db 算近 60 交易日平均成交额   ← 当前实际主路径
③ 干净宇宙全量（all_ashares − ST/无K线）
④ lhb_stocks 龙虎榜历史（仅在前三者全空时兜底，打印警告）
```

同时修掉：
- 剔北交所（4/8/92 开头）与 `selection._bad_code` 统一口径 —— 原代码 `s[0] in "03648"`
  把 4/8 开头的北交所放了进来，却又用 6 位数字过滤掉了 920 开头的（340 只），口径不一致。
- 去掉末尾的 `sorted(codes)[:limit]`，保持流动性降序（截断前剔除 ST，保证凑够 limit）。
- 池子 < 200 只时打印警告，避免再次静默锁死。

实测：`universe(2000)` → 2000 只 / `universe(6000)` → 5021 只（可用宇宙全量），耗时 3.6s。

### 3.2 `fetch_bars()` 改本地优先（配套，否则扩池必崩）

候选池扩到 5000+ 只后，原来「每只票走新浪网络抓 660 根」的做法直接不可行：

| 场景 | 修前 | 修后 |
|---|---|---|
| 全池 5021 只 | 5021 次网络 × 660 根（不可能完成） | 本地库直读 **9.5 秒**，零网络 |
| 本地缺当天 | —— | 网络只补 2 根/只，**28.5 秒**，成功率 100% |

关键验证：本地 `kline_daily.db` 与新浪 hfq **逐字段一致**（000001 / 600519 / 300750 三票核对，
开高低收量全等），且本地比新浪多当天一根。故历史统一走本地，不存在口径漂移。

顺带修掉三个隐患：
1. **新鲜度判断用裸 `today()`** → 非交易日早上会把全池判成「缺当天」→ 5000 只全量重抓。
   改为用 `_latest_trade_date_anchor()`（交易日历给出的最近已收盘交易日）。
2. **`force=True` 强制全池重抓** → 本地库就是最新源头，重抓无收益只撞限流。改为「本地有锚点日数据就直接用」。
3. **写回 kbase 报 `readonly database`** → `kc` 是 kbase 的包装对象，`__setitem__` 会触发落库。
   本地数据本就不该回写，去掉写入；网络结果写入加 try/except，落库失败不阻断预测。

并发 8 → 16（实测 200 只：8 并发 1.6s / 16 并发 0.74s，16 是拐点，再高收益递减且易限流）。

### 3.3 `selection.POOL_MAX` 300 → 1200

实测满足入池条件的有 **609 只，但只入库 300 只**——砍掉 51%，而且因为排序是 (tier, amp)，
被砍掉的全部是 C 级，等效于偷偷收紧了入池标准。SQLite 存 1000 行毫无压力，故放到 1200。
真被截断时 `payload.stats.capped=True` 会被前端显式标出。

### 3.4 `fundamentals` 全量回补

原本只有 1123 只（20%），四支柱的「基本面」支柱对 80% 的票是空的。实测抓取 10 只仅 0.9s，
全市场 5021 只约 8 分钟，故一次性补齐：

```
完成 286.1s，ok=3932，failed=0，库中 5055 只
```

连带效果：低波池 ROE 覆盖从 **213/609 → 609/609**（重算池子后）。

### 3.5 `holders_fetch.collect_codes()` 与 3.1 同源的 bug

`collect_codes` 只从 `positions ∪ lhb_stocks` 取，positions 清空后待抓列表永久停在 703 只，
股东数据 568 只就再也不动了。改为「先补干净宇宙里缺记录的票」：

- 待抓候选：703 → **4975 只**
- 串行 GAP=0.35s，全量约 2.6 小时 → 加 `--max-per-run`（默认 800 只/轮，约 25 分钟），
  每天推进一点，约一周补齐。

### 3.6 低位突破池 80 只：披露而非硬扛

`api_screener_lowbox` 原来硬编码 `universe[:80]`。实测提到 200 只后跑 3 分钟仍未算完
（估值/实控人/分红是逐只外部接口，成本线性），而 80 只稳定在 30~60s。
故**默认仍 80**，改为可配置（`LOWBOX_POOL_MAX`），并新增 `pool_candidates` / `pool_capped` /
`pool_max` 三个字段如实披露——这个模块的池子定义本就是「关注池 ∪ 板块Top30」，不是全市场选股，
把它说清楚比硬撑耗时更诚实。

## 四、前端披露（否则修了也看不见）

- **预测面板**：市场状态行新增「深度分析 2235 只」「全市场快扫 5329 只」两个标签，
  悬停有口径说明。两个数字必须同时出现——只给前者会被误读成「只分析 2235 只」。
- **选股面板**：低波池上方新增「覆盖范围：全市场 5500+ 只 → 剔 ST/北交所/新股后约 5000 只
  全量扫描 → 满足条件 609 只」。
- **修掉一处虚假披露**：前端原写 `pool.slice(0, 40)` 只渲染 40 行，文案却写「本页全部列出」。
  改为默认 60 行 + 「展开全部 609 只」链接，展开后如实渲染全部。

## 六、必须说清的边界

1. **深度分析仍是 2000 只，不是 5021 只**。四支柱对每只票跑 64 个策略，5021 只实测超时（>500s），
   2000 只是「82 秒能跑完」的合理上限。剩下的 3000 只由「全市场快扫」（`stock_universe_scan`，
   每日 5329 只全量重算）覆盖。这是**两层分工**，不是漏股——但界面上必须两个数字都给，
   否则就是第二种形式的隐瞒。
2. **指标表 5309 只 vs 日线 5534 只的 225 只缺口，全部可解释**：194 只 ST/退（设计内剔除）、
   15 只北交所、19 只新股（MA200 需要 200 根日线，新股天然算不出）。审计脚本对此有 PASS 判定。
3. **15:05 跑预测时本地库还没有当天数据**（`kline_daily` 15:30 才开始）。所以收盘后那一次
   仍会走网络补 2 根/只，实测 28.5 秒、5000 只 100% 成功。若某天新浪异常，`fetch_bars` 会
   把「本地命中/网络补/成功数」写进 meta 并打日志，不会静默用残缺数据。
4. **股东数据仍只有 568 只**，补齐需一周（每轮 800 只）。在补齐前，`sig_holders` 信号
   对没有数据的票贡献为 0——这不是「没分析」，是「这条信号对该票无输入」。
