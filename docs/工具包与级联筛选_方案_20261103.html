你的原话是：「符合 K 线预测的，5000 多只刷完只剩 2000 只，另一个策略再点剩 50 只，再筛剩 10 只」。这句话的本质不是要一个筛股器，是要一套方法论的货架——每条方法都摆上去，标好它是干什么的、什么时候收的、跑出来什么效果，你自己拿起来叠着用。

02三层模型：素材 → 工具 → 漏斗

素材（Source）

GitHub 仓库里的因子公式 / B站 3306 条教学 / 豆包 2701 条语料 / 我们自己写的模块。
素材不能直接用，它只是原料。

工具（Tool）

素材被「编译」成的可执行单元。每个工具带一张能力卡（收录时间 / 为什么收 / 干什么 / 实测表现）。这是新加的货架。

工具分三类，这是整个设计的支点

类型干什么能不能收窄池子现有例子
观察器 view给每只票打标/打分，但不淘汰任何一只不能（除非手动设阈值）Kronos 打分、共振卡
筛选器 filter入池 → 出池，明确留谁不留谁能，这是漏斗的齿准入闸门、箱体谷底、避雷 C
评分器 scorer给每只票打分并排序设了阈值就能当 filter 用四支柱、Kronos

为什么必须分这三类

Kronos 本身是个打分器，它不会告诉你「这 3000 只不要」。只有当你说「分数低于 X 的丢掉」，它才临时变成筛选器。
分清楚了，同一份能力就能以两种身份出现在货架上——只在需要收窄的时候，让它当齿。这是「过时/不好用的也留着让人自己试」能成立的前提：观察器永远不会因为「筛不出东西」被淘汰。

03统一插口：所有工具同一个函数签名

能不能级联，全看这一处。所有工具——不管是现成的闸门还是新拆的均线 — 都实现同一个 apply()：

def apply(con, codes: list[str], params: dict) -> dict:
    """任何工具对一批代码做一件事，返回统一结构。"""
    return {
        "kept":    ["600519", "000001"],        # 留下来的
        "dropped": {"300750": "箱体仅 0.4 年"},  # 淘汰的 + 原因（要能给人看）
        "score":   {"600519": 86.6},          # 可选：打分器才有
        "stats":   {"in": 5003, "out": 1408, "ms": 812},
        "note":    "箱体≥1.5年 且 位置<25%",      # 一句话讲清这步干了啥
    }

dropped 带原因是关键——你点开结果里任意一只被淘汰的票，能知道它死在第几级、为什么死。不然漏斗就是个黑箱，你不敢信它。

04工具登记表：能力卡就是这张表的字段

你点名要的「收录时间 / 为什么收 / 作用 / 表现」，我直接做成 NOT NULL 字段，写不进去就不许登记，从机制上防止以后忘了为什么收它。

CREATE TABLE IF NOT EXISTS tool_registry (
    tool_key      TEXT PRIMARY KEY,   -- 'kronos_kline'
    name          TEXT NOT NULL,      -- 'Kronos K线预测'
    kind          TEXT NOT NULL,      -- view | filter | scorer

    source_kind   TEXT NOT NULL,      -- github | bilibili | doubao | builtin
    source_url    TEXT,               -- 原始链接，点得回去
    adopted_at    TEXT NOT NULL,      -- ★ 收录时间

    why           TEXT NOT NULL,      -- ★ 为什么收它（不可空，防遗忘）
    what          TEXT NOT NULL,      -- ★ 作用是什么
    evidence      TEXT,               -- ★ 实测表现（跑出来的，不是抄的）
    caveat        TEXT,               -- 短板 / 适用边界 / 什么市况下会失效

    params_schema TEXT,               -- JSON：可调哪些参数
    default_params TEXT,              -- JSON：默认值
    status        TEXT NOT NULL,      -- active | shadow | retired | experiment
    last_run      TEXT,
    last_in       INTEGER,
    last_out      INTEGER,
    last_ms       INTEGER,
    sort_order    INTEGER DEFAULT 100
);

四个状态，直接对应你说的「过时的也留着让我试试」

状态含义在漏斗里在列表里
active在用，有效可选正常
shadow影子运行：算了但不影响结果只记录，不淘汰正常
experiment试验中，效果未知可选（会有提示）正常
retired已退场（失效/过时/市况不适配）默认不参与留着，可手动启用

收录时间怎么来——不用我编

现成模块的 adopted_at 用 git log --diff-filter=A -- viewer/xxx.py 的首次提交日回填，是真实入库日，不是拍脑袋写个 2026-11-03。GitHub 来的记仓库 commit 日期，知识库来的记语料入库日。跑一遍脚本全部灌好，一个都不留空。

规则很简单，三条：

  1. 顺序你自己调。先闸门后箱体，还是先箱体后闸门，结果不一样。这个权力给你，不写死。
  2. 每一步都能撤。点漏斗上的任一节点就把它摘掉，池子立刻回弹。
  3. 每一步都记账。哪一个工具淘汰了多少、耗时多少，全部回写到 tool_registry.last_in/last_out/last_ms。跑得多了，哪个工具最狠、哪个最没用，一眼看出来。

08能力卡的具体长相

点左边列表里的工具，右边就是这么一张卡。你要的六件事全在里面，不啰嗦：

Kronos K线预测
kronos_kline · 打分器 · 来源 GitHub · 收录 2026-09-XX（按提交日回填）
为什么收
文件体积极小（十几 MB），不依赖几十个手工因子，直接把 K 线当序列喂给模型。实测命中率不比多因子方案差，但开发成本低一个量级——性价比高到值得单独留一个位置。
作用
对每只票未来 N 日收盘价给预测，转成涨跌概率分。当打分器用是排序，设阈值后变成筛选器收窄池子。
实测表现
最近一次：输入 675 只，输出 675 只（打分器不淘汰），最高分 XX，耗时 XX 秒。此栏由每次运行自动回写，含后续 20 日胜率，不是我写死的文案。
短板
只吃价格序列，不看基本面。遇到停牌/一字板会失真。极端行情下外推不可靠。
参数
预测窗口 N 日、最小历史长度、分数阈值（设了才淘汰）
评价
把 GitHub 上某博主发布的那个 Skill 原样接进来，几乎没有二次开发。

10两个需要你定的口径

① 工具包的池子，能不能喂给 AI 复盘？

我的意见：不行。上一轮刚把 AI 复盘的取数独立化，就是为了让它的选股逻辑跟规则策略零交集。如果把工具包筛出来的池子作为「证据」给它，等于绕个弯又接回去了。
所以两条线在决策台各占一块，互不喂料。你要是想让它俩对照着看，那是展示层并排显示，不是数据层互相喂。

② 淘汰原因要不要默认展开？

我打算默认折叠，点开某只票才看它死在第几级。全部展开会让结果表变成几万行怨气。
但漏斗每个节点上会直接标出「这一级掉了多少只」，一眼看到杀伤力——你要的透明度靠这个，不靠倒垃圾。

三个第一版判据被数据推翻（计划里没预料到的）

① MACD 底背离第一版跑出 0 只。不是市场没背离，是判据自相矛盾——要求「今日创 60 日新低」（今天在跌）同时「DIF 连抬三日」（今天在涨）。实测 318 只创新低的票里，DIF 能连抬三日的只有 2 只。改成比较两个低点之后是 293 只。
② W 底第一版 1117 只（21%）等于没筛。下跌中继也会造出两个相近低点，加了「MA20 不得低于 MA60 的 98%」和「现价须离开第二底 2%」才收到 488。
③ 波浪第一版 1804 只（34%）。三个数只描述「现在长什么样」，不描述「浪走到哪儿」。加了两个顺序约束（低点须在高点之前、中途须调过 ≥15%）才收到 521。

所以计划里那句话得补一条：「跑出 evidence 再调」还不够，要先怀疑判据本身是不是自洽——见到 0 只先查代码，再查数据。

喂进去的式子结果理由
pct(close,20)拒与「风格·20日动量」相关 1.00，逐字换皮
-std(pct(close,1),20)拒撞「波动」1.00 + IC 0.006 + t 1.92

自检顺带跑出一个市况事实：近 250 日 20 日动量的 IC 是 −0.028（负），说明这段时间是反转市不是动量市。

与方案原计划的两处偏差，说明理由

① 货架是 22 个不是 20 个：原计划二期接 9 个语料方法论，实际只做了 6 个技术形态——另外 3 个（资金流类）本地没有对应数据源，硬做就是编。空着比填假的好。

② 没有做成「每 7 天扫描」的调度：项目的调度是「当日未跑就补跑」的日更模型，没有周模型。把节流放进任务内部（每日 16:30 触发、7 天内直接跳过），机器关机几天再开机也不会漏一次；写在调度层会漏。

③ 扫描器不自动编译因子，这是刻意划的边界：各仓库复权口径不同，拿我们的日线跑别人的式子，IC 会「假得像真的」。发现自动、编译必须有人——人读 README 写成一行式子，再过门禁。

级联的一个硬发现：不是叠得越多越好

「W 底 → MACD 背离 → 缠论中枢」三连实测 5264 → 488 → 16 → 0。不是数据没票，是三个判据互相排斥：W 底要两底等高（价差 ≤5%）、MACD 背离要第二个底更低、缠论中枢要现价在 60 日 25~75 分位内。
三条串起来等于要求一只票同时「在底部、还在创新低、还在横盘震荡」，逻辑上就不该有票。所以预置链只加了两级的两条：底部确认 5264→488→16、平台真突破 5264→21→5。
