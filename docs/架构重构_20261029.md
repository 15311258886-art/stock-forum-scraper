# 底层链路重构记录 · 2026-10-29

> 缘起：用户截图显示 AI 复盘面板「请求超时（15 秒未响应）→ 正在自动恢复 第2/3次」，
> 面板永久停在「正在加载数据…」。用户判断"多次修复后问题反复出现，怀疑架构层面有问题"。
> 该判断成立。本文记录**实测根因**（非推测）、改法、以及为什么以前的补丁挡不住。

---

## 一、根因：三条链路同时失效（有日志实证）

### 1. 并发雪崩 —— 调度器一次性放行 6 个重活

`viewer/logs/server-20261029.log` 原文：

```
17:42:45  调度器同 tick 启动：kbase_daily / indicators_daily / kline_daily /
          universe_scan / strategy_templates / a_shares_snapshot
17:42:46  kbase_daily 进程 RSS 3.9 GB（要读 2.3GB 的 kbase.db）
17:4x     universe_scan 抛 sqlite3.OperationalError: database is locked
17:40:52  WARNING 慢请求 GET /api/refresh_status 耗时 246505 ms   ← 246 秒
17:40:52  [sched] 本轮 623.6s｜indicators_daily=303.3s，heavy_daily_refresh=251.0s
```

**关键补充**：`/api/ai_review` 本身并不慢。事后实测该接口 **94 毫秒**返回（缓存命中）。
用户看到的"AI 复盘超时"，实质是**那 15 秒里整个后端都不在服务**，AI 复盘只是撞上这个时刻的
那一个接口。这解释了为什么"每次都修 AI 复盘、每次都没修好"。

### 2. 补丁为什么挡不住

| 已有补丁 | 局限 |
|---|---|
| `_spawn_offproc` 的 `_JOB_PROCS` 防重入 + `_OFFPROC_GAP` | 只管**单个任务**，六个任务各自都"合法"，叠加起来才是雪崩 |
| `_idle_gate` 用户忙碌闸 | 只在任务**启动瞬间**看用户是否活跃；一旦放行，跑 49 分钟期间用户回来照样冻站 |
| `_HEAVY_CACHE` 落盘 + 子进程 | 只覆盖 4 个面板接口，调度任务不在其中 |

缺的是**全局视角的准入控制**。

### 3. 日更任务「先写标记再启动」——数据静默停更

8 个 `_xxx_maybe()` 同构函数（a_shares_snapshot / kline_daily / kbase_daily / douyin_corpus /
build_exclusion / indicators_daily / universe_scan / strategy_templates）都是：

```python
DB.set_meta("xxx_done", day)      # 先落标记
_spawn_offproc("xxx")             # 再启动
```

若 `_spawn_offproc` 被拒（并发/上一轮未完成）或起进程失败，标记已经落地 →
**当天彻底不再跑**，且日志只留一句"已忽略，下轮重试"。

同时 `set_meta` 在 `database is locked` 时抛异常 → except 打 ERROR → 10 秒后再试 → 再抛。
日志 17:41:02→17:41:57 六个任务轮着刷，**每次重试都是一次新的写锁请求**，正反馈放大拥塞。

### 4. 进程堆积

`app.db-shm` 被并发子进程句柄锁死（`Permission denied`），导致**除服务进程外任何进程都打不开库**
—— 包括项目自带的 MCP 服务、`_gen_report_*.py`、`audit_*.py`。
服务停掉后 shm 立刻恢复。这也是"脚本经常跑不通"的隐藏原因。

父进程重启后，上一代 `sched_job.py` 变孤儿：新进程不知道它们存在 → 继续抢磁盘/写锁，
且会重复调度同一任务。实测清理时发现 **4 个残留进程，其中最早的 05:09 启动、已存活 12 小时**。

## 二、改法：加一层内核，而不是继续打补丁

```
请求线程 ──► 只读快照 / 仅写一行队列记录（目标 <1s，不现算）
                │
                ▼
         kernel.brake  ──► 唯一的准入闸
                │           · 全局总闸 1（compute+fetch 合计）
                │           · 写域互斥（app / kbase / kline / ai）
                │           · 失败指数退避 60→300→900→1800s
                │           · 超时熔断（先 terminate，再 kill）
                ▼
         子进程（BELOW_NORMAL 优先级）──► 落盘 / 写库
```

### 新增文件

| 文件 | 作用 |
|---|---|
| `viewer/kernel/__init__.py` | 内核包说明与设计原则 |
| `viewer/kernel/brake.py` | 全局刹车闸：配额 / 写域互斥 / 超时租约 / 退避 / 状态查询 |

### 改动点

| 文件 | 改动 |
|---|---|
| `viewer/server.py` | `_spawn_offproc` 接入闸（唯一出口，一处覆盖 25 个任务）；8 个日更函数收敛为 `_daily_job()`；子进程降优先级；启动清理孤儿；超时熔断 |
| `viewer/ai_review.py` | 新增 `workbuddy` provider + 分析队列（`ai_review_queue`）；拼包转后台并落盘 |
| `mcp_server/tools.py` | 新增 3 个工具：`list_analysis_jobs` / `get_analysis_brief` / `submit_analysis` |
| `viewer/static/app.js` | `/api/ai_review` 纳入重接口预算；失败态在面板内说清原因（不再留"正在加载数据…"） |

## 三、WorkBuddy 算力通道

### 为什么不直接在本进程调 WorkBuddy

本进程是 HTTP 服务，职责是"把数据摆出来"，不该成为任何外部智能的同步依赖。
因此拆成生产者 / 消费者：

```
查看器（生产者）  ── 取数、拼信息包、写 ai_review_queue(state=pending)，立即返回
WorkBuddy（消费者）── MCP 取 brief → 用自己的推理分析 → submit 回填 ai_review 主表
```

三个实际好处：
1. 本进程零模型调用，不会被拖慢；
2. 不绑定本机 API Key，换模型不改代码；
3. 全程留痕（`taken_at` / `done_at` / `raw_text`），比黑盒 API 调用更可审计。

### 实测链路耗时

| 环节 | 耗时 |
|---|---|
| 点「分析」→ 入队返回 | **1.35 s**（改造前 18.2 s） |
| 后台备好信息包（30717 字 / 59 KB） | 2 s |
| WorkBuddy 取包（读落盘） | 0.02 s |
| 回填 | 0.19 s |
| 前端读取 | **87 ms** |

### MCP 接入方式

MCP 客户端配置指向 `mcp_server/launch.py`，工具清单共 15 个，其中：
- `list_analysis_jobs` — 看待办
- `get_analysis_brief(queue_id)` — 取包（含 system_prompt / user_prompt / context / schema）
- `submit_analysis(queue_id, output)` — 回填（**唯一带写能力的工具**，写权限收敛在 `_rw_connect()` 单点）

## 四、运维参数

环境变量（都可选，不设则用默认）：

| 变量 | 默认 | 含义 |
|---|---|---|
| `BRAKE_MAX_TOTAL` | 1 | compute+fetch 合计并发上限。机器强可设 2 |
| `BRAKE_COMPUTE` | 1 | 重计算类配额 |
| `BRAKE_FETCH` | 1 | 网络抓取类配额 |
| `BRAKE_LIGHT` | 2 | 轻任务配额（AI 分析永不被重活饿死） |
| `BRAKE_STALE_COMPUTE` | 7200 | 租约超时（调用方失联时自动释放） |

单任务超时上限见 `server.py::_JOB_TIMEOUT`，未登记任务默认 3600s。

### 排障入口

- `BRAKE.status()` → 当前谁在占坑、各自跑了多久、被拒次数
- `brake.backoff_status()` → 哪些任务在退避、下次何时重试
- `ai_review.queue_status(conn)` → 队列统计与最近任务
- 日志关键词 `[brake]` —— 已限频，同一任务 120 秒最多一条

## 五、遗留与待办

1. **`predictor_daily` 单轮耗时异常**（历史 45 分钟以上无进度输出）。架构上已由超时熔断兜住
   （90 分钟强制终止 + 退避），但业务层为何慢未查清，建议单独排查 `viewer/predictor.py`。
2. **快照层（snapshot.py）尚未落地**。当前重接口仍各自实现落盘，未统一；下一步可把
   `_HEAVY_CACHE`、`_TTL_CACHE`、lowbox/variant 三类收敛成一套 `snapshot.get(route)` 语义。
3. **前端默认 provider 仍是 deepseek**（可自动出结果）。WorkBuddy 需手动切换 —— 有意为之：
   若默认 WorkBuddy，用户每次都要等人工触发才能出结果，反而更像"点了没反应"。
