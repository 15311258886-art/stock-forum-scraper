# 存储成本与冷热分离方案（P1-4，2026-11-01）

> 触发点：`viewer/app.db` 涨到 **8.9 GB**（9,501,859,840 字节；本文与 `du -h`、`storage_report.py` 统一用 GiB 口径，按十进制讲是 9.5 GB），而备份目录 `viewer/backups/` 又躺了 **9.8 GB**。
> 进哥的机器不是无限的，而这份库里有 **89% 是十年里没人再查的历史因子**。
> 本文只做两件事：**把账单算清楚**，**把迁移的前置条件写死**。
> 本轮**不迁移任何数据** —— 理由见第五节。

配套工具：`tools/storage_report.py`（随时重新出账）。

---

## 一、账单（2026-11-01 实测，非估算）

`dbstat` 逐对象归账（SQLite 官方口径，每页归到具体 btree）：

| 对象 | 占用 | 页数 | 说明 |
|---|---|---|---|
| `stock_indicators_daily`（表本体） | **7,323.8 MB** | 1,876,887 | 1,316.7 万行 / 58 列，2010-01-04 ~ 2026-10-30 |
| `sqlite_autoindex_stock_indicators_daily_1` | 379.4 MB | 97,134 | PK `(code, date)`，**不可删** |
| `idx_sid_code_date` | 379.4 MB | 97,134 | **与上面那行逐页完全相同 —— 纯冗余，本轮已删** |
| `idx_sid_date` | 270.5 MB | 69,253 | 按日切片唯一入口，**不能删**（主键前缀吃不到它） |
| 其余 130 张表 + 90 个索引 | 合计约 1.1 GB | — | 单表没有超过 200 MB 的 |

库级：`page_size=4096` / `page_count=2,319,767` / `freelist_count=0`（删除前）/ WAL 4.8 MB。
**一个反直觉点**：删索引后 `du -h` 不会变小 —— SQLite 把页挂到 freelist 复用，不还给文件系统。
要真变小必须 `VACUUM`（重写全库、需约 1 倍库大小的空闲空间并长时间锁库），本轮明确不做。

## 二、为什么「近端留 SQLite + 历史转列存」是对的方向

不是"因为 Parquet 时髦"，是**查询模式本来就是冷热分层的**，证据在代码里：

| 读者 | 实际取数形态 | 需要几年历史？ |
|---|---|---|
| `viewer/indicators.py`（写入方） | 每票最近 `WINDOW=260` 交易日 | 260 日 |
| `viewer/avoid.py:178` | `SELECT DISTINCT date ... LIMIT 3`（最近 3 个交易日现算，不落库） | 3 日 |
| `viewer/server.py` 各即时接口 | 按 `code` 取窗口、按 `date` 切片 | 260 日 |
| `viewer/signal_backtest.py:377` | `SELECT DISTINCT code` → 逐票 `WHERE code=? ORDER BY date DESC LIMIT ?` | 参数可调，季度跑一次 |
| `tools/backfill_factors.py` | 一次性回补 2016→今（**写**） | 全历史 |
| `viewer/security_master.py:491` | `SELECT code, MAX(name) GROUP BY code`（全表聚合，元数据刷新） | 全历史（但只需 code/name） |

即时查询（用户点一下就要出结果的那 99% 流量）**只碰近端 260 个交易日**；全历史只有季度回测
和一次性回补会碰。而这两类恰好是**列存 + 分析引擎（DuckDB）**的主场：全表扫描 + 聚合，
比 SQLite 逐行走 btree 快一到两个数量级。

### 留 260 日能省多少（实测算出来的，不是拍的）

```
日期范围        2010-01-04 ~ 2026-10-30
最近 260 交易日  起点 = 2025-09-29
这 260 日行数    1,371,899 / 13,167,610 = 10.4%
按比例推表体积   7,323.8 MB × 10.4% ≈ 763 MB
```

即：**表本体可回收约 6.5 GB**，加上同比缩小的索引，`app.db` 有机会从 8.9 GB 落到 2~3 GB。
这才是"能立刻省出真金白银"的量级 —— 而本轮删冗余索引只省了 379 MB，是零风险的顺手活。

## 三、迁移前置条件（不满足就别动）

### 3.1 必须先改的代码（`grep -rc stock_indicators_daily` 实测 38 个文件）

按"是否会读到 260 日以前的行"分类，**这几处必须改**（其余只是引用表名/注释）：

| 文件 | 命中行号 | 为什么要改 |
|---|---|---|
| `viewer/signal_backtest.py` | 377, 388, 425, 447, 455 | 回测主循环逐票取窗口；窗口长度由参数决定，会伸出 260 日之外 |
| `viewer/security_master.py` | 489-492, 549 | `GROUP BY code` 全表聚合；迁移后要么并集扫两处，要么只扫近端（会漏退市票） |
| `tools/backfill_factors.py` | 95, 136 | 回补写入方；写入目标表结构决定冷热边界 |
| `tools/signal_ic.py` / `tools/gen_signal_baseline.py` / `tools/regime_robust.py` | 各 1-2 处 | 统计类脚本，需要全历史样本 |
| `tools/backtest_lowvol_industry.py` / `tools/audit_coverage.py` / `tools/audit_universe.py` | 各 5-6 处 | 审计/回测，需要全历史 |
| `tools/probe_*.py`（6 个） | 各 1-3 处 | 一次性探针，可接受"只探近端"的降级 |

> 结论：**迁移面 = 约 10 个文件**，其中 6 个是可降级的探针/审计脚本。
> 真正要小心的是 `signal_backtest.py` 与 `security_master.py` 两个 —— 它们是"正确性"链路。

### 3.2 必须先具备的能力

1. **影子校验**：先只读导出一份 Parquet，用同一段回测分别跑 SQLite 与 DuckDB，**逐票逐日比 close/因子值**。
   没有这一步，任何"迁移后回测结果变了"的争论都会变成互相猜。
2. **口径清单**：REAL 精度、`NULL` 排序、`TEXT` 日期比较（`'2026-1-1'` vs `'2026-01-01'`）、空串 vs NULL、
   重复主键处理 —— 这些是双引擎最容易出分歧的地方，必须在影子校验里逐条断言。
3. **回滚开关**：回测入口加 `--source=sqlite|duckdb`，任何异常能一键切回。

## 四、风险（写在这里，免得下一个人重新踩）

| 风险 | 具体后果 | 缓解 |
|---|---|---|
| **Parquet 需要新依赖**（pyarrow/fastparquet） | 本机沙箱有装包限制，装不上就整个方案停在纸面 | 先确认能否装；装不上则退到 DuckDB 读 SQLite attach（省不了盘，只提速） |
| **双引擎口径不一致** | 同一策略在两个引擎跑出不同收益 → 决策依据失真 | 3.2 的影子校验 + 口径清单；不一致就不迁移 |
| **中间态最危险** | "一半历史在 Parquet、一半在 SQLite"，任何遗漏都会静默少算一段行情 | 迁移期用一个 `view()` 统一入口，禁止业务代码直连任一存储 |
| **`VACUUM` 需要停机 + 1 倍空闲磁盘** | 8.9 GB 库要 ~9 GB 空闲，锁库期间查看器不可用 | 放到单独窗口做；先 `storage_report.py` 确认 freelist 规模再约时间 |
| **备份目录也在膨胀** | `viewer/backups/` 9.8 GB（含一份 8.8 GB 的 `app.db.pre-*` 手工快照） | 本轮只加"空间闸 + 存量提示"（`tools/db_backup.py`）；**不自动删**，等人工确认 |

## 五、本轮为什么不迁移

1. **装包受限制**：Parquet 路线要新依赖，本轮无权安装，做了也只能停在"导出一半"。
2. **口径风险高于收益**：迁移错了不是"慢一点"，是**回测结论失真**，而回测结论正在驱动 `SIGNAL_WEIGHTS`。
3. **`VACUUM` 需要停机窗口**：这不是工程师能单方面决定的事。
4. **顺序问题**：先得有体检工具（本轮交付 `tools/storage_report.py`），
   才能证明"迁完真的省了"，也才能在迁移后回看有没有漏。

本轮实际做的是**零风险的部分**：删掉与主键逐页重复的 `idx_sid_code_date`（-379 MB 空间、
查询计划不变），并把账单、判定规则、迁移前置条件固化下来。
