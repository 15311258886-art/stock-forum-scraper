## D31 历史回放的前视偏差 + 一个更严重的正确性 bug：「前十大含机构 30 家」（2026-10-30）

本轮在 `viewer/predictor.py` 挖出**两个**独立问题，第二个比第一个严重：
- **问题①前视偏差**：`sig_holders(con, asof=None)` 的 `asof` 形参**从写下来那天起就没被函数体用过**
  —— 它全表扫 `stock_holders`，按 `d > a["date"]` 取每只票的**最新一期**。于是 `catch_up()` 里那句
  `generate(con, run_date=d)`（缺日补跑，逐日滚动回放）在回放 2017 年时，用的是
  **2026 年的十大流通股东名单**。同一次调用里 `sig_inst / sig_lhb / sig_extref / sig_ann /
  sig_policy / sig_board / sig_overseas / sig_desk` 全都传了 `asof=td`，只有 `holders`
  漏了 —— 是遗漏，不是设计。
- **问题②跨期累加（主结论，数据正确性）**：同一段代码的"取最新一期"逻辑是**行序依赖**的，
  线上一直在算错值，见第二节。**它比前视更需要优先修**：前视只影响历史回放的可信度，
  累加则让**今天的实盘读数也是错的**。

> **本节所有计数都是 2026-10-30 12:00 前后的只读快照，不是恒定值。**
> 公告回补进程（PID 40428）正在写 `viewer/app.db`，`stock_ann` 行数持续增长。
> 涉及 `stock_holders` 的数字（5057 只 / 池 400）不受回补影响（回补写的是公告表）；
> 涉及 `stock_ann` 计数的地方（D30 的 g/total）会漂移，那里已改成"时间戳 + 复现命令"。

### 一、改了什么（`viewer/predictor.py`，共 5 处）
1. `sig_holders(con, asof=None)`：`asof` 非空时只认 `end_date <= asof` 的报告期，再在其中
   取最新一期；`asof` 为空时**与改前完全一致**。后半段「股东户数环比」用的
   `stock_holder_num` **也有 `end_date`**（1994-12-31~2026-10-26），同口径过滤 ——
   只过滤前十大不过滤户数，等于前视从大门赶进小门。
2. 调用点 `holders_raw = sig_holders(con)` → `sig_holders(con, asof=td)`
   （`td` 是同一次 `_generate_inner` 的预测基准日，与相邻 8 行同一变量，未另造）。
3. `sig_desk`：`desk_snapshot_date(con)` 抽出 + `asof` 早于快照日 → 返回 `{}`（不可用）。
4. `_note` 追加一句不可用原因（run note 是代码里 1.5 段已写明的"如实标注"位置）。
5. 第 1 项那条 SQL 的 `ORDER BY` 末尾追加 `CASE scope WHEN 'free' THEN 0 ELSE 1 END`
   —— 去重键内部的第二层行序歧义（free/total 两行谁在前），见二之三。
   **只是一行 ORDER BY，不改口径**：实测与改前读数差 **0 只**。

### 二、主结论②：`sig_holders` 的聚合是「行序依赖」的 —— 线上一直在算错值
改前那段循环只有 `if d > a["date"]: a.clear()`，**没有"更旧就跳过"的分支，也没有 ORDER BY**。
所以只要旧报告期的行排在新报告期之后，老期的前十大会被**累加进最新期**：

| 同一份数据、只换行序 | 000001 读数 |
|---|---|
| 无 ORDER BY（= 改前真实查询计划） | 前十大含机构 **30 家** / 合计持股 **195.6%** |
| `ORDER BY end_date ASC` | 前十大含机构 **10 家** / 合计持股 **66.7%** |

**这不是个别票**。用两条物理不变量直接数（`org_n <= 10`：前十大只有 10 个名额；
`ratio <= 100.0`：前十合计占比不可能超 100%），全表 5057 只：

| | org_n > 10 的票 | ratio > 100% 的票 | 两条至少破一条（并集） |
|---|---|---|---|
| 改前 | **3977 只（78.6%）** | **2429 只（48.0%）** | **4172 只（82.50%）** |
| 改后 | **0** | **0** | **0** |

**「变化率」不是「错误率」，引错场景会得出"97% 的票是错的"**：
改前 ↔ 改后读数发生变化的票是 **4910 只（97.1%）**，但其中 **738 只**（4910 − 4172）只是
数值变了、两条不变量都没破（跨期混进了一部分，但机构家数恰好没超 10、占比恰好没超 100%）。
可证伪的错误数是 **4172 / 5057 = 82.5%**；97.1% 回答的是"这次改动动了多少票"。
两个数都要保留，但必须标清哪个是哪个 —— 见 D31 复盘（QA 指出此处初版把变化率写成了错误率）。

根因是 SQLite 无 ORDER BY 时行序由查询计划决定：**我只是加了一个 WHERE，4911 只票的读数就变了**
—— 这说明"改前的输出"本身不是一个稳定基线，而是"当前这台机器这次查询计划给的数"。

处置：加显式 `ORDER BY symbol, end_date`。这不是改设计，而是让代码**自己注释里写的口径**
（"去重后再取最新一期末"）真正可复现。不加，则 PIT 过滤的结果取决于 SQLite 版本/索引/计划，
"回放可复现"这个前提不成立 —— 前视修了也白修。

**两条不变量已写成断言永久锁死**（`tests/test_predictor_pit.py`）：
`test_invariant_org_count_never_exceeds_top10_slots` / `test_invariant_hold_ratio_never_exceeds_100_percent`
按**最坏行序**（end_date 降序插入）造数据，旧实现会给出 `org_n=30 / ratio=270%` → 必红；
`test_prod_invariants_hold_for_whole_table` 在生产库全表上再跑一遍（只读）。
断言比注释有效：注释会被后来的人"优化"掉，断言不会。

### 二之二、这个正确性 bug 对**选股**的实际影响（排序/档位，不是 Δscore）

—— 即约五分之一的相邻名次厚度小于这一路自己能造成的位移，处在"可能互换"的区间。

  改前：不加 ORDER BY（= 当时的查询计划）
  改后：ORDER BY symbol, end_date, holder_rank, CASE scope WHEN 'free' THEN 0 ELSE 1 END

### 二之三、第二层行序歧义：`free` / `total` 两行谁在前（同一个去重键内部）

第二节修的是**跨期**行序（`end_date` 方向错 → 老期累加进新期）。还有**第二层**同样的病：
去重键是 `(symbol, end_date, holder_rank)`，而同一只票同一期同一名次会有 **两行** ——
`scope='free'`（十大流通股东）与 `scope='total'`（十大股东）—— 循环里 `if key in seen: continue`
只留**先出现的那一行**。谁在前，`org_n` / `ratio` 就不是同一个数：

| 实测（`stock_holders` 全表） | 数量 |
|---|---|
| 两组都有的组（free,total） | 144,456 |
| **只有 `total` 的组** | **9,690** |
| 只有 `free` 的组 | 9,236 |
| 两行 `is_org` 不一致的组 | **15,569** |
| 两行 `hold_ratio` 差 >0.01 的组 | **38,431** |

**现状"恰好 free 在前"是运气，不是设计**：`UNIQUE(symbol, end_date, holder_rank, scope)` 的
自动索引里 `'free' < 'total'`，所以当前查询计划把 free 排在前。换插入序、换 SQLite 版本、
加减一个 WHERE，就可能翻面 —— 那是 **800 只票的 `org_n` 静默 ±1、4702 只票的 `ratio` 变化**，
而且没人会发现。故把 scope 显式写进 ORDER BY 钉死（不是改设计，是让"选谁"可复现）。

**选 `free` 优先，且拒绝 `AND scope='free'` 过滤**：
1. 语义上这一路本来就是"前十大**流通**股东里的机构"，`hold_ratio` 也是该 scope 的比例；
   切到 `total` 是**另一个决策**（影响 4,702 只票），不该藏在修 bug 里顺手做。
2. **不能 WHERE 过滤**：有 9,690 组**只有 total 行**，过滤会把这些组静默丢掉（实测 348 只票的
   读数会变）。故"free 优先、缺失回落 total"。
3. 副作用必须说清：正因为有 9,690 组回落 total，`ratio` **不是严格单一口径**。
   这是既有数据现实，本轮只保证"选谁可复现"，不假装它已经是纯流通口径。

**自证（要求"差异必须为 0，否则立即停"）**：同一份数据跑四种 tie-break，与"无 tie-break"
（= 改前那套运气行为）逐票对比 `org_n` + `ratio`：

| tie-break 方案 | 与"无 tie-break"读数不同的票数 |
|---|---|
| `CASE scope WHEN 'free' THEN 0 ELSE 1 END`（**采用**） | **0** OK |
| `CASE scope WHEN 'total' THEN 0 ELSE 1 END` | 4702 |
| `AND scope='free'` 过滤 | 348（且 9,690 组消失） |
| 不加 tie-break | —（基准，行序由查询计划决定） |

**0 差异 = 当前行为确实是 free 优先**：本轮只把它从"运气"变成"契约"，实盘读数一个都没动。
若哪天这个数不是 0，说明索引/查询计划变了，必须回来查 —— 这条已写进 `sig_holders` 的代码注释。

### 三、只能做到「近似 PIT」，这个缺口必须写在明处
`stock_holders` 有 `end_date`（报告期截止）/ `notice_date` / `disclose_at`（公告可得日），
但 **`disclose_at` 只有 2026-01-14 之后的行有值**（15.37 万 / 30.77 万，2026 年前为 0）。
没有公告日就无法按"那一天市场是否已经知道"过滤，只能拿**报告期截止日**当已知时点。
真实世界财报滞后 1~4 个月公告，所以 asof 落在「报告期已截止、公告尚未发」的窗口里时，
本函数仍会用到当时还不知道的数据 —— **残留的二阶前视，量级远小于改前**（改前连报告期都不看）。
待 `disclose_at` 回补到位，把条件换成 `COALESCE(disclose_at, end_date) <= asof` 即收敛为严格 PIT。
**不许把它当成严格 PIT 引用**（写进 docstring 与本节）。

### 四、`sig_desk` 为什么只能「标记不可用」，不能回溯
`stock_desk` 是 `watchdesk` 每次扫描**全量重写**的快照表：227 行、无历史版本，
`scan_at` 只覆盖两个时点（2026-10-14 4 行 / 2026-10-30 223 行）。没有历史 = 无法重建当期结论，
所以回放历史日时它只能整路判不可用（返回 `{}`，沿用"这一路没数据"的既有缺失语义，
不新造"不可用"标记），并把原因写进 run note。为它造一套"从 K 线反推盯盘结论"是另一个项目，
本轮不做，也不假装做了。

判据用 `快照日 > asof`（有未来数据才算前视），**不是** `快照日 != asof`：
后者会让实盘当天也被判不可用（因为那 4 行 10-14 的旧行），等于用修前视把实盘砸了。

### 五、实盘零影响：自证方法与结论（以及为什么字面做不到）
方法：改动前后各跑一次 `_pit_dump.py`（只读），对 `asof ∈ {None, 今天, 昨天, 2020-06-30,
2017-06-30}` 逐字段 diff `sig_holders` / `sig_desk` 的完整输出。

| 对象 | asof | 改前 | 改后 | lost / gain | 值变 |
|---|---|---|---|---|---|
| holders | None | 5057 | 5057 | 0 / 0 | **4910** |
| holders | 2026-10-30 | 5057 | 5057 | 0 / 0 | 4911 |
| holders | 2026-10-29 | 5057 | 5057 | 0 / 0 | 4911 |
| holders | 2020-06-30 | 5057 | **1** | 5056 / 0 | 1 |
| holders | 2017-06-30 | 5057 | **1** | 5056 / 0 | 1 |
| desk | None / 2026-10-30 | 57 | 57 | **0 / 0** | **0** |
| desk | 2026-10-29 及更早 | 57 | **0** | 57 / 0 | 0 |

**结论要说清楚**：
- `sig_desk` 做到了逐字段零影响（实盘 asof=今天：57 只、0 处变化）。
- `sig_holders` 做不到，因为**改前的值是错的**（见第二节）。"零影响"只能靠保留 bug 才成立。
- **没有一条读数变坏，变的是变对了。**

**聚合层（两个可复现人口，口径见二之二）**：

| 人口 | n | \|Δpct\| 均值 | 中位 | 最大 | strength 中位（改前→改后） |
|---|---|---|---|---|---|
| 全表 | 5057 | 5.64 个百分点 | 2.97 | 95.7 | 94.2 → 30.2 |
| `prediction_item` distinct symbol | 86 | 6.05 个百分点 | 2.81 | 51.0 | 111.7 → 38.8 |

（`Δpct` 在 0~1 与 0~100 两种记法里混过：**6.05 个百分点 = 0.0605**。
QA 独立复算给的是 0.083 / 117.9→42.6；我复现不出同一数值，试了四种 pct 分母
（5057 / 86 / `universe(400)` / `universe(2000)`）得 0.0605 / 0.0722 / 0.0938 / 0.0667，
**strength 中位一律落在 34~39、"跌约 2/3" 这个结论跨口径稳健，但小数不能跨口径引用**。）

**综合分层**：`Δscore = w_holders × |Δpct| = 0.0898 × 0.0605 ≈ 0.0054`（推导值；
早期一次性脚本实测 −0.0052，同量级，脚本已删故以推导为准）。
**别拿 Δscore 小当"没影响"** —— 见二之二那张表。


### 六、量化影响：回放早于 2025-12 时，这一路会整路消失
库内股东数据只有近 3~4 期（`end_date <= 2025-09-30` 只有 **1 只**票；`<= 2025-12-31` 969 只；
`<= 2026-09-30` 5057 只）。所以修好之后：

| asof | 改前"可用" | 改后 `sig_holders()` 返回 | 池内(400)命中 |
|---|---|---|---|
| 2017-06-30 / 2020-06-30 / 2024-06-30 | 5057（假） | 1 | 0 |
| 2025-12-31 | 5057（假） | 963 | 98 |
| 2026-03-31 | 5057（假） | 4511 | 341 |
| 2026-06-30 | 5057（假） | 5004 | 390 |
| 2026-09-30 | 5057 | 5057 | 400 |

**两个口径别混着引用（969 vs 963、4549 vs 4511 是同一件事的两种数法）**：
- 表中"改后返回"是 `sig_holders()` **真正返回**的票数 —— 已过末尾那条
  `ratio<1 且无增减持 且户数只有一期 → 不占名额` 的规则；
- 正文/表头的 **969 只 / 4549 只**是**原始有报告期的票数**（`select count(distinct symbol)
  from stock_holders where end_date <= ?`）。差额 **6 只 / 38 只** 就是被那条规则筛掉的。
  → 引用"能不能回放"用 963/4511；引用"数据覆盖到哪"用 969/4549。
- "池内(400)"明确 = `strategy_sim.universe(400)` 与 `sig_holders()` 返回集的交集。
  **这是唯一一个会随行情漂的量**（universe 按当日数据算），已按 D30 规矩标在这里；
  隔天复现若差几只属正常，不要当回归。

含义：**2025 年以前的回放里，"机构结构"这一路本来就该是空的**，改前那 5057 只全是拿 2026 年的
名单编出来的。

**那么 0.45 这个先验是不是被污染样本带下来的？——「很可能，但未证实」**
（初版写成"旧命中率是污染样本算出来的"，被 QA 的反证推翻，已降级：
`corr(旧 pct, hit_t1) = +0.018`、`corr(新 pct, hit_t1) = +0.014`，我按 `run_date` 逐日复算
337 条独立得到 **+0.0176 / +0.0141**，与 QA 一致 —— 即 pct 与 T1 命中**基本没有关系**，
污染并没有"造出一个显著的假信号"）。
事实部分只有两条能站住：
1. `predictor.SIGNAL_META` 里 holders 的 `prior` 在 2026-10-11 由 1.05 → 0.45，
   用的是含 holders 的 **362 条**历史 item（T1 命中 150/337=44.5%、T3 121/297=40.7%）；
2. 那 362 条 item 的 holders 读数**带着第二节的累加错值**（错值率 82.5%），所以这批样本是脏的。
**推不出来的**：脏样本把 0.45 拉高了多少、拉低了多少。诚实的结论是
**"0.45 不可信，但用这批样本也估不出偏多少"**；要估只能拿新逻辑重跑那 19 天（写库，本轮不做，
见第九节）。另外：这里的 0.45 是 `predictor.SIGNAL_META` 的 `prior` 字段，
**`selfpick` 没有 holders 维度**（它走 `evolve.DIMS = blogger/strategy/senti/engine`），
两个模块别混。

**复现命令**：
```text
相关系数：prediction_item 里 hit_signals 含 key='holders' 的 362 条 → 取 hit_t1 非空的 337 条
  旧pct = 该 item 里存的 pct   新pct = 用 asof=run_date 重算 sig_holders 后的百分位
  两者分别与 hit_t1 求 Pearson
```

本轮仓库内的回放窗口是 2026-09-28~2026-10-29（19 天），`asof` 都落在 400/400 可用区，
因此这批历史读数只是"值变对了"，不会"整路消失"。

**权重不会因此整体缩水吗？** 不会缩水的说法在这里不成立，但也不必救：
`predictor` **没有** D28② 那套 `dims=None + coverage 重归一化`（那套在 `selfpick.py`）；
它用的是「每路信号内部先按池内百分位归一（`_pct_le`）→ 乘权重 → 累加」。
所以缺一路的后果是"所有票少掉这一路的贡献"，而不是"全池等比缩水"（`w×p` 与票有关）。
更关键的是选股只数由 `_band_counts()` 按**当日分数分位带**决定（CORE_PCT/WATCH_PCT），
绝对分数不参与切分，所以核心/观察的只数不受影响。**故意不加全局重归一化**：
那会改动每一次打分的绝对值，且与本轮"修前视"无关，属另一个决策。

### 七、⚠ 修了代码 ≠ 修了权重：当前生效的 holders 权重仍是脏样本学出来的

> **当前生效的 holders 权重 0.0898 仍是用污染样本学出来的，修代码不等于修权重。**

事实（只读查询 `predictor_score where kind='signal'`，2026-10-30 12:20 快照）：

| signal_key | weight | updated_at |
|---|---|---|
| **holders** | **0.089837…（= 0.0898）** | **2026-10-30 05:47:30** |
| tech / extref / ann / desk / inst / policy / board / overseas / lhb | 0.0915 / 0.0246 / 0.1291 / 0.1154 / 0.1341 / 0.1290 / 0.1067 / 0.0849 / 0.0948 | 同上一行同一时刻 |

**为什么说它还是脏的**：这版权重是 `rescore()` 在 **2026-10-30 05:47:30** 学出来的，
而本轮代码修复是 **12:00 前后**才改完 —— 也就是说它**恰好是用改前那批样本学的**
（库里那 19 个交易日、含 holders 的 362 条 item，holders 读数由旧逻辑生成，82.5% 的票读数是错的）。
所以本轮修的是**未来生成逻辑**，不是**已学到的权重**。

**这意味着什么（别误解成本轮无效）**：
- 从下一次 `rescore()` 起，只要新样本是老逻辑生成的，权重就继续被脏数据牵引；
  真正干净要等"新逻辑重跑那 19 天"或"新逻辑积够新样本"（写库操作，本轮不做，见第九节）。
- 在那之前，`p` 已经修对了、`w` 还是脏的 —— 两者叠加的分数**比改前更接近真实，但不能说已校准**。
- 用户侧可见的唯一变化：分数绝对值会变（因为 `p` 变了），核心/观察只数不变
  （`_band_counts()` 按分位带切，见第六节末）。

**所以本节标题是结论、不是提醒**：任何"holders 权重已经修好"的说法都是错的，
除非 `predictor_score.updated_at` 晚于"用新逻辑重跑样本"的时间点。

### 八、数据质量待办（本轮**只记录，不清洗**）
`stock_holders` 里有两个非季末的"报告期"：

| end_date | 票 | 行数 | 异常 |
|---|---|---|---|
| 2026-11-02（周一） | 300327 中颖电子 | 10 | 不是季末，且晚于当日 |
| 2026-11-03（周二） | 002108 沧州明珠 | 10 | 同上 |

共 **2 只票 / 20 行**。怀疑成因：采集端把**公告/预约披露日**写进了 `end_date`
（真实报告期只会是 03-31 / 06-30 / 09-30 / 12-31，且 `notice_date` 这两组为空）。
**本轮不动数据**，理由有两条：① 现在是回补运行期，写历史表要单独的数据决策；
② 改了历史行不解决复发 —— 这是上游写入逻辑的问题，得连着采集端一起改。
短期影响：`asof=今天` 时这 20 行被 `end_date <= asof` 挡掉（它们本来就不该被当成已知），
正好是 PIT 过滤的正面副作用。
