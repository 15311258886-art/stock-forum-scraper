## D72 · 日更改「逐只打新浪」为「一次请求拿全市场」；卡顿改由预热解决（2026-11-03）

**来由**：进哥两条抱怨 —— ① 打开应用 / 切页经常卡、要等；② 日更抓取很慢。

**先定位，再动手（这一步比改动本身重要）**

逐个接口实测（缓存命中时全是毫秒级）：`/api/dashboard` 0.006s、`/api/universe_box` 0.019s、
最慢的 `/api/watchdesk` 2.56s。**所以卡顿不在接口。** 真正的两处：

| | 现象 | 证据 |
|---|---|---|
| A | **冷缓存现算** | 重面板走 `_variant_cached`（server.py:12373），首次进入要现算：低位箱体 **33s**、换手率榜 **14s**、中线箱体 **7~8s**、toolbox funnel 同类 |
| B | **日更链太长** | `/api/health` 的 `jobs.jobs` 里 27 个任务 `last_elapsed` 合计 **12,577.9 秒 ≈ 3.5 小时**；最重五个：`kline_daily` **3362.8s**、`indicators_daily` 2987.3s、`kbase_daily` **1886.8s**、`pillars_daily` 1529.0s、`predictor_daily` 971.4s |

B 里两个**抓取**任务（合计 87 分钟）的形状是「一只票一个 HTTP」：`kline_daily` 走
`build_kline_db._fetch_one()` 逐只调 `viewer.server.api_kline()`（新浪），`kbase_daily` 走
`kbase.incremental_update(datalen=10000, workers=2)` 逐只打新浪 —— 各 5550 次请求，
且新浪限流敏感、workers 只能压到 2。**慢不在网络，在这个形状。**

**改前 / 改后**

| | 改前 | 改后 |
|---|---|---|
| 抓全市场当日一根 | 5550 次 HTTP（新浪），`kline_daily` **3362.8s** | 1 次 HTTP（通达信盘后包 2,759,837 字节），实测 **9.3~9.7s** 下载 + 解析 |
| 写 `data/kline_daily.db` | 全量重算复权后重写（走同一份 5550 次请求） | 直接 `INSERT OR IGNORE` 当日一根；**只有当日除权的票**（实测 3~4 只）才走原 `_fetch_one()` 全量重抓 |
| 写 `viewer/kbase.db` | 逐只打新浪 hfq（`kbase_daily` **1886.8s**） | 本地两库取比值换算，**0 次请求**，0.5s |
| 冷缓存重面板 | 首次进入现算 33s / 14s / 8s | 抓完顺手 `_variant_cached` 打四张请求单预热；实测四面板 **0.010~0.088s** |
| 前端 | 无手动触发入口 | 顶栏新增「一键抓取」`#btnFastGrab`，POST 后每 1s 轮询 |

**为什么改（不是"为了快"这种空话）**

- 87 分钟里真正的计算量很小，绝大部分是**请求数**。请求数是形状问题，换个源就消失。
- 卡顿的成因是"用户在等一次 33 秒的现算"，而不是数据不新。**光把数据抓快、不预热面板，
  用户体感一点不变** —— 所以第 4 步（抓完预热四个重面板）和抓取本身同等重要。

**关键实现口径（每条都是从字节/实测反推出来的，不是猜的）**

1. **盘后包格式**：zip 内 `sh261102.cod`(定长 **150B**/只) + `sh261102.md1`(定长 **512B**/只)，
   两侧**条数必须相等且同序**，否则按位取值会整体错位（把 A 的收盘价写成 B 的），必须硬失败。
   `.md1` 用到的偏移（全部 little-endian）：`4` 昨收(double)、`12` 开、`20` 高、`28` 低、
   `36` 收（都是 double）、`56` 成交量(**int32，单位：股**)、`72` 成交额(**double，单位：元**)。
   ⚠️ **不是**通达信老日线那种「32 字节/天、日期在前」的格式 —— 按 32 切会解出 474,592 条垃圾；
   而且 14,226,944 也能被 32 整除，「字节数能整除」不能当格式正确的证据。
2. **跨市场撞号必须按交易所去重**：三个市场合计 10,473 条有价记录，但 `000001` 在沪（上证指数）
   与深（平安银行）各出现一次。不去重时对账拿 **3638.03** 去比 **11.54**，看起来像"大面积单位错"，
   还会凭空多出 **1,242** 条"库里没有的票"。判据用 `security_master.exchange_of()`，
   不写「sh 的 00 开头是指数」这种特例表。
3. **成交量单位只能让数据自证**：腾讯 `f[36]` 对绝大多数标的是「手」，**科创板 688/689 是「股」**
   （2026-11-03 实测：688111 原始 5,888,662 == 库内 5,888,662；600519 原始 74,121 → ×100 ≈ 库内 7,412,056；
   北交所 920001 也是手）。所以复用 `viewer.units.infer_volume_unit()`（amount÷close÷volume≈1→股、
   ≈100→手），判不出返回 `None` 并显式降级，**绝不回退成某个默认倍数**。
4. **前复权库的三条铁律**：
   - 前复权锚定最新价 →「包里的今日原始价 == 今日前复权价」**只在当日没有新除权时成立**；
   - `adjust_cache.json` 里 `ex_date == 当日` 的票**必须**走原 `_fetch_one()` 全量重抓。
     实测一天只有 **3~4 只**（2026-11-03：4 只 `000788/300735/605179/605300`；2026-11-02：3 只
     `001393/301536/688548`）。直接追加原始价会把这只票的历史价位**永久错位且不报错**；
   - 对账要用「**target 之后**发生除权」的集合，不是「target 当天除权」的集合。第一版用错了尺子，
     把 4 只正常除权的票报成 `value_diff`，等于用错的尺子量出"大面积不一致"。
5. **后复权库用比值搬**：`今日 hfq = 今日原始价 × (该票最近共同交易日的 hfq / qfq)`，两个数都从本地
   两库读、**不联网**。实测该比值 5,150/5,154 只恰好 = 1.0（两个库都是"锚定最新价"口径），
   只有当天除权的 4 只 ≠ 1（如 300735 = 1.005884）。取不到比值的票**跳过并计数**，不拿 1.0 顶上。
6. **降级（进哥已确认选 A）**：包没发布时**不报错退出**，改为只抓腾讯全市场快照，
   摘要标 `degraded: true / reason: 日线包未发布，已用快照顶上`，落 `viewer/app.db.stock_daily_snapshot`
   （口径照 `tools/fetch_a_shares_tencent.py`：复用其 `_ensure_schema`、会话日校验、`no_trade` 剔除）。
   ⚠️ **降级模式不写 kline/kbase**：腾讯量按百股截断（600519 实测 7,412,100 vs 精确 7,412,056），
   而 kline 是 `INSERT OR IGNORE` —— 一旦用近似值占了位，晚上真包就补不回精确值了。
   **宁可少一根 K 线，也不要一根永久偏小的量。**

**硬约束（无法用代码绕过，必须写在这里）**

- 通达信盘后包**不是收盘就有**：实测 `20261102` → HTTP 200 / 2,759,837B / 9.3s；`20261103`（当天）

**刻意不做的事 / 已知偏差**

- **按钮文案用的是后端真实步骤名（`抓取中 n/5 · 取数`），不是需求里写的「快照/日线/指标/预热」四段。**
  原因：本端点**不跑指标层** —— `indicators_daily` 实测 2987s（≈50 分钟），压在一个 UI 按钮后面
  等于卡 50 分钟；指标层由调度任务 `fast_daily` 负责。为了对齐四段制而谎报一个"指标"阶段，
  比少显示一段更坏。`fast_daily`（调度）确实按需求串了 `indicators_daily`。
- 没给 `data/kline_daily.db` 加 `amount` 列。对账的 amount 走 `app.db` 快照同日比对；
  加列会动现网表结构，超出本次范围。
- 降级模式不写 `a_shares_universe` / `stock_names`（那两张表的合并有别的脚本参与，
  顺手 UPDATE 会覆盖它们的成果）；快照只写 `stock_daily_snapshot`，并与现有 `a_shares_snapshot`
  任务用同一套 `_ensure_schema` + 同一套 `no_trade` 剔除规则。
- `fast_daily` 里指标层失败**不回滚** K 线（K 线是主产物），但返回 `ok:false` + 原因，
  交给父进程退避重试。

**推翻条件**

- 若某天对账的 `mismatch`（真不一致）> 0 且不能归因到除权/取整 → 停用 `fast_grab` 写库，
  先查清单位/复权口径再说；`--dry-run` 是默认值就是为了让这件事先暴露在纸上。
- 若通达信改包格式 / 停发 `g4day`（连续 5 个交易日 404 而腾讯通道正常）→ `fast_daily`
  会长期停在降级态（只写快照、不写 K 线），两条 K 线库会重新依赖老的 `kline_daily`/`kbase_daily`，
  此时必须改回逐只抓或换源；
- 若 `TDX_MARKET_MIN_PRICED` 阈值把正常日误判成"有价记录过少"（实测正常日 sh 5,095 / sz 5,022 / bj 356，
  阈值 3,000/3,000/50）；一旦出现误判，说明该阈值套错了对象，要重新从当日实测校准。

# D-20261104-board：四家专家团「今日荐股 · 合并榜」（自评 0-100，≥85 依次列出）

**进哥原话**：① "里边还有一个未安装的，先把这个该安装的安装了，并进到每日定时任务，四家拿同一份数据一起跑，定时任务设成一个" ② "他们推荐的个股都有哪些…每天 5 到 10 只、十几只也行，写上推荐理由，按自己的理解给每只票推荐值满分 100、最低 0，85 分以上的依次列出来，点开个股也能简单看到推荐理由"。

## 一、决定与理由

### 1. 分数不统一刻度，只做归一化 + 一条硬线

四家的方法论本来不同（趋势/估值/资金/浪型）。**强行拉到一个刻度，等于把"专家"变成同一套指标换个名字**——那就没必要请四家。
所以：分数由各家按自己体系打（`score_note` 一句话说明口径），我们只把 `"85分" / 85.0 / "约 88"` 归一成整数（`_norm_score`），
并把 ≥85 定义为"这家认为现在可以下单"。**85 这条线是硬的**：不足 5 只时用次高分补足到 5 只，但标 `[观察]`、`strong=False`、分数照实显示——
不把 80 分的票伪装成 85 分，否则这条线就没意义了。

- 只收"买/持"方向：`规避/回避/不参与/不做/减仓/清仓/卖出/观望` 不进榜。它们有价值，但不是"推荐个股"，混进来会让人以为今天有 20 个机会。
- 只收 6 位真代码（点得开个股）；未装专家包、没打分的票，一律不进榜。
- 上限 15 条，但 `n_strong` 报**真实达标数**（截断不许少报机会）。

### 2. 榜单在后端算一次，前端只画

`AX.build_board()` 一处实现，`/api/ai_expert` 直接回 `board`。
前端再算一遍迟早与接口不一致，而这张榜以后「今日看板」和每日汇报都要用（`expert_desk.py --board` 走同一函数）——
规则只能有一份。

### 3. 点代码开个股时，理由贴抽屉**顶部**，不走 `openStock` 的 `extraHtml`

`extraHtml` 插在抽屉最底部（K 线、持仓选手之后），是给"共同持仓/共识"这类补充信息用的。
进哥要的是"点开就看得到理由"，贴到几屏之后等于没贴。改为开完抽屉后把 `.aie-dr` 插到跳转 chips 之后、股票代码之前。
同码多家共推时全部列出（分数高的在前），并显示「N 家共推」——共振本身就是信息。

### 4. 定时任务：一份数据、四家同跑、只用一个任务

保持单一自动化（04:00），prompt 里把三件事写死：① 四家**只取一次** `--brief`，分析的是同一个 `brief_<D>.md`；
② 只有 `exists=false` 才跳过，且必须在汇报里点名，**不许编报告**；③ 落库后必须跑 `--board` 自检，
榜单为空/只有 1-2 只 → 只让那一家重写 picks（含 score）重新 `--save`，不整天重跑四家。

# D-20261105-basis：指标表复权口径：前复权（2026-11-05 定论）

**日期**：2026-11-05（同一天里 A→B→C 三次判断，前两次都被推翻）
**涉及**：`viewer/toolbox.py` 里 11 条 `oss_*` 工具的 `evidence` 尾句（常量 `_BASIS_TAIL`）

## 一、终版比对表（谁想知道指标表是什么口径，只看这张表）

261 日窗口（2025-09-30~2026-11-03）、**逐票全序列日收益**比对：

| 比对 | 可比票数 | 收益完全相等 | 最大单日偏差 |
|---|---|---|---|
| 指标表 vs `data/kline_daily.db`（前复权） | 120 | **119** | 0.917% |
| 指标表 vs `viewer/kbase.db`（标 hfq） | 112 | 65 | **28.58%** |

**结论：指标表存的是前复权**（与前复权库几乎逐日全等）；kbase 的 hfq 序列在**除权日**有缺口
（典型：605100 于 2026-05-25，前复权 +0.02%、kbase −28.56%，送股没打上复权因子）。

## 二、三个判断的来龙去脉（写下来是为了别再有人拿单日比值下结论）

**判断 A（team-lead）**：「差异是复权口径 —— 抽查 400 只票，393 只与前复权库误差 <0.1%，
7 只除权票在除权日附近最大偏差 4.8%。」
→ **方向基本对（指标表确实是前复权），但口径太糙**：400 只票、只看除权日附近、没有全序列比对；
而且这段话被写进了 11 张卡片的 `caveat`，**跟用户无关**，只会让他以为数据有问题。

**判断 B（QA）**：「两库同库同基准 —— 同日 `stock_indicators_daily.close ÷ kbase.kline.c`
在 4999 只票上 p1=p99=min=max=1.0000，即指标表也是后复权，**不存在复权差异**。」
→ **错，而且是最危险的一版**：前复权锚在最新日、后复权的基准在最早期，**两种口径的最后一根
K 线都等于原始成交价**，所以「最新一日两边相等」是**构造决定的**，必然通过、什么也验不出。
（`tools/audit_hfq_gap.py` 文档头把同一个坑写过一遍，我第一版也踩了。）

**判断 C（终版，全窗口日收益比对）**：见上表 —— 119/120 与前复权库全等；47/112 在除权日
对不上 kbase hfq，最大 28.6%。

## 三、结论（产品与回测各归各位）

- **卡片数字可信**：指标表是前复权，价格与涨跌幅都正确（前复权显示的就是用户看到的价）；
- **回测用 hfq 属正确选择**：算持有期收益必须用后复权（否则除权当天会出现假跌），
  两者不冲突 —— 一个负责「显示」，一个负责「算收益」。
- 这两件事**都不写进卡片**。卡片尾句只留口径差异、不给数字承诺（`_BASIS_TAIL`）：
  「卡片为 261 日窗口（2025-09-30~2026-11-03）、未扣 0.25% 成本；3 年复核扣成本并另剔次新，
  两处口径不同，数字不能直接相减。」
  —— 为什么不留具体数字：Step 6 正用前复权重建主表，3 年那几个数会变；把 -0.22%、0.15%、
  2035 只刻进 11 张卡片，主表一出来就得再改一遍。
- 11 条共用的公共说明（**来源 / 261 日窗口 / 未扣成本 / 数据源复权在少数除权日有机械缺口**）
  收进**抽屉面板底部一行**（`static/toolbox.js` 的 `BASIS_NOTE`，只在 `source_kind=github`
  的工具上出现），写一次而不是写 11 遍。
- 顺带纠正两条：`oss_shrink_vol` 的 -0.22% **不是**「扣成本扣出来的」（扣成本只解释 0.25pp，
  剩下 0.18pp 来自窗口与股票池）；`oss_high_vol` 是**反例**（5 日：卡片 -0.21% → 扣成本 -0.46%
  → 3 年 -0.36%，更长反而更不亏），**禁止**写「窗口拉长后一律更负」。

## 四、什么条件会被推翻

# D-20261105-cond 条件化回测：口径从「绝对超额」改为「池内区分力」

## 一、改了什么

新增 `tools/cond_box_backtest.py` + `tools/cond_box_market_base.py`，并确定一条**回测口径**
（不改产品代码，改的是以后所有工具怎么被评价）：

- 旧口径：`个股 H 日收益 − 同日全市场等权 − 0.25%` → 问「比随便买强吗」
- 新口径：`触发组 H 日收益 − 同池未触发组 H 日收益` → 问「在工具自己的适用条件内，它挑得准吗」
- 同一天、同一池、同一持有期，两组只差「触发/未触发」→ **天然风格中性**

## 二、为什么旧口径是错的（这次终于能拿出数证明）

旧口径下箱体类工具的「绝对超额」为负，我据此说过它不行。换成池内口径后，用 14.8 年、
103 万条样本测：

| 持有期 | 底部组 | 同池其余 | 差 | NW t | 非重叠 t |
|---|---|---|---|---|---|
| T+20 | +0.707% | +0.743% | −0.036pp | −0.14 | +0.66 |
| T+60 | +0.961% | +1.369% | −0.409pp | −0.58 | +0.39 |
| T+120 | +4.015% | +5.609% | −1.594pp | −0.88 | −0.86 |

**结论不是「箱体工具可用」，而是「给它的任务它没完成」**：`box_bottom` 默认 `pos_max=1.0`，
根本不筛底部；而真收紧到 `pos ≤ 1/3`，池内区分力为 0。两件事都比旧口径说得清楚。

## 三、由试点确定的三条规矩（写入 `docs/工具的适用条件与回测口径.md`）

1. **窗口跟着持有期走**：短线 1~5 日 → 2021 起；中线 5~60 日 → 2015 起；长线 60~120 日 → 2012 起。
   实测支撑：同一工具 T+120，3 年窗口给 **+1.894pp**，14.8 年窗口给 **−1.594pp**，**符号相反**。
2. **判据看非重叠抽样 t**，NW t 只作参考。实测 T+60 两者符号相反（−0.58 vs +0.39）。
3. **测法按角色分三种**：选股型测池内区分力、闸门型测「被剔掉的票是否真的更差」、
   排序型测分位单调性 + 头 20% vs 全池。

## 四、本轮修掉的三个 bug（都是静默的，不报错但结论全废）

1. `SELECT d, COUNT(*) c ... HAVING c>=3000` —— 别名 `c` 与 kline 的收盘价列同名，
   `HAVING` 优先解析成「收盘价 ≥3000 元」，**一个信号日都取不到**。
2. `COUNT>=3000` 绝对门槛在 2016 年前不可能满足（2010 年全市场 1953 只），
   实测把「2012 起」的窗口悄悄砍成「2017 起」。改相对门槛（≥前后 120 日最大票数的 60%）。
3. `sig_pos - 749` 在 `sig_pos<749` 时为负 → numpy 从末尾绕回，**用未来数据算箱体**。
   加 `pos_of[d] >= BOX_WIN-1` 剔除。

## 五、什么条件会被推翻

- 若把 `box_bottom` 的复合 score（pos/dwell/regular/touch 加权）按前 N 名重测，
  在 ≥2 个分段上得出非重叠 t > 2 且同号 → 池内区分力结论翻案。
- 若做风格中性化后，「池 vs 全市场」的 −3.875pp（T+120）大幅收敛 → 说明池子本身的问题
  是风格暴露而非选股，`box_bottom` 作为**前置池**仍可用（只是不能当触发）。
- 换数据源、换数据库前，先重跑 `tools/cond_box_backtest.py`，看信号日数量与日均池子是否稳定。

## D-20261105-audit 全线自审：宇宙污染 / 死任务 / 门禁空转（2026-11-05）

### ① 宇宙被新三板污染（P0，已修）

- **事实**：`tools/fetch_a_shares_snapshot.py` 的 `DEFAULT_FS` 里北交所子句写成

  `m:0+t:81` **total=6765（整个新三板）**，`m:0+t:81+s:2048` **total=364（真北交所）**。
  新三板与北交所代码段完全重叠（43/83/87/92），`units.stock_kind()` 只能看代码段，
  **判不出来** → 6464 只新三板被当股票写进 `stock_names` / `a_shares_universe`。
- **连锁**：`screener._market_pool()` 12030 只（应为 5927）→ `kline_daily` 逐只拉新浪，
  新三板无日线 → 5860 只硬失败 → 每轮判任务失败 → `health.level=degraded`
  （`任务连续失败：kline_daily`）→ 退避重试，单轮白烧 2171s，真正的日更被挤在后面。
- **修法（三层，缺一层都会复发）**：
  1. **源头**：`DEFAULT_FS` 的北交所子句补 `+s:2048`；
  2. **存量**：新增 `tools/purge_neq_universe.py`（默认 dry-run，`--apply` 才写，
     删前把待删行的完整内容导出 `data/purge_neq_<时间戳>.json` 可回滚）——
     只删「声称北交所但不在权威名单里」的行，权威名单三级降级
     （东财 `+s:2048` → `security_master.board='北交所'` → **拿不到就拒绝执行**，
     绝不允许拿空名单去删）；
  3. **兜底**：`viewer/localfeed.py::pool()` 名称表补码必须过 `security_master` 白名单。
     因为 `stock_names` 是采集管道的落地表，采集口径一错就直接变成全站口径错误。
- **实测**：`_market_pool()` 12030 → 6161；`kline_daily` 重跑
  `ok=True codes=6161 fail=11 hard_fail=0 205s rc=0`（修前 `codes=12030 fail=5877
  hard_fail=5860 2171s rc=1`）；`/api/health` 由 `degraded` 回 `fresh`。
- **推翻条件**：东财改了 `+s:2048` 的语义（届时 `m:0+t:81+s:2048` 的 total 会明显偏离 360 上下）。
  `tools/purge_neq_universe.py` 的权威名单拿到 <200 只时会自动降级，不会误删。

     「值得看」与「能买」不是同一件事。
  ④ **排除器不受行情/持有期约束**：`hard_guard`/`risk_guard` 与含 `exclude` 用途的工具跳过
     ⑤⑥ 两条。理由是风险与持有多久无关 —— 拿 120 天更该排除，不该因为「周期错配」放行。
  ⑤ **ABSTAIN 是一等结果**：没有合格的正向选择器时输出「今日弃权」并给出原因，
     不从反向工具里硬凑名单。弃权态下 `selected_chain` 必为空。
- **箱体语义（P0-04）**：`BOX_POS_MAX` 1.0 → **0.333**。位置 ≤1/3 才算箱底；
  超过 1/3 直接 `blocked`（理由写「> 1/3」）；箱底只输出 `watch`，不放宽成 buy。
  放宽时后端写告警 + 前端标「仅输出观察」，不允许悄悄放行。
- **失败语义（P1-02）**：`run_funnel()` / `run_stack()` 任一 step 硬错误 →
  `ok=false` / `final=null` / `aborted_at` / `reason`，不得再 `ok=true` 带个空结果。
- **实测（2026-11-06 当日数据，弱势下跌、20 日视角）**：33 个工具 →
  **4 个可买 / 18 个可决策 / 31 个可执行 / 2 个已淘汰**；路由输出 `ABSTAIN`，
  eligible 只剩 `gate_admit`/`avoid_c`/`oss_high_vol` 三个排除类。
  切 T+5 → `ACTIONABLE`，`selected_chain = gate_admit › reso_ab`。
  与审计预期一致（审计要求的正是「下跌 20 日应当弃权，而不是从反向工具里凑名单」）。
- **怎么验证**：`tests/test_tool_contract*.py`（契约 33 条 + 九条判定 + fail-closed）、
  `tests/test_tool_router*.py`（ABSTAIN/ACTIONABLE 两态、箱体三例：000008 22% → watch、
  000731 35% → blocked、600519 不在池 → blocked）、`pytest` 全量 694 passed。
- **推翻条件**：① 某个工具的重跑回测把 `validated_negative` 翻成正，且样本外仍成立 →
  改契约的 `evidence_state`，不改判定顺序；② 若把「排除器不受持有期限制」这条去掉，
  必须同时给出「长持有期下风险可忽略」的实证，否则不许改；③ 若将来做受约束元学习（T11），
  它只能调整 `selected_chain` 的**排序**，不得绕过 `evaluate()` 的硬否决 ——
  没有样本外支持不得上线（`policy_frozen=true` 就是这条的开关）。

## D-20261106-backtest T10 首批工具回测：方法与结论（2026-11-06）

> 审计 T10 要求「按行情/持有期/池内超额，至少 5 年、分 6 段、含成本」。
> 之前我把它判为"不可执行"，理由是 `tool_run_log` 只有 2 天 —— **那个判断是错的**：
> 工具是纯函数，只要历史 K 线在就能在历史截面上重跑，不需要回放日志。
> 数据在 `viewer/kbase.db`：1195 万行后复权日线，1990~2026，8760 个交易日，5813 只。

- **方法（三条防作弊，见 `tools/router_backtest.py` 头部）**：
  ① **时间之墙**：判据只拿 `bars[:D+1][-keep:]`，由 `window_at()` 单点控制；
     测试用"两条只在 D 之后不同的序列，D 日窗口必须逐字节相同"钉死（`tests/test_router_backtest.py`）。
  ② **同池基准**：超额 = 入选票 T+N 收益 − **同时点同池所有票**的 T+N 收益。
     不用指数当基准 —— 那会把"池子选得好"混进"工具选得好"。
  ③ **成本直扣**：13bp 双边（佣金 5 + 印花 5 + 滑点 3），不做含/不含两套结论。
- **实测（全市场 5008 只 × 239 截面 × 每 5 日，2021-11-08~2026-11-06，T+20）**：
  | 工具 | 超额 | t | 6 段方向 |
  |---|---|---|---|
  | `box_bottom` | +0.22pp | 1.35 | 前 3 段 +1.50/+0.63/+0.52（t=5.34/3.68/1.70），**后 3 段转负** |
  | `db_wave` | −0.66pp | **−5.02** | 5/6 段为负 |
  | `db_chan` | −0.56pp | **−2.81** | 5/6 段为负 |
  | `tv_wbottom` | −0.57pp | **−3.19** | 6/6 段为负 |
  | `tv_shrink_pull` | −0.61pp | −2.28 | 正负交替，不稳定 |
  | `tv_macd_div` | −0.28pp | −1.01 | 不稳定 |
  | `tv_platform` | −0.66pp | −1.49 | 入选率仅 0.3%，样本太少 |
- **结论（判据层面的三条）**：
  ① **箱底有时效性**：不是"永远没有 alpha"，而是"2021-2023 有、2024 之后没有"。
     与 14.8 年长样本的 −0.036pp 并不矛盾 —— 长样本把强弱两段平均掉了。
     保持 `watch_only` 结论不变，但卡片文案应写成"历史上曾经有效，最近两年失效"。
  ② `db_wave` / `db_chan` / `tv_wbottom`：分段稳定为负，够格判 `validated_negative`
     （**本轮只出结论，未写库** —— 改判据要单独走一次）。
  ③ `tv_shrink_pull` / `tv_macd_div` / `tv_platform`：不稳定/样本少，维持 `unvalidated`，
     不得因全期 t<−2 就判死（那是被其中两段拉动的）。
- **已知偏差（必须与结论一起读）**：
  ① **幸存者偏差**：kbase 只有现存票的历史。2021-2023 每年仅 2700~3200 只有数据
     （2024 起 5400+），那几段"池子平均"偏强 → **工具超额系统性偏负**。
     缓解办法：只看 2024 年后的段 —— `box_bottom`/`db_wave`/`db_chan`/`tv_wbottom` 仍为负，
     故方向稳健，但**幅度可能被高估**。
  ② `oss_*` 11 个工具受 `stock_indicators_daily` 限制只能回测 13 个月（45 截面），
     只作参考，不改判据（`tools/apply_backtest_verdict.py` 里 `min_sections=100` 强制这条）。
- **推翻条件**：① 换成行业/市值中性基准后，上述负超额消失 → 说明是风格错配而非工具失效，
  结论作废重算；② 补上退市票历史后重跑，偏差消失且结论反转 → 以上表作废。

## D-20261107-neutral 回测基准加规模中性：推翻 db_wave 的「反向」判决（2026-11-07）

> 承接 D-20261106-backtest。审计 T10 的「池内超额」只回答了「比池子平均好吗」，
> 但池子平均里混着规模风格 —— 工具若专挑某个规模档，而该档在这一段整体跑输，
> 超额就是风格给的，不是工具给的。少了这一层，「反向显著」可能是归因错误。

- **改前（问题形态）**：基准只有「同时点同池等权」。这导致 `db_wave` 被判成
  `validated_negative`（全池 -0.655pp / t=-5.02），但它的入选票规模分位是 **0.65（偏大盘）**——
  2021-2026 这段大盘整体跑输，它的负超额有相当部分来自这里。
- **改后（双口径基准）**：每个截面在原有全池基准之外，再按**当日成交额**分五档，
  算「与其所属规模档比」的超额（`excess_pp_liq` / `t_liq`）。
  - 为什么不用「总股本 × 收盘价」算市值：kbase 存**后复权**价，股本只有最新快照，
    两个近似叠加，误差方向不可控（历史分红多的票市值被高估）。
    而后复权是「价 × factor、量 ÷ factor」，`成交量 × 收盘价` 是**不变量**，
    等于当日真实成交额 —— 零外部数据、不受复权基准影响。
  - 因此这一层叫**规模/流动性中性**，不叫市值中性。结论里必须这么写。
- **实测（239 截面，2021-11-08~2026-11-06，T+20，13bp）**：
  | 工具 | 全池超额 | t | 同规模档超额 | t_liq | 中性化后分段 | 判决 |
  |---|---|---|---|---|---|---|
  | `tv_wbottom` | -0.572pp | -3.19 | **-0.540pp** | **-3.38** | 6/6 为负 | 反向成立 |
  | `db_chan` | -0.562pp | -2.81 | **-0.446pp** | **-2.59** | 5/6 为负 | 反向成立 |
  | `db_wave` | -0.655pp | -5.02 | -0.201pp | **-1.69** | 仅 4/6 | **推翻，回滚为 unvalidated** |
  - `db_wave` 的规模分位 0.65，剔除规模后 t 掉到不显著 —— **负超额是风格错配，不是工具失效**。
    已在 `tool_registry` 回滚（bt_verdict 清空），改动记在 `verdict_write_20261107_002633.json`。
  - `tv_wbottom` / `db_chan` 规模分位接近 0.50，剔除规模后反而更显著 —— 判据保留。
- **持有期对照（T+5，243 截面）**：`db_wave` -0.28pp/t=-3.75、`tv_wbottom` -0.24pp/t=-2.36、
  `db_chan` -0.25pp/t=-2.26，方向与 T+20 一致、幅度更小。
  说明是**持续跑输**而非短期噪声；`box_bottom` T+5 为 -0.01pp/t=-0.17，进一步支持「无 alpha」。
- **判据层面的新规则（写进 `apply_backtest_verdict.decide`）**：
  ① **双口径守卫**：判 `validated_negative` 必须「全池显著 **且** 同规模档也显著」。
     只有全池显著 → 返回 skip，理由写「负超额主要来自规模错配」。
  ② **分段一致性守卫**：6 段里至少 5 段同向（≥70%）才算稳定；4/6 不算。
     这条早一步把 `tv_shrink_pull`（-0.61pp/t=-2.28，但正负交替）挡在门外。
  ③ **降级必须显式**：`--allow-downgrade` 才能把旧结论降级，且需理由含「规模错配」。
     默认仍禁止降级 —— 防止短样本把长样本擦掉。
- **踩到的两个「假报工」（都已修，值得记）**：
  ① `UPDATE ... WHERE tool_key='factor:db_wave'` 命中 **0 行**，SQLite 不报错，
     脚本仍打印「已写入 3 个工具」。修法：归一化工具名 + `rowcount==0` 整批回滚。
  ② 落库写了英文枚举 `validated_negative`，而 `normalize_verdict()` 只认中文标签
     `B 否决·反向`，于是「写进去了但读不出来」，判定照旧。
     修法：落库统一写中文标签 + `normalize_verdict` 加英文枚举直通；
     顺带修了 `VERDICT_MAP` 里 `"A 采纳"` 缺失（只写了 `"D 采纳"`）的笔误。
- **推翻条件**：① 若能用带复权因子的历史股本算出真市值，就改回市值中性重跑，
  结论以新口径为准；② 若某工具在**行业中性**后也不显著，说明还有一层风格没摘，
  需补行业分类（当前 `plate_members` 只有 17 个精选主题，覆盖不全，做不了全市场行业中性）。

## D-20261107-pick pick_* 时点化：复用模板原文 SQL，不手抄阈值（2026-11-07）

  - 手抄阈值的版本一旦和线上漂移，回测测的就是另一个工具，而且**不会报任何错** ——
    所以这一条由测试守（`test_pick_specs_use_template_sql_not_handcopied`）。
  - `pick:quality_leaders` 依赖 `universe_scan` 质量分快照，无历史版本 → 仍然 refuse。

## D-20261107-t08 到期打分闭环：账本不再等一年（2026-11-07）

- **改前（问题形态）**：`tool_decision_log` / `tool_outcome` 建了表，但一条数据都没有。
  我之前把 T08 判成「时间不可压缩，要等决策之后 N 个交易日」—— **那也是偷懒**：
  线上决策确实要等，但**回测本身就在产出「哪天选了谁、之后 N 天赚了多少」**，
  直接落库即可，账本立刻有几万条样本。
- **改后**：`router_backtest.py --log-decisions` 把每个截面的入选明细写成
  `tool_decision_log`（一条决策）+ `tool_outcome`（每票一条到期结果），
  新增 `tools/score_ledger.py` 按 工具 × 持有期 出成绩单。
  - `status='BT'` 与线上真实决策严格分开：拿「事后算出来的决策」冒充「当时真的做的决定」
    会让账本失去全部意义。
  - `realized_date` 记**实际取到收益的那一天**（停牌/退市会偏移），不写推算值。
  - t 值**按决策日聚合**：同一天入选的 50 只票不是 50 个独立观测，
    按票堆样本会把 t 放大几倍，任何工具都能"显著"。
- **实测**：3 个工具 × 2 档持有期 × 2022-01~2026-11（step=10）
  → **716 条决策 / 248,879 条到期结果**，6 个组合全部为负：
  | 工具 | T+5 | T+20 |
  |---|---|---|
  | `db_wave` | -0.17pp / t=-1.57 | -0.67pp / **t=-3.51** |
  | `db_chan` | -0.47pp / **t=-3.16** | -0.73pp / t=-2.17 |
  | `tv_wbottom` | -0.42pp / **t=-2.82** | -0.73pp / **t=-2.82** |
  与回测结论互相印证（同一批决策，两条路径独立聚合）。
- **口径差别必须记住**：账本记的是**同池基准**，没有做规模中性。
  所以 `db_wave` 在账本里仍显示「显著为负」，但它在同规模档下不显著（见 D-20261107-neutral）。
  **判据以中性化后的结论为准**（unvalidated），账本只是"当时的决策事后赚没赚"的流水。
- **下一步（T11 的入口已开）**：账本现在能按（工具 × 持有期 × 决策日）出序列，
  前 4 年拟合、最后 1 年样本外的加权规则具备数据条件了。
  但 `policy_frozen=true` 仍然有效 —— 没有样本外支持不得上线。
