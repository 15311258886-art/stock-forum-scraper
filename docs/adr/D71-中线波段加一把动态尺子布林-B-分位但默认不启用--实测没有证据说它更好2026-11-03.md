## D71 · 中线波段加一把动态尺子（布林 %B 分位），但**默认不启用** —— 实测没有证据说它更好（2026-11-03）

这是《产品内核演进规程》第 3 节那张映射表里的**第一个落地动作**：把外部方法（FinRL 的
`boll_ub/boll_lb`，即动态箱体）灌进「中线波段」tab 的判据，而不是加进货架。

### 改前是什么

`viewer/universe_box.py` 里位置分只有一把尺 —— **静态箱体**：

- 箱体 = 近 `BOX_WIN = 750` 日（约 3 年）的 `max(high)` 与 `min(low)`，随日期滚动；
- `pos = (收盘 − box_low) / (box_high − box_low)`，`0` = 箱底、`1` = 箱顶；
- 位置分 `s_pos = clip(1 − pos / (1/3), 0, 1) × 100`，权重 `W_POS = 0.30`；
- 其余三维不动：驻留 `W_DWELL = 0.35`、规整 `W_REGULAR = 0.20`、触及 `W_TOUCH = 0.15`；
- 一级门槛 `PCT_MAX=30 / CV_MAX=40 / SLOPE_MAX=18 / MIN_AMOUNT_AVG=3e7`、二级门槛
  `min_dwell=0.15 / TOUCH_MIN=2`；
- `universe_box_hist` 只有 10 列，没有动态字段，也没有"这把尺是哪一把"的记录。

**已知的结构性缺陷**（`docs/产品内核演进.md` 第 1 节早已记录，不是这次才发现的）：
静态箱体的高低点是**历史极值**。一次极端行情把 `box_high` 拉上去之后，这只票此后的 `pos`
会长期贴着 0 —— 系统认为它"一直在箱底"，可它其实只是"比三年前那根天量 K 线低"。
箱体被永久拉宽 → 位置分失去区分度 → 名单很多天不变。这是机制问题，不是判据意图。

### 改后是什么

**并行加一把动态尺，与静态那套共存，谁也没被删掉。**

1. `scan_one()` 新增 5 个动态字段（与 `pos` / `pct750` 等**并列**，不是替换）：
   `boll_upper` / `boll_mid` / `boll_lower` / `boll_pctb` / `boll_bw` / `boll_pctb_rank`。
   - 布林 20 日 ±2σ，σ 用 `statistics.pstdev`（总体标准差，与本文件 `cv` 同口径）；
   - `boll_pctb = (close − lower) / (upper − lower)`，0 = 下轨、1 = 上轨；
   - `boll_bw = (upper − lower) / mid`，带宽（波动率收缩/扩张）；
   - `boll_pctb_rank` = 当前 `%B` 在**近 250 日** `%B` 序列中的百分位（0~100，越低越贴下轨）；
   - K 线不足 20 根、或 20 日一字横盘（σ=0 → 带宽 0）时这几个字段给 `None`，
     但**整只票不失效**：`score_one` 退回静态位置分并标 `pos_src="static_fallback"`。
2. `score_one(m, box_mode=None)` 支持三种模式，**只改位置分这一项**：
   | 模式 | 位置分算法 | 用途 |
   |---|---|---|
   | `static`（**默认**） | 原公式，一字未改 | 线上 |
   | `blend` | `(1 − W_POS_DYN) × 静态分 + W_POS_DYN × 动态分`，`W_POS_DYN = 0.5` | A/B |
   | `dyn` | 只用动态分位分 | A/B |
   动态分位分 = `(1 − boll_pctb_rank / 100) × 100`，即"越贴下轨越高"。
   **不套静态那套「下 1/3 封顶」**：1/3 是"谷底区"这个业务概念的定义，动态这边没有对应定义；
   而实测 IC 在截面上是单调的，线性铺满 0~100 能保住全部排序信息，也不会人为造一个饱和点。
3. 开关从环境变量 `UNIVERSE_BOX_MODE` 读，缺省 `static`；认不出的值（`blended` 之类）
   记一条 warning 后按 `static` 跑 —— 写错一个字母不该让整张中线表静默换尺。
4. `payload.params` 增加 `box_mode` / `boll_win` / `boll_k` / `boll_rank_win` / `w_pos_dyn`，
   并在 `delta.note` 里写明"与上一交易日对比（xx 标尺）"。**排查时最怕分数变了却不知道换了什么。**
5. `universe_box_hist` 加 `boll_pctb` / `box_mode` 两列。老库走 `ALTER TABLE` 补列
   （项目里已有 `toolbox.py :: _add_col_if_missing` 的写法，`CREATE TABLE IF NOT EXISTS`
   对已存在的表是空操作，不加这步新列只会在全新机器上存在）。
6. **必须处理的坑（这次唯一的真实故障模式）**：`_attach_delta()` 原来无条件跟"上一交易日"
   比分数。切换模式后分数水平会整段平移，跨模式相减 = 用户看到"全表突然集体涨/跌了几分"，
   而真实行情一动不动 —— **这是假跳变**。现在只跟**同 `box_mode`** 的历史比，
   老数据（2026-11-03 之前写入、`box_mode` 为 NULL/空串）一律按 `static` 认。
   `history()` 同理，避免把两种尺算出来的分数连成一条"看起来在涨"的折线。

**没动的东西（硬纪律，逐条核对过）**：`W_POS/W_DWELL/W_REGULAR/W_TOUCH` 数值、
`min_dwell/TOUCH_MIN/PCT_MAX/CV_MAX/SLOPE_MAX/MIN_AMOUNT_AVG` 默认值、
`pos/pct750/cv/slope_yr/touches/dwell_ratio/dwell_max_run/dwell_days/score/parts` 的字段名与含义、
`viewer/server.py` 里 `/api/universe_box` 的既有参数（`limit` / `min_dwell`）。
`tests/test_universe_box_mode.py` 把这几条钉成了断言。

### 为什么改

1. **有实证的预测力**，且方向与我们的判据同向。`tools/exp_finrl_indicators.py`（D69-勘误）
   用 stockstats 原库、300 只票、520 日训练 / 250 日样本外、逐维过三期因子门禁：

   | 维度 | 训练期 IC | 测试期 IC | 符号 |
   |---|---|---|---|
   | boll_lb/close−1 | +0.0614 | +0.0626 | 同号 |
   | 布林%B | −0.0535 | −0.0546 | 同号 |

   「越贴下轨、后续收益越高」= 我们的「越贴箱底越好」，只是标尺在动。
2. **规程要求**：外部方法第一顺位是升级四 tab 背后的判据，不是加工具。映射表里
   中线波段是唯一"有真实可替换点"的那一格。

### 结论：**这一条不足以推翻默认值，所以默认仍然是 static**

- 8 个样本日、`blend` 只赢 3 天、均值全线更低（T+20 −0.14pp）；`dyn` 更差。
  **没有任何一个 horizon 上动态尺稳定占优。**
- 它解决的是"名单不动"的**机制**（尺子会动），**没有**解决"选得更准"这个目标 ——
  这两件事必须分开说，否则就是拿"改了"冒充"改好了"。
- 所以：开关保留、**默认 static 不切换**。用户不主动设 `UNIVERSE_BOX_MODE`，线上结果与 D65 一致 ——
  准确说法是「**数值、排名、分项 100% 一致；payload 为加法式扩展**」（2026-11-03 QA 用改前落盘的
  `viewer/data/variants/unibox_5dcc0eedffee.json` 逐字段对比：693 只 × 13 字段 0 处不一致，
  但每行多了 8 个键、`params` 多了 5 个键。前端不读新键，故渲染不受影响）。
  原文写"逐字节一致"是**错的** —— 加字段必然改字节，那句话把"语义没变"说成了"字节没变"。

**顺带记一个没解决、但必须承认的观察**：两个模式的 Top40 在 T+20 上都**没有跑赢**
自己的候选池（static +0.29 vs 池 +0.40）。也就是说箱体排序在 20 日这个尺度上
目前贡献接近 0（T+5 有 +0.73 vs +0.40）。这不是换尺能修的，是"位置+驻留"这套判据本身的
问题，留作后续单独立项 —— 记在这里是为了防止它被"换尺 A/B 通过"这种叙事盖掉。

> ⚠ **上面这段里的绝对数字已被 QA 证伪（闸门前视），修正后的数字见下方「D71-修订」**：
> static Top40 T+20 − 候选池 = **−0.21pp**（结论不变，且更明显）。上文其余绝对收益数字同样作废。

### 什么条件推翻

1. **改默认（static → blend/dyn）**：累计 **≥20 个样本日**（或走 120 日 IC 门禁）后，
   配对差中位数 ≥ **+0.50 个百分点** 且胜率 ≥ **60%**（T+20 为准，T+5/T+10 不得反向）。
2. **删掉开关**：连续 20 个样本日胜率 ≤ 40%（即稳态确认无效）→ 保留 `boll_*` 字段与文档，
   删除 `blend`/`dyn` 分支，避免死代码。删之前必须在本文档追加一条说明。
3. **参数层面**：`W_POS_DYN`（现 0.5）、`BOLL_WIN`（20）、`BOLL_K`（2.0）、
   `BOLL_RANK_WIN`（250）任何一个调值都必须重跑本 A/B 并在本条下追加结果 ——
   "换权重也算换判据"，不能只在代码里改数字。
4. **`boll_pctb_rank` 的分子分母口径**若被改动（例如把 250 日换成 120 日），
   必须同步重跑自检第 3 条，因为它是拿 `pstdev` 逐日重算做对照的。

### D71-修订 · QA 验收后修了 3 项，并重跑了 A/B；**结论不变，但有一条绝对数字作废**（2026-11-03 当日）

上文（D71 主体）**保留原样不覆盖**，本节记录 QA 验收指出的三项问题、修法、以及在修好之后
重跑出来的数字。凡与上文冲突的，**以本节为准**。

#### 修 1：`universe_box_hist` 主键缺 `box_mode` —— 换了个触发路径的假跳变

**QA 实测的故障链**：主键是 `(trade_date, code)` 时，同一交易日先写 static(90)、再写 blend(99)，
`ON CONFLICT(trade_date,code) DO UPDATE` 把当天那行**改成** blend(99) —— static 快照被吞。
于是下一日 static 的 `prev_date` 跳回大前天，`d_score` 实际是**三个交易日**的变化量，
而 `delta.note` 仍写"与上一交易日对比"。这正是 D71 要消灭的那种假跳变，只是换了个触发路径。
我上一版只做了"按模式查询"，没意识到**主键本身**会让两把尺互相覆盖 —— 查询层再正确也没用。

**改法**：主键 → `(trade_date, code, box_mode)`。SQLite 改不了主键，所以走迁移：
`BEGIN IMMEDIATE` 事务内「建新表 → `INSERT ... SELECT` 搬数据（老行 `box_mode` 一律填 `static`）
→ DROP 旧表 → RENAME」。老库先 `ALTER` 补列再迁，所以从"两列主键且没有 boll_pctb 列"的
最老结构也能一次升上来。可重复执行：迁完主键就对了，下次检查直接跳过。

**在真实 `viewer/app.db` 上跑通的证据**：

| 项 | 迁移前 | 迁移后 |
|---|---|---|
| 主键 | `(trade_date, code)` | `(trade_date, code, box_mode)` |
| 行数 | 693 | **693** |
| 不同交易日数 | 1 | 1 |
| `box_mode` 分布 | 无此列 | `static` 693 |
| 抽样数值 | `000096 86.51 #1 / 300583 85.12 #2 / 300355 84.64 #3` | 同左，逐值一致 |
| 耗时 | — | **0.013s** |
| 幂等复跑 | — | 行数仍 693，无报错 |

**吞快照已不可复现**（探针行，用 `1990-01-02` + `ZZTEST`，不碰真实数据）：
同一天先写 static(90)、再写 blend(99) → 查询返回 `[('blend', 99.0), ('static', 90.0)]`，两行并存；
随后 `_attach_delta('1990-01-03', static 91)` 的 `prev_date` 是 `1990-01-02`、`d_score = +1.0`
（一个交易日），不再跳回更早的日期。探针行已清理，表回到 693 行。

#### 修 2：闸门的基本面前视（**这一条让上文的绝对收益数字作废**）

**QA 证据成立**：`gate.py` 取 `fundamentals` 只按 `symbol IN (...)`，没有报告期约束。
查库确认 `fundamentals` 是**每股一行的单快照**（5056 行 / 5056 个 symbol），
报告期只有三种：2025-09-30 ×1、2026-06-30 ×581、2026-09-30 ×4474 —— **没有多期历史**。

用改前的 `gate.py` 副本（`/tmp/gate_baseline.py`）与改后逐只对比（5563 只），**前视被证实**：

| 样本日 | 旧代码 hard / soft | 新代码 hard / soft | 说明 |
|---|---|---|---|
| 2025-08-04 | **105 / 415** | 0 / 0 | 旧代码用的全是 2026 年之后的财报；新代码挡掉 5046 行 → 闸门无数据 |
| 2026-07-31 | **105 / 415** | 18 / 66 | 旧代码与 2025 年那天**完全相同** = 典型前视特征 |
| 2026-09-28 | **105 / 415** | 18 / 66 | 同上 |

三个日期旧代码给出**一模一样**的 105/415，这就是"8 个样本日都在用最多 14 个月之后的财报"的铁证。

**改法（只加约束，不改任何阈值）**：
1. 取财报后按 `报告期 <= as_of` 过滤，被挡掉的行数记进 `diag["n_fund_future_dropped"]`，**不静默**；
   无报告期的行照旧放行（`report_date` 允许为空，用 SQL 三值逻辑会把 NULL 一起丢掉）。
2. `_stale_cutoff(as_of=None)`：显式传 `as_of` 时锚在 `as_of`，否则锚在今天。
3. `evaluate(..., diag=None)` 新增可选出参，回填"这一轮闸门到底有没有拿到数据"（`effective`）。

**线上实盘路径逐只对比 = 0 处差异**（`as_of=None`，5563 只）：
`hard 差异 0 只 · soft 差异 0 只 · penalty 差异 0 只`；
`diag` = `{as_of: 2026-11-02, n_snap: 5563, n_fund: 5046, n_fund_future_dropped: 0, stale_cutoff: 2025-09-29, effective: True}`
—— 最大报告期 2026-09-30 < 最新快照日 2026-11-02，所以过滤掉 0 行；陈旧锚点仍是"今天"。
（另测显式 `as_of='2026-11-02'`：锚点前移一天到 2025-09-28，结果仍 `0 / 0 / 0`。）

**残余偏差（必须写进任何引用这些数字的地方）**：`report_date` 是**报告期**不是**公告日**，
2026-06-30 的半年报实际公告多在 8 月底。所以 `报告期 <= as_of` 是**必要条件不是充分条件**：
`2026-07-31` 与 `2026-09-28` 两天放行的都是 2026-06-30 报告期（119 / 115 行），
**仍存在 ≤2 个月的"公告滞后型前视"**；其余 6 天闸门完全没数据，等于无闸门。
库里没有公告日字段，消不掉，只能标注。
