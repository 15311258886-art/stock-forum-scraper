## D61 AI 复盘从「研究助手」改为「荐股工具 + 账本」（2026-11-02）
- **背景（进哥原话，不修饰）**：「我是让你直接给我荐股的，你这个逻辑就不对……你得给我推荐东西啊，
  你给我讲一堆方向，我一个字一个字读去读研报，我用得着你吗？把结论给我。」
  以及：「你今天推的明天涨没涨啊，为什么没涨，你自己不得分析、不得反思吗？」
  以及：「往最底下看，得能看到你的预测准确率、收益率、涨跌率，不能光给我一堆假大空的空话。」
- **根因不在模型能力，在接口设计**：旧 `SYSTEM_PROMPT` 把 `opportunities` 定义为
  「symbol: 6位代码**或空**」，标题写「不是"推荐"，是"什么条件下才算"」。于是模型输出的是
  「低波池A级标的（98只）」「空仓/中证红利」这类**池名/策略名**——它们没有代码，无法验证，
  永远算不出对错。**一个允许留空的荐股字段，必然退化成方向性评论。**
- **结论（四条，缺一条就退回原样）**：
  1. **票单是主体**：新字段 `picks[]`，每只必须有 6 位代码、`score`(0-100)、
     `score_breakdown`(趋势/资金/位置/催化 各 0-25)、`entry_low/high`、`stop`、`target`、
     `horizon`、`thesis`(≤30字)、`why_now`(≤40字)、`evidence`(≥2条带数字)、`invalidate`。
     `score` 的含义**写死**为「未来 5 个交易日跑赢全市场等权概率(%)的估计」，
     且 **必须等于四项之和**（禁止先拍总分再倒推分项）。允许 `picks: []`（空仓是结论），
     但**不允许凑数**。
  2. **机检而非祈祷**：`ai_review.validate_picks()` 逐条检查代码格式、分数分解是否自洽、
     `stop < entry_low < entry_high < target`、价位是否 > 0、证据条数、是否含「占位/待补」字样。
     结果进 `picks_check`，前端显示为「票单 N 条有问题」，逐条红字标出。
     提示词是**请求**，机检才是**约束**。
  3. **次日就要能看到对错**：`review_score.HORIZONS` 由 `(5,10)` 扩为 `(1,3,5,10)`，
     并新增 `n1`（复盘日收盘 → 次一交易日收盘）。旧实现里 `if not hs: continue` 让
     「T+5 没到」变成「什么都不写」，于是**最短反馈周期是 5 个交易日**——慢到模型可以一直自我感觉良好。
  4. **认账要有对象**：新增 `picks_review[]`（逐票 `still_valid` / `first_break` / `fix`），
     上下文里注入 `review_score.picks_context()` 给出的**系统算出的收盘价事实**，
     模型只能在事实之上做归因，不能自评。禁止「市场环境变化」这类不指物的措辞。
- **首跑实测（2026-11-02 00:57，deepseek-chat，输入 11336 / 输出 1865 tokens，9.6s）**：
  产出 000568 泸州老窖 68 分（趋势20+资金25+位置13+催化10）、买入 128~133 / 止损 121.5 /
  目标 148 / 盈亏比 2.2，三条带数字证据；`picks_review` 逐条认了 10-28 那 5 只全错，
  并给出可执行的修正（「5 板开板一律不碰」「人气榜只作反向参考」「普跌日只做有板块资金流支撑的前排」）。
  **同时抓到一个真实缺陷**：它为凑「3 只」写了第二只 `entry/stop/target` 全 0、`thesis` 写「占位」的票。
  → 这条被机检红字标出，且**不入账**（见下条），页面上仍显示但标「未入账」。
- **两条数据纪律（都是实测踩出来的）**：
  1. **死账清理**：`kind in (pick, opp, avoid)` 但 `symbol` 为空的条目一律 `void` 并写明原因。
     实测 10-28 那批有 9 条这样的记录，永远 `open`，让「待回填 9 条」看起来像「还在验证」，
     实际是永远不会出结果的死账。**死账比没账更糟**：它虚高样本数、污染分母。
  2. **`not m_avg` 是陷阱**：全市场等权涨幅恰好 `0.0` 时它是 falsy，会把当天所有个股计分静默跳过。
     已改为 `m_avg is None`。
- **成绩单口径（命中率 ≠ 涨跌率，必须分开报）**：
  `hit` = 看对方向（看多要求超额 > 0）；`up` = **绝对收益 > 0** 的比例；
  `ret` = 平均绝对收益；`ex` = 平均超额。大盘普跌时「超额为正但账户是绿的」既不是纯对也不是纯错，
  只报一个数一定误导人。当前真实样本（截至 2026-11-02）：次日命中率 25%、上涨率 0%、均收 −5.49%、
  超额 −2.88%，n=4，**样本 <30，明确标注「只是趋势不是结论」**。
- **大脑 Key 的入口缺口（本次一并修）**：`PROVIDERS` 里 deepseek / hunyuan / qwen 三家早就写好，
  但**只有 `/api/settings/deepseek_key` 一个填写入口**，前端未配 Key 的按钮是 `disabled` 死按钮。
  所以「混元和通义千问没配」不是不支持，是**配不了**。现新增
  `POST /api/ai_review/provider_key`（写 Fernet 加密库）+ `provider_test`（1 token 最小请求验证），
  未配按钮改为「（未配 Key · 点我填）」，填完立刻验证、通了自动切过去重算。
  **需要澄清的事实**：Key 是用户自己云账号下的付费凭证，程序不能代为生成或开通；
  代码侧能做的只有「给入口 + 给直达申请地址 + 写完立即验活」。
- **影响模块**：`viewer/ai_review.py`（prompt / picks / validate_picks / set_provider_key /
  test_provider / picks_ctx 注入 / build_context 前回填）、`viewer/review_score.py`
  （HORIZONS / 迁移补列 / picks 入账 / n1 / 死账清理 / report 分档 / picks_board / picks_context）、
  `viewer/server.py`（`/api/ai_picks`、`provider_key`、`provider_test`）、
  `viewer/static/app.js`（票单表 / 对账表 / 成绩单 / 日期回看 / Key 填写 / 推理过程折叠）、
  `viewer/static/ai_review.css`、`tests/test_ai_picks_contract.py`（13 条含反例）、
  `tools/shot_ai_review.cjs`、`tests/routes_snapshot.json`（212 → 215）。
- **推翻条件**：若连续 20 个交易日、样本 ≥60 条后，`picks` 的次日命中率仍 ≤50% 且平均超额 ≤0，
  则说明「让模型直接选股」这条路径在本库数据上不成立 —— 届时应改为「规则引擎筛票 + 模型只做排序/否决」，
  而不是继续调提示词。**不许通过放宽 `score` 口径或删除不合格票来把数字做好看。**
- **兼容**：老记录（只有 `opportunities`）仍能计分与展示；`ai_call.kind='opp'` 保留，
  但新产出必须走 `picks`。`ai_call` 表用 `ALTER TABLE ADD COLUMN` 在线补列（SQLite 唯一可行的热迁移）。
