### 矛盾 2：龙虎榜避雷只看"上榜"，不看换手强度

  （`avoid.LHB_THRESHOLD = 15.0`，`avoid.py:140`），不在 `resonance.py` 留第二份常量。
  接法走**窄接**：只调 `avoid._lhb_turnover(con, codes, as_of=bd)`，**不**把 `avoid_payload`

### 矛盾 2 的两个追加发现（2026-10-31 只读复算，同一批改动必须一起处置）

**发现 A：15% 换手门槛对 ST 股有结构性偏差。**
`avoid.LHB_THRESHOLD = 15.0` 是在一般市场样本上标定的，而 ST/*ST 涨跌幅限 ±5%，换手天然上不去：

| 指标 | 实测（build_date=2026-10-30） |
|---|---|
| C+B 中 ST/*ST | **23 张** |
| 其中 `lhb_bonus < 0`（当前挂着风险标注） | **19 张** |
| 其中近 10 日换手 ≥15% | **1 张**（仅 `301030 *ST仕净` 18.3%） |
| ST 卡换手中位数 | **6.49%** |
| 这 19 张「其它理由为空」 | 绝大多数（仅 `002667` 另有 eng） |
| 展示 80 条中 ST | **2 张**（池子层影响 19 张，可见层 2 张） |

→ 直接把判据换成「换手 ≥15%」会让 19 张 ST 失去唯一理由。处置必须显式：
把 `_has_lhb` 拆成 `_lhb_hot`（换手≥15）+ `_is_st`（`name` 含 ST，与换手无关）——
ST 的风险来自"特别处理"这个**状态**，本来就不该搭在 `lhb_bonus` 上。
若不加 `_is_st`，就必须在已知限制里写明"19 张 ST 会失去标注"，**不许静默**。

**发现 B：`_has_lhb` 不等于"上过榜"，有 76 个反例。**

| | n |
|---|---|
| C+B 中 30 日内有上榜记录 | **505** |
| 其中 `lhb_bonus < 0` | 429 |
| 其中 `lhb_bonus == 0` | **76**（如 `000002 万科A`、`000560 我爱我家`） |

原因在 `resonance.py:982-983` 的三元式：多→`LHB_BONUS(-5)`、空→`LHB_PENALTY(-6)`、**中性→0**；
`_pull_lhb` 对 reason 归不了类的记录判中性（实测窗口内 22 条，全是「退市整理期」）。
所以真实语义是「`sig_unified` 里有该票的 LHB 信号**且方向非中性**」。
**"429/429 都有记录"是同义反复（先按 `bonus<0` 筛过再回头看），不能拿来论证"上榜即判红"。**

### 附：一个会造出假阳性的 SQL 坑（本轮踩到）

`prediction_item` 的代码列叫 **`symbol`**，不是 `code`。写

```sql
SELECT * FROM res_stock_card WHERE code IN (SELECT code FROM prediction_item WHERE tier='core')
```

时，SQLite 会把子查询里的 `code` 解析成**外层 `res_stock_card.code` 的相关引用**（correlated column），
于是 `code IN (code)` 恒真 —— 623 张卡"全部匹配 core 池"，结果看起来完全正常。
**跨表核对代码列名时必须先 `PRAGMA table_info`**，别假设都叫 `code`。
