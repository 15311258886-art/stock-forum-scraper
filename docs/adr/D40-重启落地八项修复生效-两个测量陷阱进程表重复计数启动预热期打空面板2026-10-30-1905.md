### 二、陷阱 ①：**每个 Python 逻辑进程在进程表里出现两次**

本机 `.venv\Scripts\pythonw.exe`（237KB）会再拉一个 base 解释器
`C:\Users\…\.workbuddy\binaries\python\versions\3.13.12\pythonw.exe`（90KB）作为**子进程**，
两者 `CommandLine` **完全相同**。真正跑代码、由 `/api/version` 自报 PID、真正持有端口的
是**子进程（base）**；父进程只有 ~6MB / 1 线程 / 0 CPU。

后果（本次实际踩到）：
- 「两个 `viewer.server`」「两个 guard」「两个 `predictor_daily`」**全是同一个逻辑进程被数了两次**，
  不是重复实例、不是重复任务；
- 本次我据此多杀了一个 PID（无实际损失，但判断是错的）；
- 之前「15:07 同批第二实例 PID 24676」的结论**作废**。

**正确判据**：以 `/api/version` 的 `pid` 为准（它只报真正在跑的那个）；
或比对 `ExecutablePath`——`.venv\Scripts\` 的是壳、`.workbuddy\binaries\` 的是本体。
**不要**用进程名/命令行数量判重复。

### 三、陷阱 ②：重启后 1~2 分钟内，面板会被打成「空占位」

同一份代码、同一个冒烟脚本，两次结果不同：

- **第一次**（重启后约 90 秒跑）：46 正常 / **2 空**（开源情报、豆包×主力共振）
- **第二次**（预热结束后跑）：**48 正常 / 0 空**

原因不是面板坏了，是**启动预热把请求线程占满**：日志显示预热
`/api/watch_list` **15154ms**、`/api/today_decision` 4487ms。此时用户点进去，
前端占位写在 `loadOSS()` / `renderResonance()` 里，接口排不到线程 → 面板停在占位。
预热结束后同一接口 `/api/oss` 56ms、点击渲染 268ms。

**据此确立两条规矩：**
1. **判断「面板是否真坏」不能只看一次探针**——接口单独 curl 快、但并发被预热抢占时，
   前端仍会空。必须（a）看 `/api/<x>` 独立耗时；（b）再走真实点击路径复测；
   （c）等预热结束复跑一次。
2. 与 D39 同源：单进程 + GIL + 无并发隔离。重启后的「冷启动窗口」是 D39 的最坏情况，
   方案 A（单飞 + 1~2s 共享）能同时缓解此处，**建议推进优先级上调**。
