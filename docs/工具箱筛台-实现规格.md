## 二、交互契约（以原型为准）

页面自上而下四段：

1. **头部**：`工具箱 · 筛台` + 右侧大数字「当前池子 5,264」
2. **筛道**：`[5264 干净宇宙] › [693 箱体谷底 −4,571 ×] › [675 准入闸门 −18 ×] › [出池 675 只]`
   - 每个节点显示：本步剩余数 + 工具名 + 本步砍掉多少 + `×`（单独撤掉这一刀）
   - 空态文案：`还没筛 —— 下面任点一张卡就开始了`
   - 右侧「清空」按钮
3. **建议下一刀**：`建议下一刀  双底（W）  679 → 103（砍掉 84.8%）  [就筛这一刀]`
   - **规则（2026-11-05 修订，原规则已废弃）**：不取「最狠的那一刀」，取「最接近目标剩余比例的那一刀」。

     进哥原话是「点一下筛取一半，再点又筛一半」——要的是**渐进收窄**。
     原规则「取剩余最少且 > 0」在空池时会推荐「短线冲浪 5264 → 4」「均线多头 679 → 2」，
     一刀切到个位数，后面十个工具全废，剩下的名单也没法挑。那不是建议，那是坑。

     目标剩余比例（池子越小，目标绝对值跟着收，避免最后几刀过狠）：

     ```js
     function targetRatio(cur) {
       var r = 40 / cur;          // 池子小于 267 只时，目标保底 40 只左右
       if (r > 0.5) r = 0.5;
       if (r < 0.15) r = 0.15;    // 池子大时，目标砍到 15%
       return r;
     }
     ```

     打分 = `|log(剩余/当前池) - log(目标比例)|`，最小者胜。
     用对数距离而不用线性差：线性差会系统性偏向「几乎不动」的工具——
     0.30 与 0.15 的线性差（0.15）远小于 0.90 与 0.15 的差（0.75），
     但那两个对用户的意义完全不同；取对数才是「按倍数看距离」。

     两条硬保护（不满足直接出局）：
     1. 候选剩余 < 5 只且当前池 > 50 只 → 排除（这一刀等于清空）
     2. 候选剩余 == 当前池（一点没砍掉）→ 排除（原地踏步，不是筛）

     当前池 ≤ 20 只时不出建议，改显示「池子已经很小了，再加刀容易一刀清空 —— 直接看名单」；
     一条候选都不剩时显示「剩下的工具要么砍不动、要么一刀就清空 —— 别再加刀了，直接看名单」。

     实测对照（2026-11-04 数据，20 个工具全预热）：
     - 当前池 5,264 → 目标 790，推荐「箱体谷底」699（对数距离 0.122，第二名 db_wave 532 为 0.395）
     - 当前池 679 → 目标 102，推荐「双底（W）」103（距离 0.011，第二名 MACD 底背离 60 为 0.529）
4. **工具墙**：网格卡片，每张 = 工具名 + 分组标签 + `现在点：675 → 38` + 底部一条杀伤力进度条
   - 已加入的卡片：青色边框 + 淡青底 + 「已在筛道 · 点一下撤掉」
   - 已淘汰工具：灰化、不可点、右下角标「已淘汰」，点它打开抽屉看淘汰原因

5. **结果表**：`最终 675 只` + 表格（名称 / 代码 / 得分 / 逐级 ✓✕ / 通过或淘汰原因）
   - 保留「显示被淘汰的 N 只」勾选
   - 表头标明得分来自哪个工具（沿用现有 `score_src` 逻辑）

### 2.7 2026-11-05 修订（QA 复核 + 负责人复盘后新增，以本条为准）

1. **「现在点」改叫「本次」**：卡片文字从 `现在点：5,264 → 5,018` 改为 `本次 5,264 → 5,018`，
   且整行不折（卡片最小宽 168px）。原来 4 张卡在 154px 宽度下折成两行，同排数字对不齐。
2. **会清空的卡要警示**（危险项）：`本次` 的结果为 0 时，不写 `→ 0`，改写 `→ 会清空`（红字）
   并在下方加一行「点下去池子就空了」；**点击前弹一次确认**：
   「这一刀会把 679 只全部筛掉，确定要看空池吗？」。结果 ≤5 只时写 `→ 3 只` + 「几乎清空」（琥珀色），
   点击只给一句提示、不弹框。这只影响展示与点击确认，`counted` 的真实数值不变，
   「建议下一刀」的排除逻辑也不变（它本来就排除 0 和个位数）。
3. **抽屉「最近一次运行」要说清楚是缓存还是现算**：缓存命中显示
   `本次：5,264 → 699 · 缓存命中（原始计算 63.6 秒）`；确实本次现算才显示 `本次：5,264 → 699 · 现算 63.6 秒`。
   原来的「这一次：… · 63.6 秒」会把缓存里记录的**当初耗时**误读成这次点击等了 63 秒。
4. **点击热区 ≥24×24**（视觉可以小）：卡片右上角 `i` 视觉仍是 14px 小圆点、筛道节点上的 `×` 视觉仍是
   13px 字号，但两者的元素盒子都撑到 24×24，量 `getBoundingClientRect` 得到 24×24。
5. **「已在筛道」用固定青系，不跟 `--accent`**：深色主题的 `--accent` 是品牌红，选中态跟红色会和
   「危险 / 已淘汰」撞语种，且红字压 12% 红底只有 3.37:1。改用跨主题变量
   `--tbx-on-border / --tbx-on-bg / --tbx-on-text`，实测对比度：浅色 6.65:1、深色 11.93:1。

## 三、后端

### 3.1 新文件 `viewer/toolbox_stack.py`

职责：单工具结果缓存 + 筛道求交。**不改 `viewer/toolbox.py` 的任何判据**，只调用它的 `apply_tool`。

```python
CACHE_DIR = <项目>/viewer/cache/toolbox_calc/     # 不存在则 makedirs

def tool_digest(tool_key: str, params: dict) -> str:
    """md5(json({t: tool_key, p: params}, sort_keys=True))[:16]
    ⚠️ 不要在这里做数值归一化（1.0 ↔ 1）：摘要一变，已落盘的缓存全部失效，
       20 个预热好的工具（7.7MB）要重算约 90 秒。int/float 差异在 _merge_params 消化。"""

def load_result(trade_date: str, tool_key: str, params: dict) -> dict | None:
    """命中则返回 {kept, dropped, score, marks, ms, note, cached=True}；
    落盘里的 trade_date 与当前最新交易日不一致 → 视为未命中（不能拿昨天的分数冒充今天）。"""

def compute_and_save(con, trade_date, tool_key, params, universe) -> dict:
    """调用 toolbox.apply_tool(con, tool_key, universe, params) 后原子落盘
    （写 tmp 再 os.replace）。

    ⚠️ dropped 里可能有 5000 条原因，落盘体积 300~600KB，这是可接受的：
       它只在最终名单展示时逐只回查，不做全书架加载。

    ⚠️ apply_tool 会往 tool_run_log 写一条记录。预热时每个工具只算一次，这条记录
       本身是有价值的留痕（"最近一次运行"），保留，不要绕过。
    """

def ensure_worker() -> None:
    """惰性启动一个**单线程**后台 worker（daemon），串行消费队列。
    串行不是偷懒：箱体类工具单次 7~8 秒，并发会把这台机器的 CPU 和磁盘打满。"""

def request_compute(tool_key, params, trade_date) -> None:
    """把 (key, params, trade_date) 放进队列。同一 digest 已在队列/在算 → 不重复入队。"""

def run_stack(con, spec: list[dict], limit: int = 200) -> dict:
    """spec = [{"tool": "box_bottom", "params": {...}}, ...]（顺序即筛道顺序）"""
```

`run_stack` 逻辑：

1. `trade_date = localfeed.latest_date()`
2. `universe = toolbox.universe_codes(con)`（只取一次）
3. 按 spec 顺序逐级：
   - `r = load_result(...)`；没命中 → `request_compute(...)`，记录 `pending = {tool, name, idx}` 并 **break**（后面的级算不了，因为没有输入）
   - `nxt = cur_set & set(r["kept"])`
   - 记 `steps.append({tool, name, in, out, drop, ms, source: "cache"|"fresh"})`
4. `counted`：对**所有未选中的、非 retired 的工具**，若已缓存 → `len(cur_set & kept_set)`；未缓存 → 值为 `null` 并 `request_compute`
5. `rows`：最终池按 score 降序取前 `limit`，每行给 `trace`、`marks`、`failed_at`、`reason`
   - `failed_at` / `reason` 从各级缓存的 `dropped` 里回查（第一个没通过的级）
   - 被淘汰的行同理（`tail` 部分，**单独给一份 `limit` 预算**）

   > **有意解读（2026-11-05 与主理人确认）**：原文是「最多补到 limit 条」，若按「最终名单 + 淘汰样本
   > 合计 ≤ limit」实现，则只要最终池 ≥ limit（例如 箱体谷底 + 准入闸门 = 679 只 > 200），淘汰样本
   > 一条都排不进去 ——「显示被淘汰的 N 只」这个勾选框在**最该用它的场景**下永远是空的。
   > 进哥要这个勾选框的原话是「筛出来都是什么样，死在第几级、为什么死」；最终池大于 200 时
   > 恰恰是最需要看淘汰样本的时候（说明这一刀砍得狠不狠）。
   > 所以实现为：**最终名单 ≤ limit，淘汰样本另给 ≤ limit**，合计最多 2×limit 行（约 80KB）。
   > 代价只是响应体变大一倍，收益是这个功能不会在最有用的场景里被关掉。
6. 返回：

```json
{
  "ok": true,
  "trade_date": "2026-11-04",
  "universe": 5264,
  "steps": [{"tool":"box_bottom","name":"箱体谷底","in":5264,"out":693,"drop":4571,"ms":7612,"source":"cache"}],
  "final": 693,
  "stage_sizes": [5264, 693],
  "counted": {"gate_admit": 691, "tv_wbottom": null},
  "pending": {"tool":"tv_wbottom","name":"双底（W）","idx":1},
  "rows": [...],
  "score_src": "箱体谷底",
  "warm": {"ready": 9, "total": 14}
}
```

## 附录 A：为什么可以「每个工具只算一次」——实测证据（2026-11-05）

整个筛台的地基假设是：

> 工具对**子集**算的结果 = 工具对**全宇宙**算的结果 ∩ 该子集

如果这条不成立，方案就是假的：卡片上「现在点 675 → 38」会变成近似值，用户按下这一刀却得到另一个数；
「建议下一刀」也会跟着错。所以这条**不能靠推理，必须实测**。

### 验证方法

对每个工具算两遍，比较集合是否**完全相等**（不是数量相等）：

```python
uni = toolbox.universe_codes(con)          # 5,264 只
sub = uni[:800]                            # 模拟「前面几刀剩下的一部分」
rf = toolbox.apply_tool(con, key, uni, prm)   # 全宇宙口径
rs = toolbox.apply_tool(con, key, sub, prm)   # 子集口径
assert set(rf["kept"]) & set(sub) == set(rs["kept"])   # 必须相等
```

### 为什么必然相等（代码层原因，不是巧合）

工具里的「分位」全是**单只票的时间序列分位**（60 日 25%~75% 中枢、750 日箱体位置、驻留比例），
判据逐只独立；评分走固定阈值 / 固定量纲，不随输入池大小变化。
全仓 `grep -n "rank\|截面\|percentile\|quantile\|分位" viewer/toolbox.py` 只在 `toolbox.py:1069`
命中一处 `pillar_item.rank` —— 那是**数据库列名**，不是对输入集做排名。

### ⚠️ 将来谁会打破这条前提

只要新增工具里出现下列任一种「相对池子」的判据，这个假设立刻失效，必须改方案（二选一）：

1. 按输入池做**截面排名 / 分位数**（「池内排名前 20%」「相对强弱优于同池中位数」）；
2. 按输入池做**归一化**（「涨幅高于同池均值」「PE 低于池内中位」）。

届时不能再「全宇宙算一次」，要么把**池子签名**也纳入缓存键（缓存粒度从「工具」变成「工具×池子」，
预热就失效了），要么把这类工具标记为「只能顺序算」。改之前请先回读本节。
