# 三处优化实施记录（2026-10-29 晚）

上一轮把「信号战绩」接进界面后，暴露出三个问题：所有超额都是**税前**的、AI 复盘用的**横截面数据停在 10-27**、全市场打分**没有历史留档**（IC 只能在每天选出的 20 只上算）。
本轮把这三处一起修掉，并顺带挖出两个更底层的原因。

---

## ① 回测加扣费口径

### 改了什么

`viewer/signal_backtest.py`

| 项 | 改动 |
|---|---|
| 新增 `--fee` | 默认 `0.0015`（双边 0.15%：佣金万2.5×2 + 卖出印花税万5 + 滑点） |
| 落库字段 | `signal_backtest` / `signal_baseline` 各加 `fee, winrate_net, avg_ret_net`（另加 `sharpe_net`） |
| 兼容老库 | `_ensure_col()` 用 `ALTER TABLE` 幂等加列，不重建表、不丢历史值 |
| 裁决口径 | `viewer/kernel/evidence.py` 的 `judge()` 改用**税后**值；税前值保留在接口里作对照 |

### 为什么必须做

实测全样本基线（5327 只 / 250 日）：

| 前向 | 税前胜率 | 税后胜率 | 税前均值 | 税后均值 |
|---|---|---|---|---|
| 5 日 | 46.12% | **45.35%** | −0.02% | **−0.17%** |
| 10 日 | 45.22% | **44.73%** | −0.05% | **−0.20%** |
| 20 日 | 44.18% | **43.80%** | +0.04% | **−0.11%** |

**20 日基线税前是正的（+0.04%），扣费后转负。** 这意味着任何"20 日超额为正"的结论，在税前口径下都可能是成本幻觉。

### 结论直接翻转

| 信号（前向 10 日） | 税前超额 | 税后超额 | 税前 → 税后 |
|---|---|---|---|
| 跌破BOLL下轨 | +0.8pt | **−0.31pt** | 有效 → 无效 |
| KDJ超卖金叉 | +0.6pt | **+0.41pt** | 唯一保持正超额 |
| RSI6超卖 | −0.1pt | −0.16pt | 无效 |
| 放量 | −5.9pt | −0.96pt（收益） | 反向 |

技术面聚合系数 `tech_factor` 从 **0.868 降到 0.693**（8 个反向 / 2 个有效 / 5 个中性），技术类权重 0.1499 → **0.1235**。

### 顺带修掉的性能问题

原写法 `df[c].iloc[i]` 是 pandas 标量访问，17 列 × 250 行 × 5300 只 ≈ **2260 万次**，单次约 5µs。
改为一次性 `to_numpy()` 后按行列取（数值完全等价，NaN/inf 同样转 None）：

> **全量回测 11.8 分钟 → 57 秒（12 倍）**

这一条是 ⑤「按市场状态分组回测」的前置条件——不加速就没法反复做实验。

## ② 横截面数据停在 10-27

### 表面现象

`stock_daily_snapshot` 最新只到 **10-27**，而 AI 复盘的复盘日是 10-28。它自己在结论里写了"数据陈旧，横截面结论须打折"——但这不该靠 AI 每次自己发现。

### 挖出的第一层：东财接口挂了

```
[sched-a_shares_snapshot.log]
10-27 21:03  第 1 页连续 3 次失败：Remote end closed connection without response
10-29 17:42  第 5 页连续 3 次失败：Remote end closed connection without response
```

实测当前东财 push2 **第 1 页就连不上**（不是分页偶发）。同刻腾讯 `qt.gtimg.cn` **5/5 成功**。

### 挖出的第二层（更严重）：失败被记成了成功

`tools/sched_job.py` 的 `main()` 原来只要不抛异常就 `return 0`：

```python
r = JOBS[name]()          # 返回 {'ok': False, 'error': '...'}
print("[%s] ok ..." % name)   # 日志写「ok」
return 0                       # 退出码 0 = 成功
```

父进程看到退出码 0 → 写下当日「已完成」标记 → **当天不再重试**。
这就是「日志里明明有错误，数据却静默停更」的完整机制，与 10-29 修的调度层「先写标记再启动」是同一类错误的两个层次。

### 改法

1. `sched_job.main()`：返回值 `ok is False` 一律判为失败（`FAILED(soft)`，退出码 1），让父进程走退避重试，而不是把失败记成完成。
2. `_a_shares_snapshot()`：东财失败自动降级腾讯通道。

### 结果

```
[a_shares_snapshot] ok 48.0s {'ok': True, 'trade_date': '2026-10-29',
  'collected': 5240, 'failed_batches': 0, 'fallback': 'tencent',
  'em_error': '第 1 页连续 3 次失败：Remote end closed connection without response'}
```

`stock_daily_snapshot`：10-27 → **2026-10-29（5240 只）**。

## ③ 全市场打分每日留档

### 问题

`stock_universe_scan` 以 `code` 为主键，每天覆盖写，**只有当前状态、没有历史**。
于是「评分到底有没有区分度」只能用每天选出的 top20 去算：

| 检验 | 结果 | 判读 |
|---|---|---|
| 日度 IC（2026-09-28 ~ 10-28，18 天） | 均值 **+0.030** | 每日仅 18~20 只，标准误 ≈0.056 → 在噪音内 |
| 逐日 IC 区间 | −0.468 ~ **+0.395** | 正负剧烈翻转，典型噪音特征 |
| core 层（评分最高）T+1 | **−0.95%** | 比 watch 层的 +0.09% 还差 |
| watch 层 T+1 | +0.09% | 评分最低的反而最好 |

core 在 T+1 落后 1pt、T+5 又追回 0.42pt，**方向自己打架**——这正是 IC≈0 的表现，也说明"继续调权重"在数学上不可能有效：归一化改的是相对比重，改不了整体没有区分度。

### 改法

1. `viewer/universe_scan.py` 新增 `stock_universe_scan_daily(trade_date, code, score, rank_pct, tier)`，每日约 5000 行，同日重复跑覆盖当日。
2. `trade_date` 改用 `df["date"].max()`（原来用 `iloc[0]`，取的是"第一只票的日期"，个体数据缺失时会串日）。
3. 新增 `tools/signal_ic.py`：读取端。算日度 Spearman IC、IC 均值与 t 值、五分层的平均收益与胜率；不足 `--min-days` 天时如实报"积累中"，不硬给结论。

### 现状

```
[signal_ic] 留档 1 个交易日（2026-10-27 ~ 2026-10-27），每日约 5327 只
前向1/3/5日：可用交易日 0（尚无已走完 N 个交易日的打分）
```

**只有 1 天，还没有前向收益可用**——这是诚实的起点。等到 5 个交易日后，`signal_ic.py` 就能给出第一个不受截断影响的 IC；30 天后样本量到 15 万级，标准误降到 0.01 量级，"这套评分该不该留"才会有确定答案。
