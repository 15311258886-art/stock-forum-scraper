总体结论

系统架构分层清晰、诚实状态机设计值得肯定（源状态「已接入 / 待激活 / 示例模式」分级、写操作串行化、WAL 并发读）， 这说明前期工程是有质量意识的。但按生产可用标准衡量，当前版本属于「演示形态完整、数据可信度不足」： 界面上每个数字都能显示，但支撑这些数字的三处核心算法（情绪打分、热度排序、时间归因）存在系统性偏差， 且示例数据与真实数据在库内混流、前端未逐条区分。因此：

  • 可作为：框架演示、数据源连通性验证、传导逻辑的结构化表达。
  • 不可作为：任何真实的板块涨跌判断或投资参考——除非先完成本报告 P0 级修复。

最大风险排序：① 数据真实性（示例混入 + 情绪噪声 69%）＞ ② 数据持久性（无唯一约束 + 刷新即清表）＞ ③ 服务健壮性（GET 无异常兜底）＞ ④ 展示正确性（字段契约漂移）。

一、程序设计：逻辑不严谨、边界缺失与潜在缺陷

1. 情绪打分用裸子串匹配，财经常见词被系统性误判 高

位置：overseas/lexicon.py:82-93（score_sentiment）　对比：lexicon.py:134-149（_count_kw 已用词边界）

问题：score_sentiment 仍用 low.count(w) 统计英文情绪词，未走同一文件内已写好的词边界函数 _count_kw。 于是 cut 命中 "executive"、miss 命中 "emissions / dismissed"、ban 命中 "urban / abandon? / banner"、loss 命中 "glossary"、fall 命中 "waterfall"。

实测取证（tools/audit_probe.py）： 
score=-1.00 看空 | Emissions target unveiled at climate summit
score=-1.00 看空 | Urban housing plan announced by ministry
score=-1.00 看空 | Company dismissed the report as inaccurate
三条完全中性的句子全部被判「看空」。在 seed 41 条真实语料上：子串命中 93 次、词边界命中 55 次，虚增 38 次（69.1%）。

原因：修复 classify_topic 的子串误分类时（"war" 命中 "starwars"），改动只落在一个函数，未同步到情绪打分；同类缺陷在同一文件内重复存在。

建议：score_sentiment 内英文词全部改用 _count_kw(low, w)；并对 cut/miss/ban/risk/sell/lower 等高风险短词补否定与词性白名单（如 "cut" 仅在 "cut rate / cut guidance / job cut" 上下文计分）。修完用本脚本回归，要求虚增比例 <5%。

2. 「热度」不是真实热度，且无时间衰减 高

位置：overseas/collect.py:47-49

问题：heat = (|情绪分|×2 + 主题命中数×1.5 + 1.0) × 区域权重 × 10。与阅读量、评论数、点赞、转发、转载媒体数完全无关；同时没有时间衰减项。

实测取证：三条 seed 条目 heat 分别 50 / 30 / 70，全部仅由情绪分值决定（主题命中数均为 0）。

原因：当前可用源（RSS/HTML）大多不暴露互动量，设计时用「情绪强度 × 主题密度」作为代理指标，但字段命名与界面文案仍叫「热度」，造成语义误导。后果：① 排序实质是「情绪激烈程度」而非「关注度」；② 三天前的旧闻与今天的新闻同权，「近期热点」可能全是旧闻。

建议：① 字段改名为 salience（显著度）并在界面注明口径；② 引入时间衰减 exp(-Δt/τ)（τ 建议 36h）；③ 对能拿到互动量的源（YouTube API、Reddit JSON、PeerTube views）接入真实互动数作为独立权重项；④ 「近期热点」增加 publish_time 下限过滤（如仅 72h 内）。

3. 缺失时间一律用「现在」填充，污染全部时间口径 高

位置：overseas/collect.py:55、scraper/parsers/taoguba.py:100

问题：解析不出发布时间时写入 datetime.now()。RSS 条目无时间、HTML 列表页无时间（parse_html_list 恒返回 publish_time=""，见 sources.py:296）时，这些条目全部被当成「刚刚发生」。

原因：为了让「按日趋势图」有数据而做的兜底，但没有打标记，导致趋势图中今天的数据被人为抬高、「近 5 日操作」虚高。

建议：写入 NULL 并加 time_missing=1 标记；趋势图与「近 N 日」统计排除该标记；界面显示「时间未知」。趋势图下方注明「N 条无时间戳未计入」。

4. first_seen 空串参与 min()，事件起始时间恒为当前时间 高

位置：overseas/hotspots.py:311

问题：min(r.get("publish_time") or "" for r in rows)——空字符串在任何非空时间之前，只要簇内有一条无时间，min 就返回 ""，随即被 or datetime.now() 顶替，真实最早时间丢失。

实测取证：rows = [2026-09-20, "", 2026-09-18]　现有写法 → ''；正确写法 → 2026-09-18 08:00:00。

建议：改为 min((r.get("publish_time") or "") for r in rows if r.get("publish_time"))，无值时再回落 now()。

5. 示例数据与真实抓取混流，前端未逐条标注 高

位置：overseas/collect.py:143-155（默认 include_seed=True）、viewer/static/app.js:447-452（新闻渲染）、app.js:489（界面承诺文案）

问题：联网抓取成功后，41 条人工示例条目仍会作为补充写入同一张 overseas_news 表。界面提示语宣称「真实条目与示例并存、逐条可区分」，但新闻列表渲染函数只输出 source_name 文本，没有任何针对「示例源·」前缀的视觉标记（仅数据源状态页 app.js:479 有 src-demo 样式）。用户在新闻流、热点证据链里看到「示例源·Reuters」与真实 CNBC 条目外观完全一致。

原因：seed 设计时为离线兜底（合理），但未随联网能力上线同步补上「示例」隔离与标注，形成实现与承诺不一致——这是本系统最需要警惕的一类缺陷：它不会报错，只会让人误以为看到的是真实舆情。

建议：① 数据库加 is_seed 列；② 新闻卡与热点证据链对 is_seed=1 强制加橙色「示例」徽章与浅底色；③ 顶部常驻横幅显示「本次含示例 N 条 / 真实 M 条」；④ 增加开关 include_seed（联网成功时默认关闭示例）。

6. 登录校验在配置缺失时「判定为成功」 高

位置：scraper/auth.py:88-93、viewer/ingest.py:209

问题：sites.yaml 中 success_marker: null → _looks_logged_in 返回 None，而调用处只在 verdict is False 时报错，None 被当作成功。密码错误、被踢回登录页也报登录成功。更进一步：ingest.py:209 中 sess = self._login(...) or RateLimitedSession()，登录失败后静默降级为匿名会话，抓到的登录页 HTML 被当作正文存库。

建议：marker 缺失时用「响应是否含登录表单 / 是否 302 到 /login / 关键 Cookie 是否存在」判定；返回严格 True/False；登录失败中止该站点并写入 login_status，禁止降级匿名。

7. 核心业务表无唯一约束，重复抓取必然重复入库 高

位置：viewer/db.py:66-158（posts/trades/news/positions/raw_pages/stock_mentions 建表）、db.py:598-633（均为裸 INSERT）

问题：只有 players(name)、persons(name)、login_status(site)、overseas_news(url,title)、overseas_hotspots(key) 有唯一键。国内链路五张表无任何唯一约束，每次点「抓取并更新」即全量重复累加；raw_pages 存整页 HTML，膨胀最快。taoguba.py:189 的 _post_id 在缺 id 时回退成 page_url，同页所有帖共用一个 id，叠加后导致存档只保留第一条。

建议：为 trades(post_id,action,symbol)、posts(post_id)、news(url)、positions(player,symbol) 建 UNIQUE 索引，写入改 INSERT ... ON CONFLICT DO UPDATE；_post_id 兜底改为 page_url + md5(正文前200字)[:8]。

8. 刷新即清空历史：既无失败保护，也无法「持续追踪」 高

位置：overseas/collect.py:126-127（reset=True 清空新闻表）、overseas/hotspots.py:177（clear_overseas_hotspots() 全清重算）

问题：① 每次刷新先清空再写入，若本次网络波动只抓到 3 个源，历史数据全部丢失，没有「抓取结果过少则保留上一版」的保护；② 热点每次全清重算，first_seen 恒为本次时间，无法回答「这个事件是新出现的还是持续了三天」——与「持续追踪」的核心需求直接冲突。

建议：① 改为「写入临时表 → 校验条目数 ≥ 上次 ×50% → 原子 RENAME 替换」，失败则回滚保留上一版；② 热点改为 upsert 保留首次出现时间，并产出「新增 / 持续 / 消退」三类状态，界面给出事件生命周期。

9. 时间解析跨年与相对时间失效 高

位置：scraper/parsers/taoguba.py:311-329

问题："%m-%d %H:%M" 无年份 → strptime 默认补 1900 年；「昨天 14:23」「3 分钟前」「前天」、纯日期格式一律返回 None，而上层无补齐逻辑。后果：db.player_detail 的「近 5 日操作」过滤直接失效。

建议：补齐 %Y-%m-%d、今天/昨天/前天 HH:MM、N 分钟/小时/天前；%m-%d 解析后显式补当前年，若结果 > now 则回退上一年。

10. GET 接口全部无异常兜底，一次异常即断连 高

位置：viewer/server.py:496-568（do_GET）、:537/:542/:566（int()）

问题：19 条 GET 路由无一条 try-except（POST 侧已有），且 int(q.get("min_holders")[0]) 等直接在路由里转换，?limit=abc 即抛 ValueError → 请求无响应 → 前端拿到断连。与 POST 侧的处理风格不对称，显然是遗漏而非有意。

建议：do_GET 整体包 try/except → {"error":..., 500}；参数统一走 _int(q, key, default) 辅助函数。

11. 全局关闭 SSL 证书校验 高

位置：overseas/sources.py:35-37

问题：_SSL.check_hostname=False; _SSL.verify_mode=CERT_NONE 作用于所有境外请求（含带 GitHub/YouTube Token 的私密请求）。任何中间人都可篡改返回的新闻内容，进而污染整个舆情结论，也可截获请求头中的 Token。

建议：默认开启校验；仅对个别确需放宽的源在 YAML 里加 insecure: true 并单独构造 context；Token 请求强制严格校验。

12. /api/person 提及股票写死 12 个代码 中

位置：viewer/server.py:424-427
实测取证：硬编码列表 = 600519 / 300750 / 000858 / 002594 / 601318 / 000725 / 603259 / 300059 / 600036 / 002230 / 000333 / 603501。

问题：人物详情的「提及过的股票」只在这 12 个代码中做字符串匹配，库里所有其他股票一概不出现——界面看起来像「此人只提过这几只」。

建议：改为从 stock_mentions 表按 author 聚合（该表本就按帖子记录了提及关系）。

13. 前端请求无状态校验、无失败兜底，异常即空白面板 中

位置：viewer/static/app.js:11-13（api()）、25 处 fetch 调用点仅 3 处有 catch

问题：fetch().then(r => r.json()) 不检查 r.ok；后端 404/500 返回 HTML 时 r.json() 抛错，面板停在上一状态或空白，没有任何报错提示。loadAll() 的 10 个并行请求全部裸奔。

建议：api() 改 async + if(!r.ok) throw；封装 safeRender(panel, fn, emptyText) 统一 catch 并渲染「加载失败+重试」。

14. 转义函数不处理引号，属性位存在注入面 中

位置：viewer/static/app.js:19-21（esc 仅替换 & < >）、:321/:450（href="${esc(url)}"）

问题：抓取源可控的 url/title 若含双引号即可闭合属性注入事件（x" onerror="）。正文文本位是安全的，属性位不安全。云中继（relay_json）内容来自第三方仓库，风险更高。

建议：esc 补 " → &quot;、' → &#39;；href 输出前校验 /^https?:/i，否则渲染为 #。

15. 字段契约漂移：同一含义三处口径不一致 中

位置：server.py:114-127（api_operating 未调用 _named()）对比 :84、:341

问题：/api/stocks、/api/consensus 都走 _named() 补全股票名称，/api/operating 没走 → 同一只股票在操作页显示「名称待补全」而在股票页正常。另有死字段（label、view_summary、heat_total、topics）与三条从未被调用的路由（/api/positions、/api/login_status、/api/stock_names）。

建议：api_operating 复用 _named()；清理死字段与死路由，或补前端消费，避免契约继续漂移。

16. 排序与截断的边界处理 中

位置：server.py:323、server.py:132 + app.js:239、app.js:266
  • ORDER BY rank_position ASC：SQLite 中 NULL 排最前 → 无名次选手占据榜首显示「-」。
  • api_persons LIMIT 100，前端 slice(0,80) → 静默丢弃 20 条且无提示。
  • Math.max(...list.map(t=>t.weight),1)：weight 为 null 得 NaN → 进度条宽度 NaN%。

建议：ORDER BY rank_position IS NULL, rank_position；截断处返回 total 并在界面提示「显示前 80 / 共 N 条」；数值一律 Number(x) ?? 0。

17. 采集端缺少状态码检查与编码指定 中

位置：scraper/pipeline.py:95、viewer/ingest.py:230、scraper/session.py:70
  • 三处取到响应后直接使用 resp.text，无 raise_for_status() → 403/404/500/反爬页照常入库并计为成功。
  • 未设置 resp.encoding，requests 对无 charset 响应默认 ISO-8859-1 → GBK 站点正文乱码，依赖中文的买卖模式（"买入/卖出"）100% 命中不了，表现为「抓到页面但 0 条记录」。
  • robots 拉取 rp.read() 无超时，且失败即放行、无负缓存。

建议：统一状态码检查；按 apparent_encoding 设置编码；robots 改用带超时的 requests 请求 + 失败负缓存。

18. 其他低优先级缺陷 低

  • collect.py:64：_daily_series(days=14) 的 days 参数从未使用，趋势图可能混入很早的日期。
  • server.py:486：静态文件路径检查用字符串前缀且未 resolve()，理论上存在 /static/../../ 穿越隐患（本地服务，风险有限）。
  • sources.py:106-110：PyYAML 解析报错时静默降级到 _mini_yaml，配置语法错误会被掩盖（此前 note 冒号事故即此类）。建议改为解析失败直接抛错并提示行号。
  • db.py 所有 save_* 单条 commit，707 条新闻 = 707 次提交，无批量事务、无回滚，中途失败留下部分写入的脏数据。
  • sources.py:566：8 线程并发无全局限速，GitHub 匿名 API 限额 60 次/小时，频繁刷新会 403；建议加每主机限流与 ETag 缓存。
  • app.js:453：异步渲染数据源面板无 generation 令牌，快速切换 tab 可能写入已被替换的 DOM；btnDemo/btnLogin 无 disabled 防抖。

其中「结论可回溯」建议优先做：热点卡已有 evidence 条目，但界面未把「概述/变量/板块预判」与具体条目建立点击关联。 把每条结论挂到它赖以生成的 2-3 条原文上，用户一眼能判断这条结论是「有据」还是「规则外推」——这是把系统从「看起来专业」推向「可核查」的关键一步。

方法与边界说明：本报告结论来自三部分——① 源码通读（server.py / db.py / overseas 四模块 / scraper 全量）；② 静态扫描（except 分布、timeout 覆盖、事务与唯一约束）；③ 实测取证脚本 tools/audit_probe.py（情绪误判、热度公式、first_seen、硬编码代码）。 标注「实测取证」的数据为脚本运行结果；其余为源码分析结论。未做的工作：实际联网抓一轮验证端到端、性能压测、浏览器交互回归（已有 40 项断言的既有测试未重跑）。
